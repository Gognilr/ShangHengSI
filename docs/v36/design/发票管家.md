## 一、定位与范围

### 1.1 解决什么

公司员工每月都要整理发票：报销、交财务入账、核对供应商开来的票。现在要逐张打开 PDF 或翻纸票，手抄号码与金额，还要靠人眼判断以下几件事：
* 抬头写没写对；
* 金额加税额是否等于价税合计；
* 这张票是否已经报过。

发票管家把这件事做完整：**收票 → 本机识别 → 本机核对 → 校对 → 台账 → 导出**，全程在本机，不调用模型。

典型场景：

| 场景 | 用户 | 发票管家做什么 |
|-|-|-|
| 月底报销 | 销售、采购、行政 | 拖入一个月的电子票与手机拍的纸票，得到报销明细 Excel 和两张一页的合并打印 PDF |
| 收票核对 | 采购、财务 | 供应商发来的专票逐张核对抬头税号、金额勾稽与重复 |
| 防重复报销 | 本人 | 同一张票第二次上传时提醒“台账里已有，已报销” |
| 红冲换开 | 财务、经办人 | 红字发票自动关联被冲的蓝字票，蓝字票标“已红冲” |
| 交接留底 | 本人 | 按开票日期、销售方、去向随时查找；原件按命名规则打包下载 |

### 1.2 适用票种

| 票种 | 内部代码 | 二维码种类码 | 常见格式 | 号码结构 |
|-|-|-|-|-|
| 电子发票（增值税专用发票），数电 | `de_special` | 31（样本实见） | PDF、OFD、XML | 20 位号码，无发票代码 |
| 电子发票（普通发票），数电 | `de_normal` | 32（样本实见） | PDF、OFD、XML | 同上 |
| 数电纸质发票（专用 / 普通） | `dp_special`、`dp_normal` | 待样本核实 | 纸票扫描、照片 | 同上 |
| 电子发票（铁路电子客票）、电子发票（航空运输电子客票行程单），数电 | `de_rail`、`de_air` | 待样本核实 | PDF、OFD、XML | 同上 |
| 增值税专用发票（含电子专票） | `vat_special` | 01、08 | 纸票扫描、照片、OFD | 发票代码 10 或 12 位，号码 8 位 |
| 增值税普通发票（含电子普票、卷票、通行费） | `vat_normal` | 04、10、11、14 | 纸票扫描、照片、PDF、OFD | 同上 |
| 其他（机动车、二手车统一发票等） | `other` | — | 任意 | 只取通用字段，全部标“请核对” |

* 数电票号码 20 位：第 1～2 位为年度后两位，第 3～4 位为省级税务局区域代码，第 5 位为开具渠道，第 6～20 位为顺序编码（国家税务总局公告 2024 年第 11 号）。
* 外贸商业发票（Commercial Invoice）不在此列，仍由工作台“单证核对”处理。

### 1.3 不做

* **不联网查验真伪**：外网只开放两处（模型网关、法规同步），发票管家不新增出口。台账导出包含查验所需的要素，用户到国家税务总局查验平台或电子税务局查验后，回到台账标记查验结果。
* **不送云端**：发票上的名称、税号、金额正是要取的字段，脱敏后就没有可提取的内容；版式又是国家统一的，确定性规则已经够用。发票管家不接模型网关，也不产生 llm\_calls。
* 不做进项抵扣计算、认证勾选、记账凭证、报销审批流：这些属于财务系统与电子税务局。
* 不跨人查重、不做全公司发票库：任何人只能看到本人的发票（owner\_id，非本人 404）。
* 不识别印章真伪，不识别手写批注。

## 二、技术路线与本机实测

按 SPEC 2A 三层分工，发票管家**只用第一层和本地 OCR**：

| 层 | 用在哪里 |
|-|-|
| 结构化数据 | 数电 XML、OFD 内嵌的原始发票数据与标签，直接读字段 |
| 确定性版式规则 | PDF 文字层与 OFD 版面文字，按坐标套国家统一版式 |
| 二维码 | opencv 自带 `QRCodeDetector`，取号码、日期、金额作独立证据 |
| 本地 OCR | 扫描件与照片走现有 RapidOCR、线框表格识别、去红章 |
| 云端模型 | 不用 |

**不新增依赖**：lxml、pdfplumber、pypdfium2、opencv-python-headless、rapidocr、openpyxl、Pillow 都已在锁定清单中；zip 用标准库。

**本机实测**（2026-11-27，开发机，用户提供的 11 张真实数电票 PDF）：只取结构信息，名称、号码、金额未进入仓库与对话。

| 项 | 结果 |
|-|-|
| 构成 | 11 张均为带文字层的数电票 PDF：普票 4 张（种类码 32），专票 7 张（种类码 31）；页面三种尺寸（A4 竖版、609×394 pt、600×512 pt） |
| 二维码 | 8 个逗号分隔字段：`01, 种类码, 空, 20 位号码, 金额, 开票日期, 空, 0～4 位`；开票日期有 `YYYYMMDD` 与 `YYYY-MM-DD` 两种写法 |
| 二维码对票面 | 号码、日期 11/11 一致；金额 9/11 等于价税合计，2/11 等于票面另一金额（待查是否为不含税合计） |
| 二维码解码 | 200 DPI 解出 5/11（609×394 pt 版式 7 张中有 6 张码太小），补试 300 DPI 后 11/11；每张 50～190 ms |
| 版式 | 一种版式的文字层顺序与标签不相邻，**必须按坐标取值，不能按文字顺序** |
| OCR 路径 | 把同一批 PDF 按 200 DPI 渲染后整页 OCR：每页 1.6～2.1 秒，首张另加约 25 秒模型加载；20 位号码命中 11/11，行置信度均值 0.994 |

基线机器上的耗时与扫描件、照片的准确率在 V36-I-03 实测（第十四节）。

## 三、入口、菜单与权限

* **侧栏**：“工具”分组下加 **发票管家**，排在“翻译”之后。路由 `/invoice`（台账与收票）、`/invoice/{batchId}`（批次校对）；图标 lucide `ReceiptText`，模块色“票赭”（澄明二版 6.29）。
* **权限**：不设权限点，所有账号可见，比照本地翻译。理由是全程本机、只看本人数据。导出需 `use.export`（与其他模块一致）。
* **侧栏数字**：本人“待校对”的发票张数，口径同 V35Q-22，只计等本人处理的事项。
* **一事一入口**：`/invoice*` 只高亮“发票管家”。

## 四、流程总览

```
收票（拖入 / 粘贴 / 选择，可含 zip）
  → 读取：检查格式，解开压缩包，按文件嗅探
  → 识别核对：XML / OFD 结构化 → 文字层版式 → OCR；二维码；同票合并；本机核对
  → 校对：自动通过的直接“已核对”，其余待你校对
  → 入台账：一批全部核对完，批次完成
台账：查找、标记去向与查验、导出 Excel / 合并打印 PDF / 原件包
```

* **批次**：每次收票是一个批次，即 tasks 的一行，kind=`invoice`、policy=`local_only`。发票本身进 `invoices` 表：每张票一行，跨批次构成本人台账。
* **批次状态**：`parsing`（读取与识别中）→ `active`（识别完成）。整批没有一张可识别的发票时为 `parse_failed`。待校对张数由 invoices 现算，不另存状态。
* **往返线**（本机三站，整条青色）：工具条站名为“读取 · 识别核对 · 校对 · 入台账”。

| 批次状态 | 当前站 |
|-|-|
| parsing | 读取或识别核对 · 进行中，旁写“第 n / N 个文件” |
| parse\_failed | 读取 · 失败，写原因 |
| active，待校对 > 0 | 校对 · 等你，按钮“去校对（n 张）” |
| active，待校对 = 0 | 全线完成，徽标“已完成 · 全程本机” |

迷你尺度的压缩：读取 → 读取；识别核对、校对 → 本机处理（有待校对时为“等你”）；入台账 → 完成。

## 五、收票：上传与文件检查

1. **方式**：入口拖入、点击选择、Ctrl+V 粘贴截图或文件；批次页可继续“加入发票”，加入后增量识别。
2. **格式**：PDF、OFD、XML、JPG、PNG、ZIP。只在发票管家接收 OFD、XML、ZIP，其他模块照旧。
3. **上限**：
   * 每批不超过 100 个发票文件，按压缩包解开后计算；
   * 单个文件不超过 20 MB，PDF 不超过 50 页；
   * 每批 OCR 合计不超过 100 页，沿用 8.7。
   * 超出时整批不收，提示原因与上限。
4. **嗅探**：按扩展名和文件头双重校验，沿用 17.6。
   * PDF：`%PDF`。
   * OFD：zip 格式，根目录有 `OFD.xml`。
   * XML：带 XML 声明，根元素为已知的发票根元素，例如数电的 `EInvoice`；其余 XML 拒绝。
   * JPG、PNG：文件头。
   * ZIP：只用于装运发票文件，不作为发票保存。
5. **压缩包**：只在内存中读，不解到磁盘。
   * 条目不超过 200 个，单个解压后不超过 20 MB，合计不超过 200 MB；
   * 路径只取文件名，忽略目录与 `..`；
   * 压缩包里的压缩包不打开；
   * 非发票格式的条目跳过，在批次页列“已跳过 n 个文件（格式不支持）”。
   * 加密压缩包与加密 PDF 拒绝，提示先解密。
6. **XML 与 OFD 的解析安全**：lxml 使用 `resolve_entities=False, no_network=True, load_dtd=False, huge_tree=False`。OFD 同压缩包规则，内部 XML 同此设置。
7. **同票多格式**：数电票常以 PDF、OFD、XML 三件同时下载。三者都作为原件保存，识别后合并为一张票（6.6）。
8. **存储**：原件以 UUID 名加密保存，沿用现有做法；`task_files.original_name` 存“压缩包名 / 条目名”，不超过 255 字。

## 六、读取与识别

### 6.1 取值顺序

每个字段都记下值和证据（来源、所在文件与页、坐标框、置信度）。来源可靠程度从高到低：

| 来源 | 说明 |
|-|-|
| `xml` | 数电 XML；PDF 内嵌的 XML 附件也算 |
| `ofd_data` | OFD 内的原始发票数据（`Doc_0/Attachs/` 下的发票 XML）或标签映射（`Tags/CustomTag(s).xml` 对应 `Content.xml` 对象） |
| `text` | PDF 文字层或 OFD 版面文字，按版式规则取 |
| `ocr` | 扫描页、图片，RapidOCR |
| `qr` | 二维码，只覆盖号码、种类、日期、金额，作独立核对，不覆盖其他来源 |
| `user` | 用户校对时改的值，保留原识别值 |

同一字段有多个来源时，取最可靠的来源；与其他来源不一致时报 IV-05 或 IV-13（第七节）。

XML 与 OFD 的节点映射在 V36-I-01 中用公开样例与本机样本核实，写成代码中的一张映射表。

**已知节点**：
* 数电 XML 的号码为 `TaxSupervisionInfo/InvoiceNumber`，开票时间为 `TaxSupervisionInfo/IssueTime`；
* 买卖方、金额与明细在 `EInvoiceData` 下的买方、卖方、基本信息与明细节点中。

### 6.2 文字层与版式规则

* PDF 页面可提取文字不少于 20 字的，按文字层处理（沿用 8.5）。字符串连同坐标一起取出（pdfplumber words）。
* **识别版式**：按标题与锚点判断。
  * 标题如“电子发票（增值税专用发票）”“增值税专用发票”“电子发票（铁路电子客票）”；
  * 锚点标签如“发票号码”“开票日期”“购买方信息”“价税合计（大写）”。
* **按锚点取值**：值取在锚点同一行的右侧或下一行，不按文字顺序（实测有一种版式的顺序与标签不相邻）。
* **购买方与销售方**：
  * 数电版式为左右两栏，按栏划分；
  * 传统版式为上下两框，按框划分。
  * 两栏或两框内各取名称、统一社会信用代码或纳税人识别号；传统版式另取地址电话、开户行及账号。
* **明细表**：
  * 表头“项目名称、规格型号、单位、数量、单价、金额、税率 / 征收率、税额”定出各列的横向范围，各行按纵坐标归行；
  * 项目名称跨行的按行距合并；
  * 读到“合计”行为止。
  * 项目名称保留税收分类简称，如“\*信息技术服务\*软件服务费”。
* **其他**：
  * 价税合计取大写与小写两处；
  * 备注栏整段取出；
  * 开票人；
  * 数电特定业务区（旅客运输、建筑服务、货物运输、不动产经营租赁等）按区内标签成对取。
* **铁路与航空客票**：按各自版式取乘车人或旅客、出行日期、车次或航班、出发与到达地、座位等级、票价、税率与税额（票面列有时）。

### 6.3 扫描件与照片

* 扫描页与图片按 200 DPI 交 RapidOCR，沿用 8.5 的渲染、去红章与线框表格识别。识别出的行带坐标，之后套用 6.2 同一套版式规则。
* **照片预处理**（只对 JPG、PNG）：
  * 按 EXIF 方向转正；
  * 找最大的近似四边形纸边做透视矫正（opencv），找不到时原图识别；
  * 先过方向分类，倒置的转 180°。
* 低置信的字段（OCR 行置信度低于 `ocr.low_conf`，与 8.5 同一阈值）在字段上标“请核对原件”。

### 6.4 二维码

* **解码**：在页面渲染图上用 `detectAndDecodeMulti`。
  * 先试 200 DPI；
  * 没解出时试 300 DPI；
  * 仍没有，再把四角各 35% 的区域放大 2 倍重试。
  * 实测 300 DPI 可解出全部样本。
* **解析**：按逗号拆分。
  * 第 2 段为种类码；
  * 第 3 段为发票代码（数电为空）；
  * 第 4 段为号码；
  * 第 5 段为金额；
  * 第 6 段为日期（`YYYYMMDD` 或 `YYYY-MM-DD`）。
  * 字段数少于 6 段或格式不符的，作“二维码无法解析”提示，不阻断识别。
* 二维码原文与其中字段一样加密保存，不写日志。

### 6.5 一页多票与非发票

* 一页里解出两个以上二维码，或出现两个以上发票标题时，按二维码与标题位置把页面切成多个区域，分别识别；切不开的提示“这一页像有多张发票，请分开拍或分开扫描”。
* 一个 PDF 有多页且每页一张票的（如合并扫描件），按页拆成多张。
* 没有发票标题、没有二维码、也没有号码锚点的页面或文件，记为“不像发票”，列在批次页的文件区，不进台账。

### 6.6 同票合并与指纹

* **指纹**：
  * 数电票 = HMAC-SHA256(子密钥, 20 位号码)；
  * 传统票 = HMAC-SHA256(子密钥, 代码 + 号码)。
  * 子密钥由主密钥经 HKDF 派生，用途标签为 `invoice-fingerprint`。
  * 指纹用于查重与红蓝关联，不能反推号码。
* 同一批次里指纹相同的识别结果合并为一张票：字段按 6.1 取最可靠的来源，各格式原件都挂在这张票下。合并后两种格式的同一字段不一致，报 IV-13。
* 与台账中已有发票指纹相同的，不合并、不拦截，报 IV-09，由用户决定保留或移出。

### 6.7 字段

| 组 | 字段 |
|-|-|
| 基本 | 票种、发票代码（传统）、发票号码、开票日期、校验码（传统普票）、红字标记、被冲蓝字号码（红字票） |
| 购买方 | 名称、统一社会信用代码 / 纳税人识别号；传统版式另有地址电话、开户行及账号 |
| 销售方 | 同购买方 |
| 金额 | 合计金额（不含税）、合计税额、价税合计（小写）、价税合计（大写）、税率（多个税率时列出全部） |
| 明细 | 每行：项目名称（含分类简称）、规格型号、单位、数量、单价、金额、税率 / 征收率、税额 |
| 其他 | 备注、开票人、特定业务要素（成对的标签与值）、客票要素（6.2） |

金额一律以 Decimal 保存与计算（ROUND\_HALF\_UP），单价按票面小数位原样保存。“免税”“不征税”写在税率中，税额“\*\*\*”按 0 计。

## 七、本机核对规则

**等级**：
* **错误**（红）：确定不对。
* **请核对**（琥珀）：可能不对，需要看原件。
* **提示**（天蓝）：需要知道的情况。

涉及 OCR 来源数字的计算不一致，一律降为“请核对原件”，不报错误，口径同 V34Q-57。

| 编号 | 检查 | 等级（文字层或结构化 / OCR） |
|-|-|-|
| IV-01 | 价税合计 = 合计金额 + 合计税额 | 错误 / 请核对 |
| IV-02 | 价税合计大写与小写一致（附录 B） | 错误 / 请核对 |
| IV-03 | 明细金额之和 = 合计金额，明细税额之和 = 合计税额 | 错误 / 请核对 |
| IV-04 | 每行税额与金额 × 税率之差不超过 0.06 元，合计税额之差不超过 1.27 元（V36Q-14）；单价 × 数量与金额之差超出单价末位精度 | 请核对；单价一项为提示 |
| IV-05 | 二维码与票面一致：号码、日期必须相同；金额等于价税合计或合计金额之一 | 错误 / 请核对 |
| IV-06 | 号码格式：数电 20 位，前两位与开票年份一致；传统代码 10 或 12 位、号码 8 位 | 错误 / 请核对 |
| IV-07 | 税号：18 位统一社会信用代码按 GB 32100 校验位（现有 `validators.uscc`）；15、17、20 位旧税号只查字符；购买方为个人时按身份证号校验位，或允许为空 | 错误 / 请核对 |
| IV-08 | 抬头：购买方与我方主体比对（V36Q-14）。名称一致但税号不同为错误；名称不在我方主体中为请核对；未录入我方主体时不检查 | 错误、请核对 |
| IV-09 | 重复：台账中已有同一张票的，写明所在批次与去向；那张已标“已报销”或“已入账”的为错误 | 请核对；已用过的为错误 |
| IV-10 | 开票日期晚于今天（上海时区） | 错误 / 请核对 |
| IV-11 | 票种一致：标题票种与二维码种类码对得上 | 请核对 |
| IV-12 | 红字：价税合计为负或标题含“红字”的标“红字发票”。备注中有被冲蓝字号码且台账里有那张蓝字票时，两张互相关联，蓝字票标“已红冲” | 提示 |
| IV-13 | 同票多格式不一致：同一张票的 PDF、OFD、XML 在某一字段取值不同 | 错误 |
| IV-14 | 特定业务要素：项目名称的分类简称为“建筑服务”“货物运输服务”“不动产经营租赁服务”时，特定业务区或备注里应写明项目地点、起运到达地或不动产地址，缺失的提示“财务可能退回”（V36Q-14） | 提示 |
| IV-15 | 低置信字段：OCR 置信度低于阈值的字段逐个列出 | 请核对 |

* 每条结果记编号、等级、涉及的字段与证据位置。说明文字中含金额与名称，与字段一起加密保存。
* 修改任何字段后，这张票的全部检查当场重算。
* 页面与导出固定写“未联网查验真伪”，不出现“真票”“合规”“无风险”之类的字样。

## 八、校对

* **自动通过**：同时满足以下三条的票直接记为“已核对”：
  * 所有字段来自 xml、ofd\_data 或 text；
  * 没有错误与请核对；
  * 二维码已解出且一致。
* 其余为“待校对”。**OCR 来源的票一律待校对**：二维码不覆盖名称和税号，照片识别错一个字，台账就错了。
* **校对页**：左侧是本批发票列表，中间是原件，右侧是字段（澄明二版 6.29）。
  * 点字段，原件上对应的框高亮；
  * 点核对结果，定位到涉及的两处。
* **改值**：就地改。改后标“已改”，悬停可看原识别值，同时重算第七节。
* **核对无误**：用户看过后点“核对无误”，这张票记为“已核对”。只有仍有“错误”的票，按钮写“仍有 n 项错误，确认无误”，需再点一次。
* **连续校对**：键盘操作。
  * Enter 记“核对无误”并跳到下一张待校对；
  * ↑ / ↓ 切换字段，F2 修改；
  * 只有需要看的字段高亮，其余淡显。
* **移出**：移出本批即删除这张票及只属于它的原件，例如重复上传的票。
* **批次完成**：本批待校对为 0 时，往返线走到“入台账”，批次完成。

## 九、台账

台账是本人全部发票，跨批次，是发票管家的首页主体。

* **每张票的人工状态**：
  * **去向**：未处理、已报销、已入账、已退回。可多选批量改，记下改动时间。
  * **查验**：未查验、正常、异常。异常须写原因，如“作废”“查无此票”。
  * **用途**：自由填写，不超过 100 字，如“11 月差旅”“项目 A 采购”，加密保存。
* **列表列**：开票日期、票种、销售方、购买方（仅当不是我方主体时显示）、价税合计、税额、核对状态、去向、查验、用途。
  * 默认按开票日期倒序，可按日期、金额、销售方排序；
  * 列多于 5 列且需排序，用表格换皮（澄明二版第四节）。
* **筛选**：
  * 开票日期区间、开票月份（点主图柱子）；
  * 票种、去向、核对状态、查验；
  * 销售方或购买方关键字、号码、金额区间、批次。
* **实现**：筛选、排序与合计在服务端解密后在内存中进行，只查本人数据。台账规模以每人万张以内设计，不建明文索引。
* **合计条**：列表顶部显示当前筛选的张数、合计金额、合计税额、价税合计。红字票按负数计入。
* **查验要素**：详情里列出查验平台所需的要素（号码、日期、金额，传统普票另有校验码后 6 位），可一键复制。

## 十、导出

需 `use.export`。文件只在服务器内存中生成，不落盘、不保存，沿用 17.8。审计日志记 `invoice_export`，只记格式与张数。单次不超过 500 张。导出范围为台账勾选的票或当前筛选结果。

1. **Excel 台账**（openpyxl）：
   * **“发票”表**：每张票一行，列为：
     * 序号、票种；
     * 发票代码、发票号码；
     * 开票日期；
     * 购买方名称、购买方税号、销售方名称、销售方税号；
     * 合计金额、合计税额、价税合计、税率；
     * 主要项目（第一行项目名称加“等 n 项”）、备注；
     * 核对状态、核对结果摘要；
     * 去向、查验、用途；
     * 原件文件名。
   * **“明细”表**：每个明细行一行，以发票号码关联。
   * **“汇总”表**：按票种 × 税率给出张数、合计金额、合计税额、价税合计。
   * 号码、代码、税号一律写成文本单元格，防止丢前导零或变成科学计数。金额写成数值，格式 `#,##0.00`。
   * 首行冻结，开启筛选，表头为中文。
2. **合并打印 PDF**（pypdfium2 在新文档中放置原页面）：
   * 数电专票这类横向小版式两张一页，放在 A4 竖版上；A4 大小的票一张一页；
   * 照片按矫正后的图像放置；
   * 可选“裁切线”“页脚写序号与用途”。
   * 只有 OFD、没有 PDF 的票不能合并打印，在导出前列出。
   * 原件不改，只是在新文件中引用页面。
3. **原件包**（zip）：
   * 所选票的原件按“开票日期\_销售方\_价税合计\_号码后 8 位.扩展名”命名；
   * 同票多格式的一并打包；
   * 文件名去掉非法字符，压缩包名下载时做安全编码。

## 十二、安全

* **不外发**：发票管家的代码不得引用模型网关（`app.llm`），V36-I-01 起在代码评审中核对；也不产生 llm\_calls。外网边界不变。
* **加密**：原件加密保存，沿用 17.3；字段、核对结果、二维码原文、用途均用主密钥加密；指纹为 HMAC，用 HKDF 派生的子密钥。
* **日志**：只记批次 id、文件数、张数、票种、耗时与失败原因类别，不记号码、名称、税号、金额、二维码原文与文件名，沿用 17.7。
* **审计**：`invoice_batch_create`、`invoice_batch_delete`、`invoice_export`，只记张数与格式。
* **上传**：嗅探、压缩包与 XML 解析的限制见第五节。
* **权限**：任何角色都看不到他人的发票，包括管理员，沿用 1.3。

## 十三、保留、删除与关联模块

* **保留期**：发票批次按 16.4 的两层处理，最后活动时间包括识别、校对、改去向、导出。
  * **原件层**到期：删除原件，台账字段保留；页面写“原件已按保留期限删除”，不能再合并打印或下载原件包。
  * **结果层**到期：整批连同发票删除。
  * 设置 · 数据 · 数据保留的两项说明各加“含发票管家”，不新增保留项。
* **删除**：删除批次即彻底删除其原件、发票与核对结果，沿用 17.8。移出单张只删这张及只属于它的原件。
* **历史记录**：类型分段增加“发票管家”。
  * 批次名为“发票 · {上海时区日期} · n 张”，不含名称；
  * 问题摘要为“待校对 n · 错误 m”。
* **工作台**：模块卡增加发票管家，写“待校对 n”，点开进 `/invoice`（澄明二版 6.4）。
* **全局搜索**：只按批次名搜到批次，台账内容用台账自己的筛选。
* **单证核对**：发票管家不与合同、订单比对。需要比对时，把发票原件拖进工作台，用“单证核对”。

| 段 | 含义 | 实见 |

| 2 | 种类码 | 31 专票 7 张，32 普票 4 张 |
| 3 | 发票代码 | 数电为空 |
| 4 | 发票号码 | 20 位 |
| 5 | 金额 | 9/11 等于价税合计 |

## 附录 B 大写金额

* **数字**：零壹贰叁肆伍陆柒捌玖；单位：拾佰仟万亿；元或圆、角、分；“整”或“正”结尾。
* **负数**：以“负”或“（负数）”开头。
* **做法**：解析为 Decimal 与小写比较。解析失败时按 OCR 来源处理，记“请核对”，不报错误。
