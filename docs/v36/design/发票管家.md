# 发票管家 · 功能设计规范（V3.6）

2026-11-27 Opus 起草；同日按用户要求精简为“只把发票整理成 Excel 清单”（V36Q-16），取代此前的台账版本。

* **界面**：[澄明二版设计规范](../../design/v36/澄明二版设计规范-草案.md) 6.29。
* **合并**：V36-Z 把本稿并入 SPEC：新增 13D 节，同步 1.6、19、20 节。

## 一、做什么

**一件事**：拖入一批发票，在本机识别，下载一份 Excel 发票清单。

* 全程本机，不调用模型，不接模型网关。
* 不留记录：原件和识别结果只在服务器内存盘中，下载后或超时自动清除，不进历史记录。
* 页面上只看识别进度和清单预览，不在页面上改值。识别有疑问的行在 Excel 的“核对提示”列写明，由用户在 Excel 里自己改。

**不做**：
* 台账与历史；
* 页面上的校对与改值；
* 去向、查验、红蓝关联、跨批查重、抬头比对；
* 合并打印 PDF、原件包；
* 联网查验真伪、送云端识别。

## 二、适用票种与格式

* **票种**：数电票，包括专票、普票、纸质版，以及铁路电子客票、航空电子客票行程单；传统增值税专用发票与普通发票，包括电子普票、卷票、通行费。外贸商业发票不在此列，仍用工作台“单证核对”。
* **格式**：
  * PDF：带文字层的电子票，或扫描件；
  * JPG、PNG：扫描件与照片；
  * XML：数电票；
  * OFD：只读其中的结构化数据，读不出的提示“请改传 PDF”；
  * ZIP：只用于一次装运多个上述文件。
* **上限**：
  * 每批不超过 100 个文件，按压缩包解开后计算；
  * 单个文件不超过 20 MB，合计不超过 200 MB；
  * OCR 合计不超过 100 页。
  * 超出时不收，提示原因。
* **上传检查**：
  * 按扩展名与文件头双重校验，沿用 17.6；
  * 加密的压缩包或 PDF 拒绝；
  * 压缩包只在内存中读：条目不超过 200 个，路径只取文件名，压缩包里的压缩包不打开；
  * XML 与 OFD 用 lxml 的安全设置：`resolve_entities=False, no_network=True, load_dtd=False`。

## 三、识别

按 SPEC 2A 只用确定性规则与本地 OCR，不新增依赖。

* **取值顺序**：
  1. XML、OFD 结构化数据：直接读字段；
  2. PDF 文字层：按坐标套国家统一版式；
  3. 扫描件与照片：走现有 RapidOCR，沿用 8.5 的渲染、去红章与线框表格识别，照片先按 EXIF 转正并做透视矫正；
  4. 二维码：取号码、日期、金额，只用于核对，不覆盖其他来源。
* **按坐标取值**：值取在“发票号码”“开票日期”“购买方”“价税合计”等锚点的同一行右侧或下一行。实测有一种版式的文字层顺序与标签不相邻，不能按文字顺序取。
* **二维码解码**：先试 200 DPI，解不出再试 300 DPI。
* **合并与拆分**：
  * 同一批里号码相同的视为同一张票，合并为一行。例如同一张数电票的 PDF、XML、OFD，或同一文件传了两次。
  * 一页多票按二维码与标题位置切开；切不开的，提示“这一页像有多张发票”。
  * 认不出是发票的文件，列入“未识别”。
* **金额**：一律用 Decimal（ROUND\_HALF\_UP）。
* **核对提示**：只做下面四项。提示写进清单的“核对提示”列，不拦截导出。

| 检查 | 提示 |
|-|-|
| 价税合计 = 金额 + 税额 | “价税合计与金额加税额不等” |
| 大写金额 = 小写金额 | “大写与小写金额不一致” |
| 二维码中的号码、日期、金额与票面一致；金额等于价税合计或金额之一 | “二维码与票面不一致：{字段}” |
| 照片或扫描识别的字段置信度不低于 `ocr.low_conf` | “照片识别，请核对：{字段}” |

## 四、Excel 发票清单

文件名为“发票清单\_{上海时区日期}\_{n}张.xlsx”，用 openpyxl 在内存中生成，下载需 `use.export`。

* **“发票清单”表**：每张票一行，按开票日期升序。列依次为：
  * 序号、票种；
  * 发票代码、发票号码、开票日期；
  * 购买方名称、购买方税号、销售方名称、销售方税号；
  * 项目名称：第一行明细，后面加“等 n 项”；
  * 金额、税额、价税合计、税率：多个税率时全部列出；
  * 备注、文件名、核对提示。
  * 最后一行为合计，写张数、金额、税额、价税合计。红字票按票面负数计入。
* **“未识别”表**：只在有未识别的文件时出现，列文件名与原因。
* **格式**：
  * 号码、代码、税号写成文本，不丢前导零，不变成科学计数；
  * 金额写成数值，格式 `#,##0.00`；
  * 表头中文，首行冻结，开启筛选；
  * 有核对提示的行，提示单元格用浅琥珀底。

## 五、不留记录

* **内存盘**：单独的 tmpfs 卷 `invoice_mem`，大小 1 GiB，只挂给 app 与 worker。
  * 原件与识别结果用主密钥加密后放在这里，不写持久卷，不进备份；
  * 页面图与中间结果只在当次处理的进程内存中，用完即丢。
* **清除时机**，以下任一先到即清除：
  * 用户点“清除”，或开始新的一批；
  * 识别完成后 30 分钟；
  * 上传后 2 小时；
  * 服务重启，内存盘随之清空。
* **其他规则**：
  * 每人同时只有一批，开始新的一批即清除上一批；
  * 内存盘余量不足时，提示“服务器正忙，请稍后再试”；
  * 离开页面后 30 分钟内回来，仍能看到结果并下载。
* **数据库**：不新增表。识别任务用 jobs 一行：
  * 类型 `invoice`，迁移一条，只给 jobs 的类型约束加这个值；
  * payload 只有批次随机 id 与 owner\_id，progress 只有计数，不含文件名与内容。
* **审计**：只记 `invoice_export` 与张数。

## 六、接口（前缀 `/api/invoice`）

所有接口校验 owner\_id，非本人一律 404。

| 方法 | 路径 | 说明 |
|-|-|-|
| POST | /batches | 上传并开始识别（multipart）；返回批次 id |
| GET | /batches/{id} | 进度；完成后返回清单预览的行与未识别文件 |
| GET | /batches/{id}/excel | 下载 Excel 清单，需 use.export |
| DELETE | /batches/{id} | 清除 |

## 七、安全

* **不外发**：模块不得引用 `app.llm`，不产生 llm\_calls，外网边界不变。
* **日志**：只记批次 id、文件数、张数、耗时与失败类别；不记号码、名称、税号、金额、二维码内容与文件名（17.7）。
* **权限**：菜单与下载都按 `use.export` 判断；任何人只能看到自己的这一批。

## 八、本机实测与评测

**实测**（2026-11-27，开发机，用户提供的 11 张真实数电票 PDF）。只读结构，名称、号码、金额没有进入仓库与对话。

| 项 | 结果 |
|-|-|
| 构成 | 11 张都是带文字层的数电票 PDF：普票 4 张（二维码种类码 32），专票 7 张（31）；页面有三种尺寸 |
| 二维码 | 8 个逗号分隔字段：`01, 种类码, 空, 20 位号码, 金额, 日期, 空, 末段`；日期有 `YYYYMMDD` 与 `YYYY-MM-DD` 两种写法 |
| 二维码对票面 | 号码、日期 11/11 一致；金额 9/11 等于价税合计 |
| 二维码解码 | 200 DPI 解出 5/11，补试 300 DPI 后 11/11；每张 50～190 ms |
| OCR 路径 | 同一批 PDF 渲染成 200 DPI 图片后整页 OCR：每页 1.6～2.1 秒，号码命中 11/11 |

**评测**（2A ③）：
* **效率**：在基线配置（10 vCPU、无 GPU）上测每张耗时，分文字层、扫描、照片三类；另测 100 张一批的总耗时。
* **质量**：关键字段为号码、日期、税号、金额、税额、价税合计。
  * 文字层与结构化：准确率 100%；
  * 清晰扫描：不低于 98%；
  * 照片：不低于 95%，识别错的字段须全部带上核对提示。
* **样本**：
  * 虚构样本放在 `backend/tests/fixtures/invoice/`，票面带“虚构样本”水印；
  * 真实样本只在本机评测，报告只写比率与耗时。
* **用例**：
  * 每种格式一条；
  * 四项核对各一条；
  * 合并同票一条；
  * Excel 格式一条：文本号码、合计行；
  * owner 404 与 use.export 各一条；
  * 清除一条。
