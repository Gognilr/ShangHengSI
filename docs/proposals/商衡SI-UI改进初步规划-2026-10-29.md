## 一、审核时先看什么

建议先读第二节的决策状态、第九节的技术路线、第十一节的实施顺序，以及第十四节的待审核清单；再结合第十六节的截图检查具体体验。

本次希望 Opus 判断：

1. 智能助手优先、双布局和设置直达的产品方向是否形成了完整且一致的信息结构。
2. Nuxt UI 的迁移收益是否足以覆盖组件替换、样式体系转换和回归成本；是否先保留 Element Plus 更合适。
3. 两种布局是否能严格共用组件、状态与业务流程，是否存在被低估的空间和维护成本。
4. 哪些内容进入首个改造批次，哪些应后置；与当前 V2-D-10、V2-Z 和版本发布如何衔接。
5. 哪些 SPEC、界面规范和任务卡需要由 Opus 提出正式修改稿，再交用户确认。

## 三、当前系统基线

### 3.1 已有能力

当前系统已经有三个主入口：智能审核、审核历史、智能助手；设置仅管理员可见。不能依据旧参考资料，把“增加智能助手”误写成从零建设的功能。

| 位置 | 当前基线 | 本次拟改进点 |
|---|---|---|
| 登录与默认首页 | 默认进入 `/review/new`；有登录恢复、权限守卫及强制改密 | 建议默认进入 `/assistant`；保留深链接和现有鉴权行为 |
| 公共布局 | `MainLayout.vue` 中的顶部导航、用户区和管理员提醒 | 抽取可切换的公共布局，调整入口顺序与空间分配 |

## 四、目标与范围

### 4.1 首期目标

1. 用户登录后容易开始一次会话，也容易找回已有会话；智能审核仍有清楚的独立入口。
2. 主要阅读区域安静、连续，常用操作容易发现；辅助信息按需要展开。
3. 设置直接进入可工作的页面，分类层级清楚，减少多余跳转。
4. 两种导航布局可选择、可恢复，切换不丢失当前工作状态。
5. 所有页面使用同一套视觉规则、控件语义和错误反馈。
6. 保持现有业务契约和安全边界，以真实前端回归证明改造没有削弱功能。

### 4.2 范围边界

首期覆盖公共布局、智能助手、智能审核及结果、历史、八类设置、登录，以及这些页面使用的业务弹窗和抽屉。可以分阶段实现，最终形成完整覆盖。

本规划不新增仪表盘、“我的待处理”、部门协作、会话共享、联网搜索或自动代理等能力；不将智能助手变成绕过智能审核专业流程的入口。客户端封装、本地文件工作区和服务器存储生命周期不随 UI 重构实施。

## 五、信息结构与双布局

### 5.1 共同结构

主导航建议依次为：**智能助手 → 智能审核 → 审核历史**。设置保留管理员入口；个人界面偏好放在所有登录用户可访问的用户菜单内，与管理员设置权限分开。

建议将默认首页改为 `/assistant`。访问原有任务、会话、设置深链接时仍进入原页面；登录重定向、强制改密和权限守卫须一起核对。进入空白助手首页不应仅因页面加载就自动创建一个空会话。

### 5.2 默认侧栏布局

```text
全局侧栏                    主工作区                         按需展开的文件区
品牌 / 新建会话             当前会话标题、必要操作            文件及解析、确认状态
智能助手 / 智能审核 / 历史   对话、引用和结果                  原文 / 外发文本入口
近期会话（助手场景）         输入区、模板、发送条件             脱敏与待处理提示
设置 / 用户菜单
```

- 助手场景中的会话列表与全局侧栏整合，避免再叠一列内容相同的导航。
- 离开助手时，会话区不占用审核或设置的主要操作空间。
- 文件区默认收起；存在待确认文件、解析失败等事项时，工作区保留明确的数量、状态和处理入口。
- 提供侧栏展开、收起能力。审核结果的原文阅读优先，收起行为及恢复规则由正式设计确定，不静默改变用户选择的导航布局。

### 5.3 顶部导航布局

```text
品牌 / 智能助手 / 智能审核 / 审核历史                 设置 / 用户菜单
会话列表（助手场景）       当前会话及输入区             按需展开的文件区
```

- 顶部导航与侧栏导航使用同一份菜单定义和权限判断。
- 会话列表仍使用同一套组件与数据；仅在助手场景安排到页面内。
- 内容区的字体、卡片、表格、确认流程和操作位置规则保持一致。

### 5.4 切换与保存规则

1. 首次使用建议默认侧栏；用户选择后恢复上次有效偏好。
2. 首期建议只保存当前浏览器的界面枚举，不增加账号偏好接口；跨设备同步另行评估。
3. 个人偏好不能写入文件内容、名称、消息、脱敏映射或接口返回的业务数据。新增偏好项和存储键须先写入正式设计。
4. 读取失败、值无效、浏览器禁用存储时，使用默认布局，业务仍能使用。
5. 切换不刷新页面、不改变当前路由、不重复请求生成、不重建业务页面实例。
6. 草稿、当前会话、模板参数、文件区展开状态、审核筛选与问题选择、设置分类和未保存字段都要保留。
7. 用户正在阅读的段落或原文定位应尽量保持；因宽度重排无法保持精确像素时，优先保持消息、问题或段落锚点。
8. 模态确认期间遵守焦点约束，不提供绕过确认或在后台触发发送的路径。

两种布局是一套产品的两种导航排列，不分别维护两套业务页面，也不增加第三种导航形态。

## 六、主要页面体验

### 6.1 智能助手

- 空白会话以输入区为主要入口，辅以简短用途说明和现有五个模板；不增加装饰插画或大面积欢迎卡片。
- 对话正文按连续阅读排版，适度区分用户消息与助手回复，避免每段回复都装进厚重卡片。
- 输入区清楚显示已选文件、模板参数、知识库及历史引用选项；只在需要时展开详细参数，但发送前能够检查有效选择。
- 文件管理、脱敏和引用不会因为文件区收起而失去入口；未确认文件不能被视觉上的“已上传”状态误导为可外发。
- 生成、停止、失败、重试、不可发送、只读及保留期到期均使用真实服务端状态；保留已有并发和调用上限行为。
- 保留现有五个模板及其专用展示：翻译的译文与对照、比价的本地计算表格、摘要、起草回复、单证核对。
- 原文定位、引用来源、复制及 Word / Excel 导出保持可发现；没有实际可导出内容时说明原因。
- 历史合同仅限本人且按现行选择规则使用；知识库服从管理员开关和现有会话设置，不因界面重排扩大检索或外发范围。
- 消息及模型内容继续按安全文本节点渲染；组件库提供的聊天组件不自动获得接管业务渲染和外发流程的资格。

**特别说明：**“设置不再弹中间窗口”与“取消发送确认”没有关联。每次发送前仍按 V2Q-127 展示确认内容、处理疑似项，并由服务端重新执行校验；首次加入文件的脱敏确认也继续保留。

### 6.2 设置

- 点击设置直接进入完整页面。系统管理员、业务管理员、兼任角色只看到各自有权限的分类。
- 默认进入有权限的设置分类；优先恢复上次合法分类还是使用角色默认分类，列入正式设计决定。
- 使用“分类导航＋标题与用途说明＋表单或列表＋操作反馈”的一致结构。
- 账号、模型、审核要求、法规库、公司范本、知识库、脱敏、数据八类沿用现有资源与接口，不因视觉分组增加新业务分类。
- 表单的修改、保存中、保存成功及失败要明确；切换布局保留未保存字段，切换设置分类的离开提醒策略单独定义。
- 新增、编辑、删除确认等局部操作可使用对话框；完整设置目录不放在对话框中中转。
- 数据保留、主密钥和删除等高影响操作继续采用各自既有确认、权限和结果提示。

### 6.3 智能审核、审核结果与历史

- 保留上传与设置、确认脱敏、审核中及结果的专业流程，明确本地校验与智能助手的能力差异。
- 确认脱敏保留原文与外发文本对照、疑似项处理、我方选择和提交条件；底部操作区域不能遮挡内容。
- 审核结果突出结论、问题、原文与依据的层次；问题清单与原文独立滚动，选择问题后仍能准确定位。
- 避免重复呈现同一筛选条件；等级语义、覆盖情况、失效引用、轮次状态及固定声明保持现行契约。
- 历史列表保持本人范围、筛选、分页、进入任务及删除规则，优先提升列宽与长文件名的阅读质量。
- 解析和审核中的进度来自实际状态；没有真实进度时不编造百分比或预计剩余时间。

### 6.4 登录与公共反馈

- 登录延续商衡SI品牌，不增加无对应能力的注册、忘记密码、外部登录等入口。
- 强制改密、退出、鉴权过期、无权限、资源不存在及管理员提醒保持现有处理规则。
- 加载、空白、失败、拦截、只读和重试采用统一文案与视觉层级，不用短暂提示替代必须处理的持续状态。

## 七、视觉与阅读规范建议

以下为本稿建议值，供 Opus结合截图与四种桌面窗口评定；批准前不替换现行 `frontend.md`。

| 项目 | 初步建议 | 目的 |
|---|---|---|
| 品牌与色彩 | 中性底色，深海蓝作为主要品牌色，青蓝仅用于少量辅助强调 | 克制、清楚，避免整页高饱和 |
| 界面正文 | 15px，行高约 1.6～1.7 | 比当前常规正文更易读 |
| 长文与对话 | 默认 16px，行高约 1.8 | 适合中文合同、来函和持续会话 |
| 标题 | 页面标题约 24px，区块标题 18px，分组标题 15～16px | 减少字号档位，建立稳定层级 |
| 辅助信息 | 通常 13px；12px 仅用于少量非核心说明 | 避免把操作条件和错误写得过小 |
| 字重与字体 | 优先系统中文字体，主要使用 400 / 600 | Windows 环境下保持清楚、稳定 |
| 对话宽度 | 常规正文最大宽约 760px；表格和对照视图可使用更宽容器 | 避免宽屏一行过长 |
| 导航与文件区 | 导航约 220～240px；文件区按可用宽度安排并支持收起 | 优先保障正文和原文阅读 |
| 控件 | 常规高度约 40px，次要紧凑操作约 32～36px | 建立一致且容易点击的操作尺度 |
| 间距 | 延续 4px 基础间距体系，常用 8 / 12 / 16 / 20 / 24 / 32 / 48px | 形成自然分组和一致节奏 |
| 边框、圆角、阴影 | 轻边框、少阴影，主要容器约 12px 圆角；通过留白区分内容 | 减少卡片套卡片的拥挤感 |

颜色、尺寸、字号和状态都通过统一令牌管理。即使最终使用 Tailwind，也不能在业务组件中各自建立一套品牌值。

以 WCAG 2.2 的相关准则作为校验依据：普通文字对比度至少 4.5:1，大字号至少 3:1；同时检查键盘操作、可见焦点、标签和错误关联。采用这些检查不等于已取得整站 WCAG 符合性结论。[W3C 文字对比度准则](https://www.w3.org/TR/WCAG22/#contrast-minimum)

首期仍按当前桌面范围规划；草图在窄窗口可显示不代表手机适配已纳入需求。字号调整、紧凑密度和深色模式分别定范围，不能只完成局部样式就宣称全系统支持。

## 八、业务与安全不变量

1. 任何模型调用仍经服务端网关执行调用上限、出口复检、发送和审计；页面或组件不直接访问模型供应商。
2. 外发只有现行契约允许的脱敏文本与引用；不发原文件、图片、真实文件名或脱敏映射。`local_only` 绝不调用模型。
3. 外发预览以服务端返回为准；页面不拼接、重算或替换真实发送正文。
4. 所有任务、会话、知识库管理及设置接口继续按 owner 与角色校验；菜单隐藏不能代替服务端权限判断。
5. 敏感信息的加密、还原、保留期、删除及审计继续使用现有服务端契约。
6. 原文、模型文字和引用继续通过安全文本节点展示，不引入 `v-html` 或库内未经审查的 HTML / Markdown 渲染路径。
7. 布局偏好与业务状态分开管理；草稿可在本次页面运行内保留，不随偏好写入浏览器持久存储。
8. 不向浏览器日志、URL、埋点或远程资源请求泄露原文、文件名、消息、金额及密钥。
9. 金额和比价继续由后端 Decimal 计算；前端只展示既有接口结果。
10. 固定提示、安全声明、错误码及接口形状保持契约；减少点击不能成为省略确认的理由。

## 九、组件库与技术路线

### 9.1 方案比较

| 路线 | 收益 | 成本与限制 | 建议定位 |
|---|---|---|---|
| 保留 Element Plus，重构布局与设计令牌 | 复用现有表单、表格、弹窗和验证链；现行规范兼容程度最高 | 需要认真覆盖默认外观并拆分业务组件，视觉提升依赖设计落地 | 可独立完成全部产品目标的稳妥路线，也是回退方案 |
| Nuxt UI 4＋业务工作区组件 | 统一基础控件、布局和交互原语，有利于构建会话与工作区视觉 | 引入 Tailwind / Reka 体系；表单、表格、焦点、图标和样式需迁移验证 | 优先做隔离验证，验证通过后再决定是否整体采用 |
| shadcn-vue＋Reka UI 等原语 | 组件代码可直接定制，适合高度定制的设计体系 | 需要承担更多组件代码、组合规则与后续维护 | 当 Nuxt UI 限制确实妨碍设计、且团队接受维护成本时再评估 |
| 迁移整个应用到 Nuxt 框架 | 可获得 Nuxt 自身的应用组织能力 | 本轮没有 SSR 等明确需求，扩大改造面 | 当前规划没有采用理由 |

Nuxt UI 官方仓库明确支持普通 Vue 应用的 Vite 插件接入，技术上不要求把本项目改成 Nuxt 应用；官方同时说明其基于 Reka UI 和 Tailwind。可接入不等于值得迁移。[Nuxt UI 官方仓库与 Vue 接入说明](https://github.com/nuxt/ui#vue)

shadcn-vue 官方将其定位为可分发、可定制的组件代码体系；将其列为备选时，需要同时接受维护这些组件的责任。[shadcn-vue 官方介绍](https://www.shadcn-vue.com/docs/introduction)

### 9.2 建议选型程序

先批准目标体验，再用同一组业务场景验证候选库。不能仅凭组件展示页、星数或一张聊天截图决定全量替换。

验证至少包括：

- 中文长文本会话、流式增量展示、引用、复制、只读与失败状态。
- 复杂设置表单、字段校验、表格筛选分页、权限可见性与危险操作确认。
- 原文与外发文本对照、手动脱敏、审核问题与 PDF / 文本定位。
- 弹层嵌套、键盘焦点、滚动容器和窄桌面窗口。
- Tailwind 基础样式与 Element Plus、PDF 预览及现有令牌的冲突。
- 类型检查、构建、依赖许可、产物体积和加载行为；以现有前端为对照，正式阈值由 Opus 写入任务卡。
- 生产构建不依赖公网字体、CDN 图标、远程组件资源或运行时外部请求；相关资源在获准后本地打包。
- 候选聊天组件不得引入自动外发、SDK 直连模型、HTML 渲染或隐式持久化。

验证通过后锁定精确版本与最终迁移范围。若收益不足或关键场景不通过，采用 Element Plus 路线完成同一套产品设计，不让组件库选型阻塞 UI 改进。

### 9.3 迁移原则

- 保留 Vue、TypeScript、Vite、Pinia、路由和后端接口；只在批准范围内替换控件与样式。
- 临时共存必须有组件边界和移除计划，同一个业务区不长期混用两套表单、消息反馈与视觉语义。
- 先抽取业务组件，再更换其基础控件，便于隔离风险。
- 未经批准，不修改依赖、不下载新库或模型、不运行真实模型试用。

不默认给所有业务页加永久缓存；保留布局切换状态与跨任务、跨账号缓存业务内容是不同问题。退出及会话切换仍清理相应状态，遵守权限与当前生命周期约定。

## 十二、工作量与风险判断

### 12.1 双布局的增量成本

保存一个有效布局枚举的工作量很小。较多成本来自会话列表在两种位置的组合、正文与原文宽度、状态与滚动保留，以及未来每次布局相关改动的复核。

以“本轮完整 UI 改造只做一种布局”为比较基线，严格共享业务页面时，讨论阶段可以先按**额外增加约 20%～30% 的前端布局与回归工时**预留。这是未拆任务前的粗估，不是实测、排期或总项目预算；不包含组件库迁移、新增业务、跨设备偏好或手机适配。

若两种布局发展出不同页面、流程或组件，以上估计失效。新增页面时也必须检查两种布局，长期维护成本不能只按一个偏好开关计算。

### 12.2 主要风险及处理

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 候选库的默认体验不适合本项目 | 迁移后仍需大量改写，收益不足 | P2 用真实业务形态验证，保留 Element Plus 路线 |
| 三栏内容再叠全局侧栏 | 1280px / 1366px 下正文和原文过窄 | 会话导航整合、文件按需展开、提供侧栏收起；以实测宽度定稿 |
| 切换布局触发卸载 | 草稿、选择、轮询或生成状态丢失 | 保持页面实例稳定，业务状态与呈现位置分离 |
| 两套 CSS 基础样式冲突 | 表单、PDF、弹层和焦点出现异常 | 明确共存范围、样式边界和最终移除安排 |
| 为追求简洁隐藏关键条件 | 用户不理解不能发送，或误认为文件已确认 | 关键状态与处理入口常驻，保留发送前确认 |
| 只验证正常状态或单个角色 | 空白、失败、只读、权限页面出现遗漏 | 按状态、角色、布局、窗口组成验收清单 |
| 改造与现有 V2 审核、发布交叉 | 审核基线失效，回归与回退困难 | P0 先定版本安排，保留清楚的提交边界 |

## 十五、后续架构议题：本地工作目录与临时处理

本节只保存讨论，**不进入本次 UI 实施、依赖安装、数据库迁移或存储清理范围**。

讨论过的可行方向是：网页选择本地工作目录 → 文件送到服务器短时处理 → 结果与可恢复任务包保存本地 → 完成校验后释放允许清理的临时数据。支持的浏览器可使用目录授权；其他浏览器保留上传、下载路径。

后续单独设计时，至少需要明确：

1. 原件、解析正文、脱敏映射、会话、结果、引用、向量、审计与备份分别放在哪里，哪些仍有服务端保留要求。
2. 本地任务包怎样加密、重新打开、重新校验并恢复追问；仅保存一份报告不足以恢复完整会话。
3. 本地写入成功与完整性校验、用户取消、保存失败、断网、关页、超时和服务端重启的恢复协议。
4. 服务器内存、受限临时空间、容量上限、并发、交换空间和异常清理；不能把 `tmpfs` 等同于绝不落盘。
5. 备份、电脑更换、丢失恢复、跨电脑使用、企业留存及集中审计之间的取舍。
6. 服务端网关、权限、出口复检和必要审计继续保留；客户端或网页提交的数据重新进入服务端安全边界。

目前没有服务器存储占比实测，不给出节省比例；不承诺纯内存处理、自动彻底擦除、立即删除现有持久数据或桌面客户端交付。
