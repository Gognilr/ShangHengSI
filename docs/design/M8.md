## 二、脚本通用约定（lib.sh，M8-01 建立）

* bash，`#!/usr/bin/env bash` + `set -Eeuo pipefail`；`ROOT="$(cd "$(dirname "$0")/.." && pwd)"`，在仓库里是 `deploy/`，在发布包里是包根目录，两处都能直接运行。
* 公共函数（名字固定，M8-02 只追加，不改已有函数）：

```bash
die "消息"                 # 输出“错误：消息”到 stderr，exit 1
info "消息"                # 输出到 stdout
require_root               # 非 root 时 die “请用 sudo 运行”
require_cmd docker sha256sum ...
compose ...                # docker compose --project-directory "$ROOT" -f "$ROOT/docker-compose.yml" "$@"
env_get KEY                # 从 $ROOT/.env 读取一个值（不 source .env，避免执行其中内容）
confirm "提示" "要输入的文字"   # 要求原样输入指定文字；设置了 ASSUME_YES=1 时跳过
wait_healthy app 180       # 等某服务 healthy，超时 die
require_on_data_disk PATH  # PATH 所在文件系统是根分区时 die（Q-131）
```

* 所有脚本：输出中文；**不得输出**密码、主密钥、备份密码、数据库连接串、API 密钥（create-admin 打印的初始密码是 SPEC 20.5 明确要求的唯一例外）；不使用 `set -x`；临时目录权限 700 并在 `trap ... EXIT` 中删除。
* 参数统一：`--yes` 设置 ASSUME_YES=1（只用于演练和自动化，运维说明里不推荐）；`-h/--help` 打印用法。
* 返回码：成功 0；任何失败非 0，并说明哪一步失败、系统处于什么状态、下一步怎么办。
* 运行前统一检查（Q-131）：`/data` 已挂载（`findmnt /data`），安装目录、备份目录、`docker info` 的 Docker Root Dir、containerd 的 root（`/etc/containerd/config.toml`，缺省 `/var/lib/containerd`）都不在根分区上；不满足时 die 并指向运维说明的对应章节。

### 2.1 文件属主与权限（Q-120）

* 容器内 appuser 固定 uid=10001、gid=10001。宿主上 install.sh 创建同 gid 的组 `aireview`（gid 10001）；需要用 SFTP 拉取备份的运维账号加入该组。
* 备份目录：属主 10001:10001，权限 2750（setgid，新文件继承组）。.tmp、.bak、.sha256 以 0640 创建（M7-01 原为 0600，M8-01 改）。备份本身已用备份密码加密，组内只读不降低保密性。
* `secrets/`：属主 10001:10001，权限 700；`master_key`、`backup_password` 权限 600。`.env` 属主 root，权限 600。

## 三、恢复（M8-01，Opus）

### 3.1 命令

```text
sudo ./scripts/restore.sh [--yes] /data/apps/aireview/backup/aireview_20261022_0200.bak
```

### 3.2 流程（restore.sh）

1. **前置检查**（任何一项不满足都 die，系统未做任何改动）：root；第二节的统一检查；文件名匹配 `^aireview_\d{8}_\d{4}\.bak$` 且位于 `BACKUP_HOST_DIR` 下；同名 `.sha256` 存在；db 服务在运行；备份目录所在盘剩余空间 ≥ 备份文件大小 × 2.2（解密后的 tar + 解出的原件与 db.dump）。
2. **校验 SHA-256**：在备份目录执行 `sha256sum -c 文件名.sha256`。
3. **解密**：创建 `$BACKUP_HOST_DIR/.restore/`（700，属主 10001），`compose run --rm --no-deps -T worker python -m app.cli decrypt-backup --in /backup/{名} --out /backup/.restore/backup.tar`（直接调用 M7-01 的命令，不重新实现解密）。`trap` 在任何情况下退出时删除 `.restore/`。
4. **校验并解包**：`compose run --rm --no-deps -T worker python -m app.cli restore-prepare --tar /backup/.restore/backup.tar --work /backup/.restore`（3.3），输出一行 JSON 摘要。
5. **确认**：打印摘要（备份时间、系统版本、任务数、原件数），提醒“恢复会用备份覆盖当前全部数据，建议先在 PVE 中为虚拟机创建快照”，`confirm` 要求输入 `确认恢复`。
6. `compose stop app worker`（db、web 保持运行）。
7. **恢复数据库**：`compose run --rm --no-deps -T worker python -m app.cli restore-db --dump /backup/.restore/db.dump`（3.4）。
8. **替换原件**：`compose run --rm --no-deps -T worker python -m app.cli restore-files`（3.5）。
9. `compose up -d app worker`，`wait_healthy app 300`（app 启动时自动 `alembic upgrade head`，备份来自旧版本时随之升级）。
10. **核对**：`compose exec -T app python -m app.cli restore-files --verify --expect-files M`（M 为第 4 步实际解出的原件数）；通过后执行 `restore-db --drop-old`、`restore-files --drop-old` 清理旧库和旧原件。
11. 打印“恢复完成；所有用户需要重新登录”。

* 第 6 步之后任何一步失败：脚本**不自动回滚**，停止并打印当前状态和处理办法（旧数据库名、旧原件目录、恢复 PVE 快照），由运维说明“恢复失败怎么办”一节给出手动回退命令（Q-117）。
* 第 1～5 步失败，系统不受影响；app、worker 未停止。

### 3.3 restore-prepare（app/backup/restore.py：`prepare(tar_path, work_dir) -> dict`）

依次检查，任一不满足抛 `RestoreError`（中文消息，不含文件内容），命令返回非 0（Q-119）：

* tar 成员只允许：`manifest.json`、`db.dump`、`files/<32 位小写十六进制>`，且都是普通文件；出现其他名字、目录穿越（`..`、绝对路径）、链接、设备文件，或同名成员重复，一律拒绝。manifest 必须是第一个成员，`db.dump` 必须存在。
* manifest：`format == 1`；`db_dump == "db.dump"`；实际 files/ 成员数**不大于** `file_count`（Q-114 ①：备份过程中被删除的原件会跳过，file\_count 可能比实际多；恢复不依赖该数字相等）。
* 数据库迁移版本：`pg_restore --data-only --table=alembic_version -f - db.dump` 取出版本号，必须是当前代码 Alembic 脚本目录中已知的版本（`ScriptDirectory`），否则“备份来自更新的系统版本，请先升级到不低于备份时的版本再恢复”。
* 主密钥：至少有一个原件时，用当前主密钥解密第一个原件（`crypto.decrypt_file`，只解密、不保存结果）；失败时“当前主密钥与备份不匹配，恢复需要备份时使用的主密钥”。没有原件时跳过并在摘要中写 `key_checked: false`。
* 通过后：`db.dump` 解到 `work_dir/db.dump`（600）；原件解到 `FILES_DIR/.restore-new/`（目录 700），逐个写入、fsync。`FILES_DIR/.restore-new/` 已存在时先删除（上次中断的残留）。
* 输出 `{"created_at", "app_version", "task_count", "file_count", "files_extracted", "revision", "key_checked"}`（task\_count、file\_count 只作展示）。

### 3.4 restore-db（`restore_db(dump_path, *, target_db: str | None = None)`、`drop_old()`）

恢复到新库再改名（Q-117），保证要么完全换成备份的数据、要么当前库原样不动：

1. 从 DATABASE\_URL 取库名 D（默认 aireview）与连接参数（复用 service.py 的 `_pg_env` 做法：用环境变量传，不放命令行）。连接维护库 `postgres`。
2. `DROP DATABASE IF EXISTS {D}_restore`；`CREATE DATABASE {D}_restore`。
3. `pg_restore --no-owner --no-privileges --exit-on-error --single-transaction -d {D}_restore db.dump`；失败时删除 `{D}_restore`，抛 RestoreError（“数据库恢复失败（返回码 n）”，不带 stderr）。
4. 在 `{D}_restore` 中一个事务内做恢复后的清理（Q-118）：删除全部 sessions；`jobs` 中 running 的置 failed（`last_error="RESTORED"`）；`backup_records` 中 running 的置 failed（`error_message` 用已有的 BACKUP\_INTERRUPTED\_MSG）。写一条审计 `restore_run`（target\_type 为空，detail `{"revision", "files"}`）。
5. 终止其他连到 D 的会话（`pg_terminate_backend`，此时 app、worker 已停止），`ALTER DATABASE {D} RENAME TO {D}_pre_restore`（已存在同名旧库时 die，提示先处理上次恢复留下的旧库），`ALTER DATABASE {D}_restore RENAME TO {D}`。
6. `--drop-old`：`DROP DATABASE IF EXISTS {D}_pre_restore`。

### 3.5 restore-files（`swap_files()`、`verify(expect_files)`、`drop_old_files()`）

* 交换：建 `FILES_DIR/.restore-old/`（700）；把 FILES\_DIR 下文件名匹配 `^[0-9a-f]{32}$` 的普通文件 `os.replace` 进去；再把 `.restore-new/` 里的文件 `os.replace` 到 FILES\_DIR；删除空的 `.restore-new/`。`.restore-old/` 已存在时拒绝（上次恢复未清理）。不碰不匹配命名的文件。同一文件系统内只做重命名，不复制。
* `--verify`：FILES\_DIR 下匹配命名的文件数 = expect\_files；task\_files 中 original\_deleted\_at 为空的每条记录，其 storage\_key 文件都存在（备份时刚好被删除的任务，其记录也不在 dump 中或已标记删除）。任一不符返回非 0 并打印差异的数量（不打印内容）。
* `--drop-old`：删除 `.restore-old/`。

### 3.6 测试（tests/test\_restore.py；真实测试库 + pg\_dump，用临时 FILES\_DIR、BACKUP\_DIR）

* 用 M7-01 的 `run_backup` 做出一份真实备份并解密成 tar，作为正常样本。
* prepare：正常样本通过且摘要正确；成员名非法、`../x`、绝对路径、符号链接、重复成员、manifest 不在首位、缺 db.dump、实际原件数大于 file\_count、format≠1、未知迁移版本、主密钥不匹配，各自报对应错误，且 `.restore-new/` 不残留；实际原件数小于 file\_count（Q-114 ①）时通过。
* restore\_db（`target_db` 用测试专用的库名，不碰其他测试库）：恢复后数据与备份时一致（备份后新增的任务消失、删除的任务回来）；sessions 为空、running 的 jobs 与 backup\_records 已置 failed、有 restore\_run 审计；pg\_restore 失败时原库不变、`_restore` 库被删除；`_pre_restore` 已存在时拒绝且原库不变；`drop_old` 后旧库不存在。
* swap\_files / verify：交换后文件集合等于备份；不匹配命名的文件保留；`.restore-old/` 已存在时拒绝；verify 能发现缺文件和数量不符。
* 数据库密码、备份密码不出现在日志、异常消息和子进程命令行参数中（检查 `subprocess.run` 的参数）。
* service.py：.bak、.sha256 权限为 0640（改 tests/test\_backup.py 中对应断言）。
* tests/test\_scripts.py（需整仓挂载，与 test\_forbidden\_words 相同）：`bash -n deploy/scripts/*.sh`。
* **服务器实跑**：用 `git archive HEAD` 把代码同步到服务器的 /data/apps/aireview（保留服务器上的 .env、secrets/、backup/ 和 Caddyfile 中的 default\_sni），重建镜像并重启现有测试部署；然后执行一次 restore.sh（用当天的备份），并演练一次主密钥不匹配（用临时的错误主密钥，演练后还原），确认失败时系统未被改动。结果写入完成报告。

## 四、安装、升级、手动备份（M8-02）

### 4.1 install.sh

```text
sudo ./scripts/install.sh [--site <服务器IP或内网域名>] [--admin admin] [--backup-dir /data/apps/aireview/backup] [--yes]
```

`--site` 缺省时取本机第一个非回环 IPv4 地址；`--backup-dir` 缺省为 `$ROOT/backup`。

1. 前置检查：root；`docker`、`docker compose` 可用；第二节的统一检查；发布包完整（`sha256sum -c SHA256SUMS`，在仓库里运行时跳过此项）；`.env` 或 `secrets/master_key` 已存在时 die“系统已安装，升级请用 upgrade.sh”；80、443 未被其他进程占用。
2. 组：`aireview`（gid 10001）不存在则创建；gid 10001 已被别的组占用时 die。备份目录不存在则创建，`chown 10001:10001`、`chmod 2750`。
3. `docker load -i images/aireview-images-*.tar`，确认 `aireview-backend:{VERSION}`、`aireview-web:{VERSION}`、`postgres:16.15` 都在。
4. `.env`：由 `.env.example` 生成（umask 077），写入 `POSTGRES_PASSWORD`（随机 32 位十六进制）、`APP_VERSION`（VERSION 文件）、`SITE_ADDRESS`、`HTTP_PORT=80`、`HTTPS_PORT=443`、`BACKUP_HOST_DIR`，其余用示例中的默认值。
5. 密钥（Q-124）：`secrets/`（700，属主 10001）；主密钥用 `docker run --rm -v secrets:/out aireview-backend:{VERSION} python -m app.cli gen-key --out /out/master_key`；备份密码用 `docker run ... python -c` 生成 32 个字符的随机串写入 `secrets/backup_password`（600，属主 10001）。**两者都不在屏幕上显示**；脚本提示“请把 secrets/master_key 和 secrets/backup_password 拷到离线介质交专人保管，丢失任一个都无法恢复备份”。
6. `compose up -d`，`wait_healthy app 300`，确认 worker 在运行；`curl -k https://{site}/` 返回 200。
7. `compose exec -T app python -m app.cli create-admin --username {--admin}`（初始密码只显示这一次）。
8. 打印：访问地址、首次登录改密码 → 设置 - 模型填写接口与密钥（推荐值见运维说明）→ 设置 - 数据确认备份时间并点一次“立即备份” → 配置异地拉取；以及启动、停止、查看状态的命令。

### 4.2 upgrade.sh（在新发布包目录中运行）

```text
sudo ./scripts/upgrade.sh [--target /data/apps/aireview] [--skip-backup] [--yes]
```

1. 前置检查：root；第二节的统一检查；新包 `sha256sum -c SHA256SUMS`；目标目录有 `.env`、`secrets/master_key`；新版本号不同于目标 `.env` 的 APP\_VERSION。
2. `confirm`：“升级前请先在 PVE 中为虚拟机创建快照。已创建请输入：已创建快照”。
3. 除非 `--skip-backup`：在目标目录执行 `backup_now.sh --wait`，失败则 die（不继续升级）。
4. `docker load` 新镜像；把新包的 `docker-compose.yml`、`scripts/`、`docs/`、`VERSION`、`.env.example` 复制到目标目录；`Caddyfile` 与目标现有的不同时不覆盖，另存为 `Caddyfile.new` 并提示人工比较（公司证书配置可能写在里面）。
5. 修改目标 `.env` 的 `APP_VERSION`（只改这一行）；`compose up -d`（自动执行迁移）；`wait_healthy app 300`。
6. 失败时：不自动回退，提示“用 PVE 快照恢复到升级前”（Q-126）。旧镜像不删除。

新包解压到临时目录（如 `/data/apps/aireview-upgrade-{版本}`）后运行；成功后可删除该临时目录。

### 4.3 backup\_now.sh 与 backup-now 命令

```text
sudo ./scripts/backup_now.sh [--wait]
python -m app.cli backup-now [--wait] [--timeout 3600]
```

* `backup-now`：调用 M7-01 的 `enqueue_backup(db, trigger="manual", user_id=None)`；返回 None 时输出“已有备份正在进行”并返回 2。`--wait` 时每 3 秒查一次本次之后最新的 backup\_records，直到不再是 running：success 打印文件名和大小、返回 0；failed 打印 error\_message、返回 1；超时返回 3。审计 backup\_run 的 user\_id 为空（与定时备份相同）。
* `backup_now.sh`：`compose exec -T worker python -m app.cli backup-now "$@"`。

### 4.4 compose 与配置（M8-02）

* 每个服务加日志轮转（SPEC 21）：`x-logging: &logging {driver: json-file, options: {max-size: "50m", max-file: "5"}}`，四个服务都 `logging: *logging`（只作用于本系统的容器，不改 daemon.json）。
* 只有 web 发布端口（80、443，供局域网访问）；db、app、worker 不发布端口（已是如此，保持）。
* web 增加只读挂载 `./certs:/etc/caddy/certs:ro`。
* Caddyfile 增加全局块 `{ default_sni {$SITE_ADDRESS:localhost} }`（Q-130：用 IP 访问时浏览器不发送 SNI，没有这一行 HTTPS 握手失败）；注释写明公司证书放在 `certs/server.crt`、`certs/server.key` 时的写法（Caddy 默认会把 80 跳转到 443，无需另配）。
* `build:` 段前后加注释标记 `# build-begin`、`# build-end`（各占一行），供 build\_release.sh 生成不含 build 段的发布用 compose（Q-122）。开发时的 `docker compose up -d --build` 不受影响。
* `.env.example`：生产值 `BACKUP_HOST_DIR=/data/apps/aireview/backup`、`HTTP_PORT=80`、`HTTPS_PORT=443`，说明 install.sh 会自动生成 `.env`。
