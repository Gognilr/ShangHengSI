## 三、不带币种的金额（R4-02）

**问题**：9.3 第 5 步只认带币种符号或“元”的金额和报价表列中的数字。“合同总价：125000”“预计采购额约 350万”“合同金额（元）：86,400.00”和左侧单元格是“合同总价（元）”的表格数字都原样外发，出口复检也拦不住（不在对照表、不带币种）。

**文件范围**：`backend/app/redaction/detect.py`、`backend/app/redaction/tables.py`、`backend/app/redaction/engine.py`（只在第 5 步加一处调用）、`backend/app/chat/service.py`（只在第 4 步加一处调用）、`backend/tests/test_detect*.py`、`backend/tests/test_tables*.py`（如有，没有则放进 test_detect）、`backend/tests/test_recheck.py`（只追加 3.5 第 11 条）、`backend/tests/fixtures/redaction_golden/bare_amounts.yaml`（只按 3.5 移动条目）。

**注意**：出口复检（recheck.py）的重扫直接调用 `detect.find_amounts(text)`，并把每个命中都当作拦截原因。因此本节规则**不得写进 `find_amounts`**，而是新建 `detect.find_bare_amounts(text) -> list[Hit]`，由 engine 第 5 步（与 `find_amounts` 的结果一起参与取舍，`find_amounts` 的命中优先）和 chat `_redact` 第 4 步调用；recheck 不调用它（理由见 3.6）。

### 3.1 金额标签

* 中文：合同总价、合同总额、合同金额、合同价款、合同价、总价款、总价、总金额、总额、金额、价款、货款、报价、单价、含税单价、不含税单价、含税价、不含税价、合计、总计、小计、预付款、首付款、定金、订金、进度款、尾款、质保金、保证金、履约保证金、违约金、服务费、费用、预算、投资额、采购额、销售额、税额。
* 英文（不区分大小写）：Total Amount、Total Price、Total Value、Contract Value、Contract Price、Contract Amount、Amount、Total、Subtotal、Unit Price、Price、Deposit、Advance Payment、Down Payment、Balance、Retention。
* 含“单价、Unit Price、Price”的标签归为单价（PRICE），其余为金额（AMOUNT）。

### 3.2 正文规则（新函数 `detect.find_bare_amounts`，engine 与 chat 共用，recheck 不用）

匹配 `标签` + 可选单位说明 `（元）（人民币）（万元）(RMB)(CNY)(USD)` 等（括号内只能是币种或“元 / 万元 / 亿元”）+ 可选 `为、是、：、:`、空白 + 可选 `约、共计、合计、计、不超过、不低于` + 可选填空括号 + **数字** + 可选紧跟的 `万` 或 `亿`：

1. 数字（及“万 / 亿”、填空右括号）之后**紧挨着**的字符不能是 `%`、`‰`、数字、字母或汉字；隔空白之后紧接的是计量或期限单位（天、日、个月、月、年、周、小时、台、套、件、个、只、项、条、次、批、吨、公斤、千克、克、米、平方米、立方米、人、家、份、页）或字母时也不算。“合同总价：125000 是否合理”算，“合计：12 台”“预付款 30%”不算。“元、万元、美元”等已由现有币种规则处理，本规则不重复命中（同一位置只出一个 Hit）。
2. 数字须满足其一：整数部分至少 3 位；含千分位；有两位小数；后接“万 / 亿”。（“合计：5”这类计数不替换。）
3. 标签前紧挨“第”或数字的不算；标签与数字之间不得跨行。
4. 只替换数字部分；“万 / 亿”与单位说明保留在原文中（与“币种保留”一致），数值换算时乘 10000 / 100000000。
5. 币种：单位说明里有币种的取该币种（“元、万元、人民币、RMB、CNY”为 CNY），否则 `None`；代号 key 按现有 `_amount_key`（同类别、同币种、同数值同一代号）。
6. 金额比例（9.6）沿用现状：没有币种的金额不作为合同总价、也不加比例。

### 3.3 表格中左侧单元格是金额标签

在 `tables.table_hints` 中增加：同一表格同一行，某单元格是纯数字（可带千分位、小数，或后接“万”）且**紧邻左侧单元格**（列号小 1）的文字去掉空白、末尾冒号和单位说明括号后**等于** 3.1 中的某个标签时，该单元格提示为 PRICE 或 AMOUNT。已有表头列提示的单元格不覆盖。XLSX 的列号按字母序比较（沿用 `_col_order`）。

### 3.4 不处理的情形（保持原样）

百分比、日期、期限（“30 天”）、件数（“12 台”）、条款号（“第 3 条”）、HS 编码、规格指标；没有金额标签的纯数字（“交货期（天） | 60”）。

### 3.6 为什么不改出口复检

出口复检第 2 条按 9.3 的正则重扫外发文本（实现上是对整段请求调用 `detect.find_amounts`，每个命中都拦截）。新规则对文件正文、补充说明、追问三处已经在识别阶段生效，重扫新增的只有提示词、公司说明和历史对话中的模型回复；模型回复里出现“总价约 50000”时会让该任务之后的追问永远被拦截。所以新规则放在单独的 `find_bare_amounts` 中，recheck 不调用，记为 Q-152 ③；3.5 第 11、12 条锁定这一点。

## 四、本次补充说明（R4-03）

**问题**：补充说明（≤ 500 字）作为编号 NOTE 的审核要求**原文**拼进请求，只做 document 标签转义；出口复检只拦对照表中的真实值和固定格式，写了文件里没有的公司名、人名或无币种金额会直接外发。原文还明文存在 tasks.user_note、review_runs.user_note、requirement_results.req_text 三处。

**文件范围**：`backend/app/db/alembic/versions/0005_user_note_enc.py`（新）、`backend/app/db/models.py`、`backend/app/redaction/engine.py`、`backend/app/redaction/router.py`、`backend/app/tasks/router.py`、`backend/app/tasks/service.py`、`backend/app/tasks/schemas.py`、`backend/app/review/service.py`、`backend/app/review/job.py`、`backend/app/export/report_docx.py`、`backend/app/backup/retention.py`、对应测试（`test_migrations.py` 只改 tasks / review_runs 的期望列，新增 `tests/test_user_note_redaction.py`；既有测试只按 4.7 修订：`tests/test_runs_api.py`、`tests/review_support.py`、`tests/test_tasks_api.py`、`tests/test_review_job.py`）。

### 4.1 做法：补充说明作为一个“伪节点”参加脱敏

* engine `_run` 构建节点列表时，若任务有补充说明，在**最后**追加 `NodeIn("NOTE", 补充说明原文, None)`。它与正文节点一起走第 1～7 步、数量脱敏、疑似遗漏和用户词条，代号分配排在全部正文之后（文件中的代号字母和序号不受影响）。
* `NOTE` 节点**不进**外发正文（`outbound_text` / `build_outbound` 只用 doc_nodes），也不参与本地校验、报价明细表、合同总价（总价只在 `main_prefix` 文件中找）。
* 脱敏后的文字写入 `tasks.user_note_redacted`；审核时 NOTE 要求的文字、`review_runs.user_note` 快照、`requirement_results.req_text`（req_source=note）一律用代号形式。
* 补充说明里出现的公司名会和正文一样成为签约方（角色“其他”），出现在第二步签约方列表和【主体说明】中；这是预期行为。
* `redaction_items`、`redaction_suspects` 中 loc=`NOTE` 的行照常写入；第二步的“替换”“忽略”“手动补充”对 NOTE 同样有效，疑似遗漏未处理时照常不能确认发送（SUSPECTS_PENDING）。

### 4.2 存储与迁移 0005

| tasks | 删除 `user_note`；新增 `user_note_enc bytea`（主密钥加密的原文，可空）、`user_note_redacted text`（代号形式，可空） |
| review_runs | `user_note` 改为 `text`，语义改为代号形式（可空） |

迁移的数据处理（Q-154）：V1.0 尚无正式数据（M8-05 全新安装），已有的补充说明只来自开发与测试环境。迁移**不解密、不加密**：tasks 的旧补充说明丢弃（两列置空），review_runs.user_note 置空，req_source=note 的 req_text 改为“（本次补充说明，升级时已清除）”。降级：恢复 `tasks.user_note varchar(500)`（置空）、review_runs.user_note 截断为 500 字，删除新列。`test_migrations.py` 的列期望同步修改。

### 4.3 写入与修改

* `POST /tasks`：补充说明加密写入 `user_note_enc`，不再明文保存；解析任务中的脱敏（`redact_task`）一并生成 `user_note_redacted`。
* `PATCH /tasks/{id}`（重新审核）改了补充说明时：**先删除本任务 loc=NOTE 的 `redaction_items`（detected_by=user）和 `redaction_suspects`**，再加密写入新原文并重算。原因：这些行按字符位置保存，补充说明改动后位置对不上，旧的“忽略”可能套到新文字上而放行敏感信息，旧的手动词条可能截出错误的文字。补充说明未改时不删。
* 补充说明清空时两列都置空，NOTE 节点不再出现。

## 五、追问的疑似遗漏检查（R4-04，后端）

**问题**：追问在服务端脱敏，但只有脱敏结果与原文不同时才弹窗；什么都没识别出来时（叙述中的人名、没有后缀的字号）用户收不到任何提示。

**文件范围**：`backend/app/chat/service.py`、`backend/app/chat/router.py`、`backend/tests/test_chat.py`（只追加，另按 5.3 修订一处）。

### 5.1 规则

* `_redact` 完成替换后，在**未被替换的文字**上调用 `suspects.find_suspects(text, occupied)`（与第二步同一函数），得到本条问题的疑似遗漏 `[(start, end, reason)]`，偏移量相对 `message.strip()`。
* `POST /tasks/{id}/chat/preview` 响应增加 `suspects: [{start, end, text, reason}]`。
* `POST /tasks/{id}/chat` 请求增加 `decisions: [{start, end, decision: "replace" | "keep", category?: "ORG" | "PERSON" | "CUSTOM"}]`（可省略，默认空）。服务端重新计算疑似遗漏：
  * 每一条都必须有起止位置完全相同的决定，否则 409 `CHAT_SUSPECTS_PENDING`（“问题中有尚未确认的疑似敏感信息”），不调用模型、不写对话；
  * `replace` 必须带类别，否则 422；按 `code_for(该文字, 类别)` 分配追问代号并替换；
  * `keep` 原样发送；
  * 与任何疑似遗漏都不对应的决定忽略。
* 逐条决定只对本条问题生效，不写入已记住的名称和本任务词条。
* 其余流程（对照表写入、网关、出口复检、还原、不自动重试）不变。

### 5.2 测试用例

| # | 输入 | 期望 |
|-|-|-|
| 1 | preview `"Meridian Fictive Inspection 的检验报告能用吗？"` | `changed=false`，`suspects` 一条覆盖 “Meridian Fictive Inspection” |
| 2 | 同上直接 send，不带 decisions | 409 CHAT_SUSPECTS_PENDING；网关调用次数 0；chat_messages 无新增 |
| 3 | 同上带 `replace / ORG` | 请求中该文字为追问代号，回复还原后显示原文 |
| 4 | 同上带 `keep` | 原样发送（经出口复检） |
| 5 | `replace` 不带类别 | 422 |
| 6 | 没有疑似遗漏的问题，不带 decisions | 与现在相同，正常发送 |
| 7 | 决定的起止位置与疑似遗漏不一致 | 视为缺少决定，409 |
| 8 | 日志安全 | 日志不含问题原文 |
