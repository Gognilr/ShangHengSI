# R2 旧格式支持（DOC、XLS、WPS、ET、RTF）

来源：docs/business\_review.md B-15；产品负责人决定见 open\_questions Q-136（2026-10-22）。本轮细化中的取舍记入 Q-143，需要用户提供的样本见 Q-144。

思路：旧格式文件在独立、断网的 **converter** 容器中由 LibreOffice 转为 .docx / .xlsx，转换结果交回 worker 后走现有解析、本地校验与脱敏，解析器、脱敏和审核逻辑不因格式而分叉。

## 〇、R2-00 实测结论（2026-10-23，本机 Docker）

用临时镜像 python:3.12.15-slim-trixie + Debian 软件包 libreoffice-writer-nogui、libreoffice-calc-nogui（4:25.2.3-2+deb13u8，LibreOffice 25.2.3）验证，均只用虚构样本：

| 项目 | 结果 |
|-|-|
| 运行条件 | `--network none`、非 root（uid 10002 / gid 10001）、只读根文件系统、`--cap-drop ALL`、no-new-privileges、只有 /tmp 可写（tmpfs）时转换正常 |
| 速度 | 每个文件约 0.4–0.6 秒（每次新起 soffice 进程、新建配置目录） |
| 体积 | LibreOffice 层约 436 MB（/usr/lib/libreoffice 232 MB）；基础层与 backend 镜像共用（同一 python 基础镜像），不含 Java、不含 python3-uno |
| 保真度（DOCX→DOC→DOCX、XLSX→XLS→XLSX，再用现有解析器比对节点） | 修订（w:ins / w:del）、页眉页脚、批注、文本框、嵌套表格、隐藏工作表、公式缓存值都保留；XLS 三份节点完全一致；DOC 中有合并单元格的表格列号整体后移一列（位置编号以转换后文件为准，同一表内一致，不影响表头识别） |
| 自动编号 | 本仓库人工构造的编号样本导出为 DOC 时 LibreOffice 本身丢失了个别列表的续号（导出侧问题，读回的 DOCX 与 LibreOffice 自身显示一致）；现有解析器读取 LibreOffice 输出的 DOCX，与 LibreOffice 显示相比只有一处退化列表编号不同（“第1条”与“第2条”）。Word / WPS 保存的真实 DOC 的编号需用样本验证（Q-144） |
| RTF | 正文、表格正常；LibreOffice 自己导出的 RTF 中编号模板里的汉字变成“?”（“?1?”），同样需用 Word / WPS 保存的 RTF 验证 |
| OLE 结构 | DOC 含 WordDocument 流，XLS 含 Workbook 流；RTF 以 `{\rtf` 开头 |
| 共享内存盘 | 以 tmpfs 为后端的命名卷可同时挂入两个容器，文件互相可见，权限按 uid / gid 生效 |

## 一、范围与存储

1. 新增上传格式：doc、wps、rtf（转为 docx 解析）；xls、et（转为 xlsx 解析）。宏文件（docm、xlsm、dotm、xlsb 等）及含宏的旧格式文件仍拒绝。
2. task\_files.ext 存真实扩展名（doc / xls / wps / et / rtf）。迁移 **0004** 放宽 task\_files 的 ext CHECK；models.py 同步。
3. **不保存转换结果**：转换只在解析时做一次，结果在内存中解析后丢弃。原件（加密）照常保存，“下载原件”照旧只对 PDF、图片开放；预览按节点渲染（doc / wps / rtf 同 docx，xls / et 同 xlsx）。
4. 位置编号、节点结构、修订、自动编号、页眉页脚等全部以转换后的 DOCX / XLSX 为准（SPEC 8.2–8.4 不变）。
5. 解析成功的旧格式文件加一条警告（显示在第二步与覆盖说明中，不影响发送）：`已由 {DOC} 格式转换为 {DOCX} 后解析，个别格式（如自动编号、表格列）可能与原文显示不同`。
6. parser\_version 写解析器版本加转换器标记：`docx-1+lo25.2`（varchar(20) 内）。

## 二、上传检查（SPEC 17.6，在 app 中同步执行）

| 格式 | 文件头 | 结构检查（olefile） | 拒绝 |
|-|-|-|-|
| doc、wps | `D0 CF 11 E0 A1 B1 1A E1` | 能按 OLE 打开，含 WordDocument 流 | 含 Macros 存储或任何 VBA 存储（\_VBA\_PROJECT、VBA）→ MACRO\_NOT\_ALLOWED；含 EncryptedPackage / EncryptionInfo（加密的 OOXML）→ FILE\_ENCRYPTED |
| xls、et | 同上 | 含 Workbook 或 Book 流 | 含 \_VBA\_PROJECT\_CUR 或任何 VBA 存储 → MACRO\_NOT\_ALLOWED；加密的 OOXML 同上 |
| rtf | `{\rtf` | — | — |

* 新依赖 **olefile**（BSD，纯 Python，锁定版本 0.47）：只在上传检查中读取目录，不解析流内容；任何异常按 FILE\_CONTENT\_MISMATCH 处理。
* 二进制格式本身的密码保护（Word 的 fEncrypted、Excel 的 FILEPASS）不在上传时判断：LibreOffice 无交互时打不开，按转换失败处理（第四节）。
* 金山 WPS / ET 的 OLE 流名按与 DOC / XLS 相同实现（WPS 2003 起与 Word 97 格式兼容），R2-02 用 Q-144 的真实样本核对，不符时以样本为准调整。
* 前端 ALLOWED\_EXTS、文件选择框 accept、格式提示文字同步；后端错误文字为“不支持的文件格式：…（支持 docx、doc、wps、rtf、pdf、xlsx、xls、et、jpg、png）”。

## 三、converter 容器

### 3.1 镜像

* 目录 `converter/`（仓库根目录下，与 backend、frontend 并列）：Dockerfile、main.py（只用 Python 标准库）、tests/。
* 基础镜像 `python:3.12.15-slim-trixie`（与 backend 相同，共用层）；apt 安装 libreoffice-writer-nogui、libreoffice-calc-nogui，**锁定版本 4:25.2.3-2+deb13u8**，`--no-install-recommends`，不另装字体（转换只取文字，不排版）、不装 Java、不装 python3-uno。版本从镜像源下架时，改用 snapshot.debian.org 的同一版本（Q-143 ④）。
* 用户 `converter`，uid **10002**、gid **10001**（与 appuser 同组，以便通过共享盘交换文件；不同 uid，converter 读不到 app / worker 的其他文件，本来也不挂载）。
* 镜像标签 `aireview-converter:${APP_VERSION}`。

### 3.2 compose 服务（deploy/docker-compose.yml）

```yaml
  converter:
    image: aireview-converter:${APP_VERSION:-dev}
    build:
      context: ../converter
    restart: unless-stopped
    network_mode: none           # 不接任何网络
    read_only: true
    user: "10002:10001"
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    tmpfs:
      - /tmp:size=256m,mode=1777  # LibreOffice 配置目录
    volumes:
      - convert_spool:/spool
    mem_limit: 1536m
    cpus: 2
    pids_limit: 256
    healthcheck:                 # 心跳文件 30 秒内更新过
      test: ["CMD", "python", "/srv/converter/main.py", "--check"]
      interval: 15s
      timeout: 5s
      retries: 3

volumes:
  convert_spool:
    driver: local
    driver_opts:
      type: tmpfs
      device: tmpfs
      o: size=512m,uid=10001,gid=10001,mode=0770
```

* worker 增加卷 `convert_spool:/spool` 与环境变量 `CONVERT_SPOOL_DIR=/spool`；app 不挂载。
* converter 不挂载 files\_data、密钥、备份目录，不连数据库；不设 depends\_on（worker 自己判断转换服务是否可用）。
* docker-compose.mock.yml 不变。

### 3.3 交换协议（/spool）

```text
/spool/in/{id}.{kind}        worker 写入的待转换文件（先写 .part 再改名，原子出现）
/spool/work/{id}/            converter 处理中（只有 converter 写）
/spool/out/{id}.docx|.xlsx   结果（先写 .part 再改名）
/spool/out/{id}.err          失败，内容只有错误代码：TIMEOUT / FAILED / NO_OUTPUT / TOO_LARGE / BAD_OUTPUT
/spool/converter.alive       心跳，每轮循环更新 mtime
```

* `id` 为 32 位小写十六进制（uuid4().hex）；`kind` 只取 doc、xls、rtf（wps 按 doc、et 按 xls 交给 LibreOffice，避免 .wps 被识别为 Microsoft Works 格式；以 Q-144 样本核对）。converter 只处理文件名完全匹配 `^[0-9a-f]{32}\.(doc|xls|rtf)$` 的文件，其他文件忽略并在超时清理时删除。
* converter 循环（每 0.5 秒）：更新心跳 → 取 in/ 中最早的一个文件，改名移入 work/{id}/src.{kind} → 执行
  `soffice -env:UserInstallation=file:///tmp/lo-{id} --headless --norestore --nolockcheck --nodefault --convert-to {filter} --outdir work/{id}/out work/{id}/src.{kind}`，
  filter 为 `docx:"MS Word 2007 XML"` 或 `xlsx:"Calc MS Excel 2007 XML"`；**60 秒**超时时杀掉整个进程组 → 检查输出：存在、≤ 100 MB、以 `PK` 开头，否则写 .err → 删除 work/{id} 与 /tmp/lo-{id}。
* 同一时间只转换一个文件（worker 并发 2 时最多排队 1 个）。
* 清理：in/ 与 out/ 中超过 10 分钟的文件（worker 已超时放弃的）每轮删除。
* 日志只写 id、kind、耗时、结果代码；不写文件内容（converter 里本来没有原文件名）。

### 3.4 worker 侧（app/parsing/legacy.py）

`convert(data: bytes, ext: str) -> bytes`：

1. 心跳文件不存在或超过 30 秒未更新 → ParseError“文件转换服务不可用，请联系管理员”。
2. 写 in/{id}.{kind}.part → 改名；等待 out/{id}.docx|.xlsx 或 .err，最长 **120 秒**（含排队）。
3. 超时：删除仍在 in/ 中的文件，ParseError“旧格式文件转换超时”；.err：ParseError“无法转换该文件（可能已加密或已损坏），请另存为 DOCX / XLSX 后重新上传”。
4. 读出结果后删除；对结果执行与上传时相同的 OOXML 检查（ZIP 合法、条目数、解压总大小 ≤ 200 MB、必需部件、无 vbaProject），不通过按转换失败处理。上传检查中的 OOXML 检查函数移到可共用的位置（R2-02 决定具体模块），两处调用同一函数。
5. 明文只出现在 worker 内存和 tmpfs 共享盘上，用完即删；日志不写文件名。

pipeline.\_parse\_bytes：doc / wps / rtf → convert → parse\_docx；xls / et → convert → parse\_xlsx；加第一节第 5 条的警告，parser\_version 按第一节第 6 条。转换不占 OCR 名额。

本地校验中按扩展名判断 XLSX 的一处（checks/amounts.py 公式警告）改为按“解析为 xlsx”判断（xlsx、xls、et）。

## 四、安全加固要点

* converter 无网络、无密钥、无数据库、无原件卷；只读根文件系统、去掉全部 capability、非 root、限制内存 / CPU / 进程数；LibreOffice 每次用新的配置目录，转换完删除，不保留宏安全设置之外的任何状态。
* 含宏的文件在上传时即拒绝；LibreOffice 无界面转换不运行文档宏（默认宏安全级别），即使漏网也无网络、无数据可接触。
* 转换输出视为不可信输入，按上传检查同样的规则复检后才解析。
* 测试：T-20 的禁止网络导入扫描范围加上 converter/；converter 测试中断言容器内除 lo 外没有网络接口（`/sys/class/net` 只有 lo）。

## 五、样本

* backend/tests/fixtures/legacy/：由 converter 镜像从现有虚构 DOCX / XLSX 样本生成的 .doc、.xls、.rtf（生成脚本 make\_legacy\_fixtures.py 一并提交，在 converter 镜像中运行），以及 converter 转回的 .docx / .xlsx 和 manifest.yaml（期望节点数、条款编号、修订、警告）。backend 测试只用转回的文件和模拟转换（不需要 LibreOffice）；converter 测试用 .doc / .xls / .rtf 实际转换。
* .wps / .et：LibreOffice 不能导出这两种格式。先用 .doc / .xls 改扩展名作为测试样本（金山格式与之兼容）；Q-144 的真实样本到位后补充。
* 含宏样本：用 olefile 无法写入，按 OLE 规范在测试中手工构造带 Macros / \_VBA\_PROJECT\_CUR 存储的最小文件（生成脚本提交）。

## 六、对其他里程碑的影响

## 八、验收（R2-05）

1. Docker 全量测试通过（backend；converter 测试在 converter 镜像中通过）；`npm run build` 通过。
2. compose 全套（真实 converter + 模拟模型）经界面各上传一份 DOC、XLS、WPS、ET、RTF：解析成功、第二步显示转换警告、预览与定位正常、确认发送后外发记录出口复检零命中（A-03）。
3. 含宏的 DOC、XLS 上传即被拒；加密 / 损坏的 DOC 解析失败并提示另存为 DOCX；停掉 converter 后上传 DOC，提示“文件转换服务不可用”，其他格式不受影响。
4. converter 容器内无网络接口（只有 lo），根文件系统只读，进程以 uid 10002 运行。
5. Q-144 的真实样本（Word / WPS 保存）逐个核对：正文、表格、自动编号、修订与原文一致；不一致处列出并交用户决定。
