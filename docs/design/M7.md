## 二、管理接口的通用约定（M7-02～M7-08 都遵守）

* 权限：/admin/\* 全部经 `require_admin`，非管理员 403 FORBIDDEN（已有）。修改类请求照常经 CSRF 校验（总路由已挂）。
* 入参用 Pydantic v2，`extra="forbid"`；校验失败统一 422 VALIDATION\_ERROR（已有的错误处理），需要说清原因的另给专门错误码（各节列出）。字符串先去掉首尾空白再校验长度。
* 分页：`page`（从 1 开始）、`page_size` 固定 20，响应 `{"items", "total", "page", "page_size"}`（19.1）。
* 时间：出参 ISO 8601 UTC；日期筛选参数 `from`、`to` 为 `YYYY-MM-DD`，按 Asia/Shanghai 的整天计算（与审核历史 GET /tasks 相同的做法）。
* **审计**：每个成功的修改在同一事务中写一条审计（`app.audit.service.record`），失败不写。action 与 detail 见下表；detail 只放键名、编号、id、开关值、数量，**不得放**密码、API 密钥（含末 4 位）、名称与敏感词文字、补充要求和公司说明的文字、外发内容。

| 动作 | action | target\_type / target\_id | detail |
|-|-|-|-|
| 新增账号 | user\_create（已有） | user / 用户 id | {"role"} |
| 修改账号显示名、角色、状态 | user\_update | user / 用户 id | {"fields": ["role", "status"], "role", "status"}（只列改动的字段；显示名只记字段名） |
| 重置密码 | user\_update | user / 用户 id | {"fields": ["password"]} |
| 修改模型、脱敏、备份、保留期设置 | setting\_update | setting / 分组名（model、redaction、backup、retention） | {"keys": ["model.name", "model.api_key_enc", …]}（只列值真正变化的键） |
| 公司补充要求增删改、公司说明 | setting\_update | company\_requirement / CO 编号；company\_profile / null | {"op": "create" / "update" / "delete", "version": 新版本号} |
| 自定义敏感词新增、启停、删除；删除已记住的名称 | setting\_update | term / term id | {"op", "kind", "enabled"（启停时）} |
| 立即备份、定时备份完成 | backup\_run | backup / 备份记录 id | {"trigger", "status"} |
| 原件保留期清理 | retention\_run（Q-109，17.7 未列，按“设置与数据变更可追溯”补充） | — | {"tasks": n, "files": n} |

* 日志（标准输出）同样只写 id、键名、数量和错误码。

## 三、备份（M7-01，Opus，`app/backup/`）

### 3.1 备份文件格式（archive.py）

```text
文件 = 文件头 + 若干块
文件头（明文，共 32 字节）：
  magic        8 字节  b"AIRVBAK\x01"（最后 1 字节是格式版本 1）
  scrypt_log_n 1 字节  15（n = 2^15）
  scrypt_r     1 字节  8
  scrypt_p     1 字节  1
  reserved     1 字节  0
  chunk_size   4 字节  大端，1048576（明文每块 1 MiB）
  salt        16 字节  os.urandom(16)
块：
  nonce       12 字节  每块 os.urandom(12)
  length       4 字节  大端，本块密文长度（明文长度 + 16）
  ciphertext   length 字节  AES-256-GCM（含 16 字节标签）
  AAD = 文件头 32 字节 + 块序号（8 字节大端，从 0 开始）+ 末块标志（1 字节，最后一块为 1，其余为 0）
密钥：cryptography 的 Scrypt(salt, length=32, n=2^15, r=8, p=1).derive(备份密码 UTF-8 字节)
```

* 最后一块一定带末块标志（明文可以为空，即文件恰好是 chunk\_size 整数倍时追加一个空的末块）。AAD 绑定块序号和末块标志：调换、删除、截断任何一块都会解密失败。
* 解密时任一条不满足都抛出 `BackupFormatError`（消息只说哪一类错误，不带任何内容）：magic 或版本不对、scrypt 参数不是上面的值（防止被改成极大的 n 耗尽内存）、chunk\_size 不是 1048576、某块 length 大于 chunk\_size + 16、标签校验失败（密码错误或被篡改）、末块之后还有数据、文件在末块之前结束。
* 函数：

```python
MAGIC = b"AIRVBAK\x01"
class BackupFormatError(Exception): ...
class EncryptingWriter:                       # 流式写：write(bytes)、close()；close 时写末块
    def __init__(self, out: BinaryIO, password: bytes): ...
def decrypt_stream(src: BinaryIO, dst: BinaryIO, password: bytes) -> int   # 返回明文字节数
def load_backup_password(path: str) -> bytes  # Q-100
```

* 解密命令（给 M8-01 的 restore.sh 用）：`python -m app.cli decrypt-backup --in X.bak --out X.tar [--password-file PATH]`，不给 `--password-file` 时读 BACKUP\_PASSWORD\_FILE。输出文件用 O\_EXCL 新建、权限 600，已存在时拒绝；解密失败时删除不完整的输出文件并返回非 0。输出与报错都不含密码。

### 3.2 tar 内容

tar（`tarfile.open(fileobj=EncryptingWriter, mode="w|")`，流式，不压缩）中依次是：

```text
manifest.json   {"format": 1, "app_version", "created_at"(UTC ISO), "task_count", "file_count", "db_dump": "db.dump"}
db.dump         pg_dump -Fc 的输出
files/<storage_key>   /data/files 下文件名匹配 ^[0-9a-f]{32}$ 的普通文件（已是主密钥密文，原样放入）
```

manifest 先写（task\_count 取 tasks 表行数，file\_count 为实际放入的文件数，两者在 pg\_dump 之后统计）。恢复时需要**备份密码 + 主密钥**两者：原件和敏感字段在备份里仍是主密钥密文（运维说明在 M8-04 写明）。

### 3.3 流程（service.py）

```python
def run_backup(db: Session, *, trigger: str, user_id: uuid.UUID | None, now: datetime | None = None) -> BackupRecord
```

1. 取会话级 advisory lock（固定键，`pg_try_advisory_lock`）；取不到时直接返回（另一个备份正在运行），不写记录。取到后把其他仍为 running 的 backup\_records 置 failed（`error_message="备份中断"`，进程崩溃遗留的记录，Q-101）。
2. 写一条 backup\_records(status=running, trigger, started\_at) 并提交（数据页能看到“进行中”）。
3. 文件名 `aireview_{yyyyMMdd_HHmm}.bak`，时间取 Asia/Shanghai。目标 .bak 已存在时失败（“同一分钟内已有备份”，Q-102）。删除 /backup 下残留的、匹配 `^aireview_\d{8}_\d{4}\.bak\.tmp$` 的文件。
4. pg\_dump：`pg_dump -Fc --no-owner --no-privileges -f {BACKUP_DIR}/.work/db.dump`，连接参数从 DATABASE\_URL 拆成 PGHOST、PGPORT、PGUSER、PGPASSWORD、PGDATABASE 环境变量传入，**不放在命令行参数中**（避免出现在进程列表）；`.work/` 目录权限 700，在 finally 中删除（Q-103）。返回码非 0 时失败，错误信息只写“数据库导出失败（返回码 n）”，不带 stderr。
5. 打开 `{name}.tmp`（O\_EXCL，权限 600）→ EncryptingWriter → tar 流式写入 3.2 的内容 → close → flush → `os.fsync`；同时边写边算 SHA-256（对加密后的字节）。
6. 写 `{name}.sha256`，内容 `{hex}  {name}\n`（与 `sha256sum -c` 兼容），fsync。
7. `os.replace(.tmp, .bak)`，再 fsync 目录。
8. 轮换：列出 /backup 下匹配 `^aireview_\d{8}_\d{4}\.bak$` 的文件，按文件名排序，删除超过 backup.keep 份的最旧文件及其同名 `.sha256`；不匹配命名规则的文件一律不碰。只在本次成功后执行。
9. 记录 status=success、file\_name、size\_bytes、sha256、finished\_at；写审计 backup\_run；提交。
* 任一步失败：删除 .tmp 和本次的 .sha256，记录 status=failed、error\_message（中文、只写哪一步失败和错误类名，不含路径以外的内容），写审计，提交，然后正常返回（不让 job 进入重试，Q-101）。最后在 finally 中释放 advisory lock、删除 .work。
* 备份密码文件无效（Q-100）、备份目录不存在或不可写，同样记为 failed 并给出中文原因，便于管理员在数据页看到。

### 3.4 触发（job.py）

* job 类型 `backup`，payload `{"trigger": "manual" | "schedule", "user_id": "…" | null}`；处理函数调用 run\_backup。worker.py 的 main 增加一行 `import app.backup.job`。
* 立即备份（接口在 M7-07）：调用 `enqueue_backup(db, trigger="manual", user_id=…)`；已有 queued / running 的 backup job，或 backup\_records 中有 running 的记录时返回 None，接口据此返回 409 BACKUP\_RUNNING“已有备份正在进行”。
* 定时（`register_periodic("backup_schedule", check_schedule, 60)`）：本地时间（Asia/Shanghai）已到 backup.time，且“今天（本地日期）还没有创建过 trigger=schedule 的 backup job”时，入队一个 schedule 备份（Q-104）。worker 在备份时间之后才启动的，当天启动后补做一次。
* `jobs.finalize_failed` 增加 backup 分支：job 在处理函数之外最终失败时，把 running 的 backup\_records 置 failed（Q-53 的做法）。

### 3.5 测试（tests/test\_backup\_archive.py、tests/test\_backup.py）

* archive：往返（0 字节、恰好 1 块、多块、不足 1 块）；改动文件头 / 任一块的任一字节 / 调换两块 / 删除末块 / 末块后追加数据 / 密码错误 / scrypt 参数被改大，全部 BackupFormatError；相同内容两次加密的密文不同。
* run\_backup（真实测试库 + pg\_dump，BACKUP\_DIR、FILES\_DIR 用临时目录）：T-16——写入过程中只有 .tmp、没有 .bak（在 EncryptingWriter 写入时检查目录），完成后只有 .bak 与 .sha256，`sha256sum -c` 语义校验通过；decrypt\_stream 后 tar 中有 manifest、db.dump、files/，`pg_restore --list db.dump` 成功；保留 2 份时第 3 次成功后最旧的 .bak 与 .sha256 被删，`aireview_x.txt`、`other.bak` 不被删；失败（pg\_dump 返回非 0、密码文件为空）时没有 .tmp 残留、不轮换、记录 failed；advisory lock 被占用时不写记录；定时检查当天只入队一次；明文备份密码和数据库密码不出现在日志、记录和异常消息中。

## 四、账号（M7-02，`app/admin/users.py`、`Users.vue`）

```text
GET   /admin/users                → {"items": [UserRow]}（不分页，账号 ≤ 200；按 created_at 升序）
POST  /admin/users                {username, display_name, password, role} → UserRow（201）
PATCH /admin/users/{uid}          {display_name?, role?, status?} → UserRow
POST  /admin/users/{uid}/reset-password  {new_password} → 204
UserRow = {id, username, display_name, role, status, must_change_password, last_login_at, created_at}
```

* username：1–50 个字符，只允许字母、数字和 `_ . @ -`（Q-99），已存在时 409 USERNAME\_EXISTS；display\_name：1–50 个字符；role：user / admin；password 按 6.6 规则（`validate_password_strength`，422 PASSWORD\_TOO\_WEAK 沿用已有错误码）。新建与重置后 must\_change\_password=true；重置同时清零 failed\_login\_count、清空 locked\_until、删除该用户全部会话。
* 停用（status=disabled）时调用 `delete_user_sessions`。启用时清零 failed\_login\_count 与 locked\_until。
* 最后一个管理员：把某个启用中的管理员停用或改为 user 之后，若不再有启用中的管理员，返回 409 LAST\_ADMIN“不能停用或降级最后一个启用中的管理员”。判断前对全部 role=admin 的行加 `FOR UPDATE`，防止两个请求同时各降一个。
* 不能修改自己的角色和状态：409 SELF\_CHANGE“不能停用自己或修改自己的角色”（Q-99）；自己的显示名可以改。
* 不存在的 uid（含非法 UUID）返回 404 USER\_NOT\_FOUND。不提供删除接口。
* 前端：表格列 用户名、显示名、角色、状态、最近登录时间、操作（编辑 / 停用或启用 / 重置密码）；“新增账号”按钮在表格上方。新增、编辑、重置密码用 el-dialog；停用用 ElMessageBox 二次确认。角色、状态的中文放 labels.ts（管理员 / 普通用户；启用中 / 已停用）。当前登录的管理员那一行不显示停用和角色修改。
* 测试：每个错误码；停用后会话被删除、该用户再访问 401；重置后须改密；最后管理员并发两次降级只有一次成功；非管理员 403；审计 detail 不含密码。

## 五、模型（M7-03，`app/admin/model.py`、`Model.vue`）

```text
GET  /admin/settings/model  → ModelSettings（api_key 只返回 {"api_key_set": bool, "api_key_last4": "abcd" | null}）
PUT  /admin/settings/model  ModelSettingsIn（全部字段必填，api_key 可选：缺省、null 或空串表示不修改）→ ModelSettings
POST /admin/settings/model/test → {"ok": true, "model": "…", "duration_ms": n, "reply": "OK"} 或 {"ok": false, "message": "中文原因"}
GET  /admin/usage           → {"calls", "cap", "tokens_in", "tokens_out", "cost": "12.34", "month": "2026-10"}
ModelSettings = {base_url, name, temperature, max_tokens, timeout_s, json_mode, extra_params, chunk_chars,
                 price_in_per_m: "0.00", price_out_per_m: "0.00", monthly_call_cap, api_key_set, api_key_last4}
```

* 校验（Q-105）：base\_url 以 http:// 或 https:// 开头、不超过 500 字、不含空白；name 1–100 字；temperature 0–2；max\_tokens 1–1000000；timeout\_s 10–600；chunk\_chars 1000–1000000；monthly\_call\_cap ≥ 0 的整数；单价为 ≥ 0、最多 4 位小数的十进制数（接口收发字符串，存入 settings 时也存字符串，计算一律 Decimal）；extra\_params 必须是 JSON 对象（前端文本框里填 JSON 文字，前端先 `JSON.parse` 再提交对象），不得含 `messages` 键（422 EXTRA\_PARAMS\_INVALID“附加请求参数须为 JSON 对象，且不能包含 messages”）；api\_key 只接受可见 ASCII 字符、8–500 个（与 cli set-model 一致）。
* api\_key 用 `crypto.encrypt_to_b64` 存 model.api\_key\_enc；GET 解密后只取末 4 位；任何响应、日志、审计都不出现完整密钥。
* 测试连接：调用已有的 `gateway.test_connection(db, user.id)`，测的是**已保存**的设置（Q-106）；GatewayError 时返回 ok=false 和网关的中文说明（不抛 5xx）；同样受上限与出口复检约束，写 llm\_calls（purpose=test）。测试连接不写审计。
* 用量：`app.llm.usage.monthly_usage`；cost 以字符串返回。
* 前端：一个表单卡片（接口地址下方提示“更换地址后，需 IT 同步修改虚拟机防火墙白名单”；API 密钥用 `type="password"`，已设置时占位文字“已设置（末 4 位 xxxx），留空表示不修改”；附加请求参数文本框下方提示 DeepSeek 推荐值 `{"thinking": {"type": "enabled"}}`（Q-12），保存前前端校验是合法的 JSON 对象）；“保存”“测试连接”两个按钮，测试连接旁提示“测试的是已保存的设置”；用量卡片显示本月调用次数（上限为 0 时写“不限”）、输入 / 输出 token、估算费用（元）。
* 测试：每条校验的边界；密钥为空不修改、新密钥生效且 GET 只有末 4 位；审计 keys 只列变化的键且不含密钥；测试连接成功 / 未配置 / HTTP 错误（模拟服务）；monthly\_call\_cap 生效（复用 T-13 的做法）。

## 六、审核要求（M7-04，`app/admin/requirements.py`、`Requirements.vue`）

```text
GET    /admin/company-requirements        → {"items": [CompanyReqRow], "version": 当前版本号 | null}
POST   /admin/company-requirements        {text, doc_types, stances, enabled, sort} → CompanyReqRow（201）
PUT    /admin/company-requirements/{id}   同上（全量）→ CompanyReqRow
DELETE /admin/company-requirements/{id}   → 204
GET    /admin/company-profile             → {"text": "…", "version": n | null}
PUT    /admin/company-profile             {text} → 同上
GET    /admin/requirement-versions        → {"items": [{version, created_by_name, created_at, snapshot}]}（按版本号降序，不分页）
CompanyReqRow = {id, code, text, doc_types, stances, enabled, sort, created_at, updated_at}
```

* text 1–200 字；doc\_types 为 `["all"]` 或 DOC\_TYPES 的非空子集（去重；含 all 时只能是 `["all"]`）；stances 同理（sales / purchase / other）；sort 0–9999 的整数。条数已有 30 条时新增返回 409 COMPANY\_REQ\_LIMIT“公司补充要求最多 30 条”。公司说明 0–300 字（可为空）。

## 七、脱敏（M7-05，`app/admin/redaction.py`、`Redaction.vue`）

```text
GET    /admin/settings/redaction   → {"mask_quantity": false}
PUT    /admin/settings/redaction   {mask_quantity} → 同上
GET    /admin/terms?kind=learned|custom&q=&page=   → 分页 TermRow
POST   /admin/terms                {term} → TermRow（201），只能新增 custom
PATCH  /admin/terms/{id}           {enabled} → TermRow，只能用于 custom（learned 返回 409 TERM_NOT_EDITABLE）
DELETE /admin/terms/{id}           → 204（learned、custom 都可以）
TermRow = {id, kind, term（明文）, category, is_our_party, enabled, hit_count, last_hit_at, created_by_name, created_at}
```

* kind 必填；q 为空时不筛选。term\_enc 需解密才能搜索：取出该 kind 的全部行解密后在内存中按规范形式（`parties.normalize`）做包含匹配，再按 created\_at 降序分页（Q-110）。解密出的文字只进响应，不写日志。
* 新增自定义敏感词：去掉首尾空白后 2–100 字，category 固定 CUSTOM；term\_hash 用 `engine.term_hash`；(kind, term\_hash) 已存在时 409 TERM\_EXISTS；文字按出口复检规则出现在固定提示文字中（`prompt.fixed_prompt_text`）时 422 TERM\_IN\_PROMPT（复用 M5-02 的判断与文字，否则每次审核都会被出口复检拦截）。
* 修改 mask\_quantity、新增或删除词条**只影响之后的解析与重算**，已在第二步的任务不自动重算（Q-110）。
* 前端（三块卡片）：① 数量脱敏开关（切换即保存，下方说明“开启后数量也会替换为代号，只影响之后解析的文件”）；② 自定义敏感词：输入框 + “添加”，表格（敏感词、启用开关、添加时间、删除）；③ 已记住的名称：搜索框，表格（名称、类别（公司 / 人名）、是否我方、记录人、记录时间、命中次数、删除），分页 20。删除用二次确认。名称与敏感词按纯文本显示。
* 测试：分页与搜索（中英文、大小写、全角）；TERM\_EXISTS、TERM\_IN\_PROMPT、TERM\_NOT\_EDITABLE；新增的自定义词在之后的新任务中被替换、停用后不再替换、删除后出口复检不再检查；审计 detail 不含词条文字；非管理员 403。

## 八、原件保留期清理（M7-06，`app/backup/retention.py`）

* 定时：`register_periodic("retention_schedule", check_retention, 60)`：本地时间已过 03:30，且今天（本地日期）还没有创建过 retention job 时入队一个（payload `{}`）；retention.original\_days = 0 时不入队。处理函数 `job_handler("retention")`；worker.py 的 main 增加一行 `import app.backup.retention`。
* 处理：再次读取 original\_days（为 0 直接结束）；截止时间 = now − days 天。选出 `last_completed_at < 截止时间`、`status in ('reviewed', 'completed_local')`、且有 original\_deleted\_at 为空的文件的任务（Q-109）。逐个任务：锁任务行（`FOR UPDATE`）后重新检查上述条件 → 对每个未删除的文件 `storage.delete_original`（文件不存在不报错）→ 该任务全部 doc\_nodes 的 text\_enc 置 NULL → 文件 original\_deleted\_at = now → 提交。单个任务失败只记日志（任务 id 和错误类名）并继续下一个。结束写一条审计 retention\_run（{"tasks", "files"}）。
* 不删除也不修改：redacted\_text、对照表、轮次、问题（含引用快照）、本地校验结果、对话（16.4）。
* **last\_completed\_at**：不外发的任务在 pipeline 置 completed\_local 时同时写 last\_completed\_at（M5 只在审核完成时写，不外发的任务原来一直为空，永远不会被清理）。
* **原件删除后的限制**（16.4“不再提供重新审核和追问”）：
  * `PATCH /tasks/{id}`（重新审核）：任务有任一文件 original\_deleted\_at 不为空时 409 ORIGINAL\_DELETED“原件已按保留期限删除，不能重新审核”（放在状态检查之前）；
  * 追问 `chat.service.availability`：增加原因“原件已按保留期限删除，不能追问”（放在最前），preview 与发送随之 409 CHAT\_UNAVAILABLE；
  * TaskFileOut 增加 `original_deleted_at`（可空）；结果页在任一文件已删除时不显示“重新审核”按钮（追问按钮按 chat 接口的 available 自动禁用并显示原因）。右栏提示沿用 M3 的“原件已按保留期限删除”。
* 测试（T-18）：保留期设为 1 天、把任务 last\_completed\_at 改到 2 天前后执行处理函数：原件文件不存在、text\_enc 全为空、original\_deleted\_at 已写；报告仍可导出且原文列来自引用快照（复用 M6 的报告测试）；节点接口 text\_available=false、raw 接口 404 ORIGINAL\_DELETED；重新审核 409、追问不可用；未到期、awaiting\_confirm / reviewing / parse\_failed 的任务不动；days=0 不入队也不处理；同一天只入队一次；第二次执行不重复处理已删除的文件。

## 九、数据页（M7-07，`app/admin/data.py`、`Data.vue`）

```text
GET  /admin/settings/backup      → {"time": "02:00", "keep": 7, "dir": "/backup"}
PUT  /admin/settings/backup      {time, keep} → 同上
POST /admin/backup/run           → 202 {"queued": true}；已有备份在进行 409 BACKUP_RUNNING
GET  /admin/backup/records       → {"dir", "free_bytes", "latest": BackupRow | null, "items": [BackupRow]（最近 20 条）}
GET  /admin/settings/retention   → {"original_days": 0}
PUT  /admin/settings/retention   {original_days} → 同上
GET  /admin/outbound-logs?user_id=&from=&to=&status=&page=  → 分页 OutboundRow（按 created_at 降序）
GET  /admin/outbound-logs/{id}   → OutboundRow + {request_text, response_text, block_reason, error_message}
GET  /admin/system/status        → {"version", "queued_jobs", "data_free_bytes"}
BackupRow = {id, trigger, status, file_name, size_bytes, sha256, error_message, started_at, finished_at}
OutboundRow = {id, created_at, user_id, user_name, task_title, purpose, model_name, chars, status, tokens_in, tokens_out}
```

* time 为 `HH:MM`（00:00–23:59）；keep 1–60；original\_days 0–3650 的整数（Q-111）。dir 只读显示 BACKUP\_DIR。
* free\_bytes / data\_free\_bytes：`shutil.disk_usage(BACKUP_DIR / FILES_DIR).free`；目录不存在时为 null。queued\_jobs：jobs 中 status=queued 的条数。version：APP\_VERSION。
* 外发记录：status 取 sent / blocked / error；user\_name 为该用户的显示名（用户不存在时为 null）；chars 为 request\_text 的字符数（blocked 为 0）。详情原样返回脱敏后的内容（17.2 允许管理员查看）。id 不存在 404 OUTBOUND\_LOG\_NOT\_FOUND。外发记录只读，不写审计。
* 前端（四块卡片）：① 备份：备份时间（el-time-select 或 el-time-picker，格式 HH:mm）、保留份数（el-input-number 1–60）、保存；备份目录（只读）、剩余空间、最近一次结果（状态标签、时间、文件名、大小）；“立即备份”按钮，点击后每 3 秒刷新记录直到最新一条不再是 running（离开页面停止，SPEC 21）；最近 20 条记录表格，失败的显示原因；② 原件保留期限：天数输入（0 表示永久）+ 保存，说明“到期后删除原件和节点原文，保留审核结果和报告；删除后不能重新审核和追问。旧备份中仍保存着这些原件，直到被轮换删除。”；③ 外发记录：筛选（用户下拉取 /admin/users、日期范围、状态），表格，点击行打开 el-drawer 显示外发文本和返回内容（纯文本 `white-space: pre-wrap`，不得用 v-html）、拦截原因或错误信息；④ 系统状态：版本号、排队任务数、数据盘剩余空间。字节数显示为 MB / GB（保留 1 位小数）。立即备份、保存后调用 `auth.refresh()` 更新提醒条。
* 测试：每个接口的校验和 403；立即备份入队与 409；外发记录筛选（用户、日期边界按 Asia/Shanghai、状态）、分页、详情 404；records 的最近一条与空间字段。
