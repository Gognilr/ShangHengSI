## 一、填空括号（B-01，R1-01）

**现象**：模板用【】括起填写内容，“法定代表人：【张某】”“人民币【123456】元”“账号：【6222…】”“合同编号：【 HT-01 】”都不识别；签约方名称带上了“【”。

**根因**：各条规则要求“标签 / 币种”与值紧挨（只允许空白），中间的括号把规则打断。

**规则**：定义填空括号 `【】［］[]〖〗`（只这几种，不含圆括号和书名号）。

1. 标签（签约方、人名、账号、SWIFT、编号、地址、合同总价）后的冒号与值之间，允许“空白 + 一个开括号 + 空白”；值在遇到对应的闭括号时结束。
2. 金额：币种与数字之间、数字与后置币种（含“元”）之间，允许“空白 + 一个括号 + 空白”，如“人民币【123456】元”“￥【 100 】”“【100】元”。替换范围仍只是数字。
3. 中文大写金额：“人民币【贰拾贰万贰仟零陆拾叁】元整”——大写部分在括号内、“元”在括号外时同样识别，替换括号内的大写数字（与同值的小写金额同一代号，沿用现有键规则）。
4. 签约方名称两端的括号不属于名称；对照表中的名称不含括号。
5. 出口复检的“带币种”判断（`_has_currency`）与重扫（find_formatted、find_amounts）同样跨越填空括号——重扫直接复用第 1、2 条的 detect 函数即可。

**测试**：虚构的【】模板合同样本，覆盖签约方、法定代表人、联系人、电话、账号、开户行、合同编号、合同总价、分期金额（小写与大写）、地址；另加反例：“【2】份”“第【3】期”“【30】％”“【十】日”不替换。

## 二、人名误识别与代号内部命中（B-03、B-04，R1-02）

**现象**：“授权代表：（空）授权代表：”识别出“授权”；“联系人电话：”识别出“电话”；“联系人姓名：”识别出“姓名”；“授权代表应签署”识别出“应签署”。人名会全文替换，条款原意被破坏。“电话”进入对照表后，代号“[电话]”本身含这两个字，出口复检永远拦截。

**规则（find_persons）**：

1. 标签后紧接的汉字串如果以另一个人名标签、地址或信息标签（电话、手机、传真、邮箱、地址、姓名、名称、职务、日期、签字、签章、盖章、授权、委托、代表）开头，不识别。
2. 候选串（截断、去称谓之前）后面紧跟冒号的，是标签，不识别。
3. 非人名词表（扩充 `_CN_NOT_PERSON`）：上述词以及“签署、盖章、姓名、名称、日期、电话、本单位、法人、代理人”等；去称谓后的结果在表中时不识别。
4. 不带冒号的标签（`_PERSON_LABELS_OPT` 无冒号分支）：标签与人名之间必须有空白或填空括号（“法定代表人 张某”“法定代表人【张某】”），紧挨着的汉字（“授权代表应签署”）不识别。
5. 全文替换（Q-71 ②）只用于通过第 1–4 条的人名，不另加规则。

**规则（recheck）**：检查真实值、词条之前，先把文本中**本任务对照表的代号**（对照表的键，去掉“#序号”）和固定代号（`[电话]`、`[邮箱]`、`[网址]`、`[证件号]`、`[地址：…]`）原样遮盖为等长的不可匹配字符；遮盖只影响 MAP / TERM 的匹配，格式化与金额重扫仍在原文上做。代号列表由 `RecheckContext` 新增字段 `placeholders` 提供（`recheck_context` 从对照表读出），`recheck()` 新增关键字参数 `placeholders=()`，默认不遮盖，其他调用方行为不变。

**测试**：两种签字栏布局（两栏空白、“联系人姓名：”“联系人电话：”）不出人名；“授权”“电话”等词在正文中不被替换；真实值“电话”（人为放入对照表）出现在“[电话]”中不拦截、出现在正文中仍拦截。

## 三、表格金额（B-02，R1-03）

**现象**：报价表下方的“结算价合计”小表（第二个表头只有“金额”列）的金额原样外发；“小计”行的数字落在第一个表头的“数量”列，未替换；合计列名为“合计”的清单整列不按金额处理。出口复检拦住一个金额、用户补充后，同一数值的其他写法（`1150000` 与 `1,150,000.00`）不带币种时不拦截。

**规则（tables.py）**：

1. **多个表头行**：一个表格可以有多个表头行。表头行 = 某个单元格是单价 / 金额表头、且该行没有“纯数字”单元格的行；第一个表头行仍只在前 20 行中找（Q-65），之后的表头行不限行号。每个表头行的列提示管到下一个表头行为止。
2. **金额列名**：`_AMOUNT_HEADER` 增加“合计、小计、总计、Subtotal”（列名中出现即为金额列；单价优先不变）。本条只影响脱敏，不改本地校验的列名同义词（B-09 另行决定）。
3. **合计行**：行内第一个非空单元格含“合计、小计、总计、Total、Subtotal”的行，该行所有“纯数字”单元格一律按金额（AMOUNT）处理，不管落在哪一列。
4. 汇总行（9.7）的范围仍按第一个表头行和数据行确定，不因第 1 条改变。

**规则（recheck）**：对照表中的金额类真实值（`_AMOUNT_VALUE` 能匹配的值），文本中出现**数值相等**的数字即拦截，不再要求带币种——但只限数值 ≥ 10000 的值（避免“30”“2023”和条款编号“1.8”这类小数字误拦截；小于 10000 的仍按原规则须带币种。原定“带小数也算”在 R1-03 实测中误拦条款编号，已改）。

**测试**：虚构的双表头报价表（主表 + 合计小表 + 小计行落在数量列 + 列名为“合计”的清单）全部金额替换；recheck：`1150000` 在对照表中时，`1,150,000.00`、`1150000.00` 不带币种也拦截，“2023 年”“30 天”不拦截。

## 四、合同总价（B-05，R1-05）

**现象**：“合同总价的 30%，即人民币 X 元”“软件总价款的 20%，即 ￥X”中的 X 被当作合同总价，比例写成 1306.8%、333.3%。

**规则（ratio.contract_total 的标签法）**：

1. 标签与金额之间出现百分比（`数字 %`、`％`、`‰`）或“的”字时，这个标签不算。
2. “总价、总金额”前面紧挨着“合同、本合同”以外的汉字时（如“软件总价款”“硬件总价”），这个标签不算；“合同总价、合同总额、合同金额”不受影响。
3. 其余不变：都不算时按“同币种取最大”。

**测试**：两种“总价的 N%，即……”写法不作为总价；“本合同固定总价为：人民币【X】元”（依赖 R1-01）作为总价；分项总价不作为总价。

## 五、企业名称截断（B-07，R1-04）

**现象**：“乙方：【××集团山东有限公司德州分公司】”在“集团”处截断，剩下的“山东有限公司德州分公司”留在正文；开户行“××银行股份有限公司××支行”的支行名留在正文。

**规则（parties.extract_org_name、find_other_org_names）**：

1. 取到第一个后缀后继续向后看：在同一名称内（不跨越冒号、分号、句号、逗号、顿号、引号、空白、填空括号、换行，不跨越“（以下简称”“（下称”“(hereinafter”），若后面还有企业后缀，名称延伸到**最后一个**后缀；最长 60 个字。
2. 后缀表在延伸时（只在延伸时）增加“分公司、支行、分行、营业部、办事处、分厂”。
3. 名称内的地区括号（“（深圳）”）按现有规则保留。

**测试**：集团 + 有限公司 + 分公司、银行 + 支行、“××有限公司（以下简称“××”）”不把简称并入、“A 有限公司与 B 有限公司”不连成一个名称（“与”隔开时第二个由正文识别）。

## 六、中国地址（B-08，R1-06）

**现象**：“××省××县……”“××市××区……”的地址代号为“[地址：国家未知]”。

**规则**：地址文字中查不到 countries.yaml 中的国家时，若含“省、自治区、市、县、区、镇、乡”且这些字前面至少有 2 个汉字（如“山东省”“临邑县”），判为“中国”。香港、澳门、台湾按 countries.yaml 已有词条优先。签约方国家（_assign_countries）读地址行时同样适用。

**测试**：省 / 市 / 县 / 区地址判为中国；英文地址、只有“区”字的英文转写不受影响；“香港特别行政区”仍按词典。

## 七、疑似遗漏误报（B-17，R1-07）

**现象**：“《……规范》（GB 50312-2007）”这类标准编号被列为长数字疑似遗漏；“以下模块仅本公司”被列为企业名称疑似遗漏。

**规则（suspects.py）**：

1. 长数字（long_digits）候选前紧挨（允许空白、“/”和“T”）标准代号时排除：GB、GB/T、GB/Z、GBJ、JB、JB/T、HG、HG/T、SH、SH/T、YB、DL、DL/T、JGJ、CJJ、SJ、YD、NB、ISO、IEC、EN、ASTM、DIN、JIS、ANSI、API；编号形如“数字（可含小数点）- 4 位年份”。只排除这一种结构，其余长数字不变。
2. before_company：候选汉字串中，“公司 / 厂”前紧挨的是泛指词（本、贵、我、该、其、此、各、我方、对方、双方等，即现有 _GENERIC_BEFORE_COMPANY 中的单字与词）时，不论前面还有多少汉字都不列。

**测试**：五种标准编号写法不列；“GB 12345678”（无年份）、“账号 1234 5678 9012”仍列；“仅本公司不限”“由我公司负责”不列；“××虚构科技公司”仍列。

## 八、本地校验金额列名（B-09，R1-08）

**现象**：清单表头为“数量 / 单价 / 合计”，整表“未识别报价表结构”。

**规则（checks/amounts.py column_kind）**：表头单元格文字为“合计、总计、总额、合计（元）、合计金额”等（含“合计 / 总计 / 总额”，且不含单价、数量、税率、税额字样）时为金额列。合计行的判断（行首单元格含“合计 / 总计 / Total”）不变：表头行与合计行由所在位置区分（表头行之下的行才可能是合计行）。

**测试**：“合计”列名的清单完成 L-01、L-02；原有样本 manifest 不变；“合计”作为行首的合计行仍是合计行。

## 九、同一文件内的合同总价与附件合计（B-10，R1-09）

**现象**：附件清单与合同正文在同一个 DOCX 中，L-05 只比较跨文件，正文总价与附件合计不核对（M6-02 的设计是“主文件自身报价表不参与”）。

**规则（checks/consistency.py）**：

1. L-05 的比较对象增加主文件自身的报价表（合计行能解析出金额的表），与附件文件的表同样处理；改写 design/M6.md 3.4 的“主文件自身报价表不参与”（记入 Q-135）。
2. 表格本身识别不到币种、而合同总价有币种时：若整个任务中所有带币种的金额只有一种币种，则表格按该币种比较，详细说明中注明“报价表未注明币种，按合同币种比较”；否则不比较（不报 L-05，也不报 L-06）。
3. 其余（L-06 报出后不再报 L-05、差额判断）不变。

**测试**：同文件正文总价与附件合计一致不报、不一致报出；表格无币种、任务单一币种时按合同币种比较并注明；多币种时不比较；原有跨文件用例不变。

## 十一、邮编（B-18，R1-11）

**现象**：“邮政编码：【251500】”原样外发；邮编对审核没有用，却能定位到县级地区。

**规则**：

1. detect.find_formatted 新增类别 POSTCODE：标签“邮政编码、邮编、Postal Code、Post Code、Zip Code、ZIP”（英文不区分大小写）后，冒号或空白、可跨一个填空括号（同第一节），取 3–10 个字母、数字、空格或短横线组成、至少含一个数字的值；值的两端不含空格。只认标签，不按“6 位数字”猜测。
2. 代号为共用的“[邮编]”（placeholders.FIXED 增加一项），与电话相同：不能唯一还原，真实值写入对照表（键“[邮编]#n”）供出口复检第 1 条拦截。recheck 遮盖的固定代号增加“[邮编]”。出口复检第 2 条的重扫不加邮编（无标签的 6 位数字太常见）。
3. 类别约束：新增迁移 0003，redaction\_items、redaction\_suspects 的 category CHECK（0001 中这两张表共用 9.2 全部代码）增加 POSTCODE；models.py 的类别元组同步；tests/test\_migrations.py“模型与迁移一致”通过；降级时删除 POSTCODE 行后恢复原约束。
4. 前端：labels.ts 与 ConfirmStep.vue 的类别文字增加“邮编”（“个邮编”）；追问代号 CHAT\_LABELS 增加“邮编”。

**测试**：带【】与不带括号、中英文标签各一；“邮编：100000-1234”“Zip Code: SW1A 1AA”识别；“邮编为空”“邮编：”（无值）不识别；正文中无标签的“251500”不识别；出口复检：真实值在对照表中时拦截，“[邮编]”本身不拦截；迁移升级 / 降级。

## 十二、开户行（B-20，R1-12）

**现象**：“开户银行：××行××高新技术园区支行”没有明确企业后缀，不识别，原样外发（取代 Q-137 ③）。

**规则（parties.find\_labeled\_parties）**：标签规范为“银行”（开户行、开户银行、收款银行、Bank Name、Beneficiary Bank；单独的“Bank”不在此列）时，冒号后（可跨一个填空括号）的值若以“银行、支行、分行、分理处、营业部、储蓄所”结尾（英文值不处理），即使不含企业后缀也作为该标签的主体；值不跨越分隔符、空白和换行，最长 60 字，至少 4 个汉字。已有的“取到企业后缀并延伸”的结果优先，本条只在原规则取不到名称时生效。类型按 org\_types.yaml 判为银行（名称含“行”的写法若词典不命中，类型固定为“银行”）。

**测试**：“开户银行：示例行虚构园区支行”“开户行：【虚构银行】”识别为银行主体并全文替换；“开户行：见附件”“开户行：”不识别；已有的“××银行股份有限公司××支行”结果不变；回归集与 A-03 通过。

## 十三、带简称定义的宽泛后缀名称（B-21，R1-13）

**现象**：“我单位对于所申请的××通信集团公司（以下简称“××”）的……”——宽泛后缀“公司”在正文中不自动替换，只列为疑似遗漏；用户忽略时简称会外发（全文 10 余次）。

**规则（parties、engine 第 2、3 步）**：

1. 正文中以“公司、集团、厂、研究院、研究所”结尾、且后面紧跟第 3 步简称结构（只允许空白）的名称，作为其他主体登记（与带明确后缀的名称同等处理，同一 \_Entity 规则），简称归入该主体全文替换。
2. 名称起点：从后缀向前取汉字，与疑似遗漏 \_cn\_name\_span 相同的边界（Q-56 边界词、“的并且或”、最多 10 个汉字、可含一组地区括号）；不足 2 个汉字或为泛称（本公司、该公司等，含 R1-07 / Q-138 的泛指词规则）时不登记。
