## 一、处理流程的变化

```text
parse 处理函数（app/tasks/pipeline.py）：
  解析全部文件 → 识别文件类型 → 【新增】checks.service.run_checks(db, task, today) 写 local_findings
  → local_only：completed_local（不脱敏）；ai：redact_task → awaiting_confirm
  （本地校验与解析在同一个事务中；本地校验内部异常按解析内部错误处理，任务 parse_failed）

外发文本（app/redaction/engine.build_outbound）：
  报价明细表汇总行末尾补“，本地校验：…”（第四节 4.3），文字由 checks.service.table_notes() 给出

审核上下文（app/review/service.build_context）：
  local_summary = checks.service.local_summary(db, task)（第四节 4.2），即【本地校验摘要】

追问（M6-07）：结果页 → POST /tasks/{id}/chat/preview → 用户确认 → POST /tasks/{id}/chat → 网关 → 还原后返回
```

“今天”取 Asia/Shanghai 的当天日期，由 run\_checks 的调用方传入（pipeline 传 `datetime.now(ZoneInfo("Asia/Shanghai")).date()`），校验函数本身不读系统时间，便于测试。本地校验只在解析时执行一次，之后不重算（Q-85）。

## 二、公共数据结构（M6-01，新建 `app/checks/model.py`）

```python
@dataclass(frozen=True)
class CheckNode:
    loc: str
    text: str          # 原文（解密后）
    file_seq: int      # task_files.seq
    clause_no: str | None

@dataclass(frozen=True)
class CheckFile:
    seq: int
    is_main: bool
    ext: str
    doc_type: str | None
    warnings: list[str]

@dataclass
class CheckResult:
    code: str            # "L-01"…"L-08"、"L-INFO"
    severity: str        # high / medium / low，按 SEVERITY[code]
    locs: list[str]      # 第一个是最该高亮的位置（L-01、L-02 为金额单元格）
    file_seq: int | None
    detail: str          # 含真实数字的中文说明，只在本地显示，加密存储
    ai_summary: str      # 不含绝对金额（见 4.1），会发给模型

SEVERITY = {"L-01": "high", "L-02": "high", "L-03": "medium", "L-04": "high", "L-05": "high",
            "L-06": "medium", "L-07": "medium", "L-08": "medium", "L-INFO": "low"}
```

只用 part=body 的节点做校验（Q-81）。所有数值用 Decimal；比较前 `quantize(Decimal("0.01"), ROUND_HALF_UP)`；差额判断一律 `abs(a - b) > Decimal("0.01")`。

## 三、各校验项

### 3.1 报价表识别（M6-01，`app/checks/amounts.py`）

* 表格与行列：复用 `app.redaction.tables.table_cell(loc)`（DOCX/PDF 表格 `…-T{n}`、XLSX 整个工作表为一个表）。“行号”取 loc 中的 R 序号或 Excel 行号。
* 表头行：每个表前 20 行（`tables.HEADER_SCAN_ROWS`）中第一个“同时含数量、单价、金额三列”的行；没有这样的行时，取第一个含单价列、或同时含数量列和金额列的行作为“疑似报价表”的表头。
* 列名识别（按此顺序，先命中先定，不区分大小写；本模块自己的函数 `column_kind(text)`，不改 redaction/tables.py）：
  1. 税率：税率、Tax Rate、VAT Rate
  2. 税额：税额、Tax、VAT（Tax Rate 已在上一步命中）；表头同时含金额、总价、单价、Amount、Total、Price 时不算税额列，继续往下匹配（“Amount incl. VAT”是含税金额列。M6 评审补充，2026-10-22）
  3. 单价：单价、Unit Price
  4. 金额：金额、总价、小计、Amount、Total、Subtotal（“Total Price”“Total Amount”在这里命中）
  5. 单价：Price
  6. 数量：数量、Qty、Quantity
  金额列中表头含“不含税”“excl”“net”的记为 amount\_excl，含“含税”“incl”“gross”的记为 amount\_incl，其余记为 amount（Q-82）。同一类有多列时取最左一列。
* 合计行：表头行以下，该行第一个非空单元格含“合计”“总计”或单词 Total（不区分大小写；“Subtotal”“小计”不算）的行（Q-83）。第一个合计行之后的行不再作为数据行。
* 数据行：表头行与合计行（没有合计行时到表尾）之间、金额列或单价列能解析出数字的行。
* 返回：

```python
@dataclass
class QuoteTableCheck:
    table: str               # 表格标识，与 redaction.quotes.QuoteTable.loc 相同
    file_seq: int
    recognized: bool         # 数量、单价、金额三列齐全
    rows_checked: int        # 三个值都能解析、参与 L-01 的行数
    rows_skipped: list[int]  # 金额或单价有值、但三个值不全能解析的数据行号
    row_errors: int          # L-01 不一致的行数
    total: Decimal | None    # 合计行金额（能解析时）
    total_ok: bool | None    # L-02：None 表示没有合计行或无法比较
    currency: str | None     # 金额列与单价列中识别到的第一个币种；表头中的币种其次；都没有为 None

def find_tables(nodes: list[CheckNode]) -> list[QuoteTableCheck]
def check_tables(nodes, files) -> tuple[list[QuoteTableCheck], list[CheckResult]]
```

### 3.3 L-04（M6-02，`app/checks/amounts.py`）

* 在每个正文节点中用 `app.redaction.detect.find_amounts(text)` 找金额，`detect.chinese_upper_value` 已能解析大写金额；大写金额命中（surface 由零壹贰…组成）与同一节点中距离最近的阿拉伯数字金额（含“万元”换算后的值）配对。同一节点中没有阿拉伯数字金额时，取同一表格行中紧邻的左、右单元格（Q-84）。
* 两者 quantize 到 2 位后不相等 → L-04，locs=[节点]；detail：`F1-P12：大写金额“捌拾万元整”= 800,000.00，相邻的小写金额 850,000.00`；ai\_summary：`F1-P12：大写金额与相邻的小写金额不一致，差异约 5.9%`。
* 大写部分无法解析（chinese\_upper\_value 返回 None）时不报 L-04，也不报 L-INFO。

* 合同总价：复用 `app.redaction.ratio.contract_total()`（9.6 与 Q-72 的规则），只在主文件（is\_main）中找；找不到时不做 L-05、L-06。

* L-05：币种相同，或任一方币种未知时（detail 末尾注明“附件报价表币种未识别”），合同总价与报价表合计差额 > 0.01 → L-05（高）；detail：`主文件合同总价 USD 186,500.00，附件报价表 F2-S1 合计 168,500.00，相差 18,000.00`；ai\_summary：`主文件合同总价与附件报价表 F2-S1 合计不一致，差异约 9.7%`。

## 四、发给模型的内容

### 4.1 ai\_summary 的约束（所有任务都要测）

* 只允许出现：位置编号、行号、校验名称、百分比、币种代码、日期、文件序号（F2）、行数。不得出现金额、单价、数量、税额的数值，不得出现文件名、单元格原文。
* 测试：对每个产生 CheckResult 的样本，断言 `recheck(ai_summary, real_values=对照表真实值, terms=[])` 为空，且 detail 中出现的每个金额数字（如 52,400.00、52400）都不出现在 ai\_summary 中。

### 4.2 【本地校验摘要】

`local_summary(db, task)`：按 local\_findings.id 顺序，每条一行 `[L-01] {ai_summary}`，用换行连接；没有记录时返回 ""（prompt.build\_user\_message 已有“空内容省略”）。build\_context 把它填进 ReviewContext.local\_summary。预检（create\_run）与 review 处理函数都经 build\_context，保证出口复检检查的就是发送的内容。分段时每段都带完整摘要（11.5，已由 prompt 实现）。

### 4.3 报价明细表汇总行

`quotes.summary_text(t, note: str | None = None)`：note 不为空时在 `】` 前追加 `，本地校验：{note}`。build\_outbound 调用 `checks.service.table_notes()` 按 QuoteTable.loc 取 note。note 的取值（按顺序拼接，用“，”连接）：

* 该表 recognized=False：`未识别报价表结构，未做金额核验`（只这一句）；
* 否则：rows\_checked=0 时 `金额未核验`；row\_errors=0 时 `金额计算一致`，否则 `金额计算有 {n} 行不一致`；rows\_skipped 非空时追加 `{n} 行未核验`；
* total\_ok 为 True / False 时追加 `合计一致` / `合计不一致`；
* 该表参与了 L-05 且未报 L-05、L-06 时追加 `合计与合同总价一致`；报了 L-05 追加 `合计与合同总价不一致`；报了 L-06 追加 `币种与合同总价不一致`。

示例：`[F2-S1] 【报价明细表：共 12 行，币种 USD，产品：油系针状焦等 3 种，本地校验：金额计算一致，合计一致，合计与合同总价一致】`。没有报价明细表、或某表 table\_notes 中没有对应项时汇总行与 M5 逐字相同。

```text
响应：application/vnd.openxmlformats-officedocument.wordprocessingml.document；
     Content-Disposition: attachment; filename="report.docx"; filename*=UTF-8''{百分号编码的中文文件名}
```

* 文件名 `审核报告_{主文件名去掉扩展名}_{yyyyMMdd}.docx`，日期为导出当天（Asia/Shanghai）；主文件名中的 `\ / : * ? " < > |` 和控制字符替换为 `_`。
* 每次导出调用 app/audit 中现有的写审计函数：action=report\_export，target\_type=run 或 task，target\_id，detail 只放 {"run\_no": n}，不含文件名。
* 页面 A4 横向；字体宋体（east-asia）/ Calibri；标题 16 磅，正文 10.5 磅，表格 9 磅。不用模板文件。
* 所有模型生成的文字先 `restore()` 还原（9.9），再去掉 XML 不允许的控制字符后作为纯文本写入；不解析 Markdown。

报告结构（与 SPEC 14 一一对应）：

1. 标题“商务文件审核报告”；基本信息表：文件名（主文件，其余文件列为“附件：…”）、文件类型、立场、来源、审核人（任务所有者 display\_name）、审核时间（finished\_at，Asia/Shanghai，`yyyy-MM-dd HH:mm`）、模型、审核要求版本（`内置 {builtin_req_version}；公司补充要求 第 {company_req_version} 版`，为空写“公司补充要求：无”）、轮次（`第 n 轮`）。立场、来源、类型用与前端相同的中文。
2. 覆盖说明与限制事项：第一句同结果页覆盖说明卡片，其余每条复用 `app.review.coverage.describe()`；coverage 为空时写“本轮次没有覆盖说明”。
3. 结论摘要：高 / 中 / 低问题数量；制裁结论（无明显风险 / 需注意 / 高风险（建议合规人员或律师确认））及原因，固定附“未联网核查，基于模型自身知识，需合规人员确认最新制裁与出口管制规定”。
4. 问题清单表：序号、等级、类别、位置、原文、问题说明、修改建议、引用状态、处理状态与备注。位置与结果页相同（复用 review/service 中现有的位置文字函数，必要时把它提为公共函数）；原文 = quote\_snapshot\_enc 解密，没有快照时写“—”（待核实、缺失型）；问题说明 = problem，后接“对我方的影响：{impact}”“依据：{basis}”（为空则省略）；修改建议 = suggestion，后接“建议措辞：{suggested\_text}”；处理状态与备注 = 待处理 / 已采纳 / 已忽略 + 备注。按结果页默认顺序（等级、序号）。
5. 本地校验结果表：校验项、严重程度、位置、说明（detail，含真实数字）；没有时写“本地校验未发现问题”。
6. 审核要求逐条结论表：编号、内容（req\_text 快照）、结论（有问题 / 未发现问题 / 不适用 / 无法判断）、备注。
7. 固定声明（原文照抄 SPEC 14）。

* 不外发的任务：只有 1（模型、审核要求版本、轮次三项写“—”，另加一行“未做 AI 审核”）、5、7。
* **不得读取 doc\_nodes.text\_enc 和原件**：报告只用快照、local\_findings、轮次与问题表，保证保留期清理（T-18）之后仍可导出。位置文字只用 clause\_no、sheet、cell\_ref、loc 等不加密字段。
* 界面与报告不出现“审核通过”“无风险”（A-08）；“无明显风险”是规定的制裁等级。
* 前端：结果页底部操作加“导出报告”（下载当前查看的轮次；completed\_local 用任务级接口）；审核历史的“操作”列加“导出”（最新轮次已结束或 completed\_local 时可用，否则不显示）。下载用 `<a>` 或 blob，文件名取响应头。
