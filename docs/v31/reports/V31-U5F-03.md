## 大文档提速（用户要求当场修，2026-11-05）

剖析（测试机 worker 容器内对该任务重算，回滚、不写库）发现四处，均为“结果不变”的改法：

1. **闭环逐段比对全部真实值**：
   * 先对脱敏后全文做一次“骨架”预筛（归一化、去掉空白与 `-.,`、OCR 折叠）。骨架不在全文中的真实值 / 词条，三条比对通路都不可能命中，不再逐段比对；数字类值不筛。
   * 逐段的格式化信息 / 金额 / 人名 / 地址重扫，按“段文本 + 文中出现的代号 + 保留项”的摘要缓存，只存类别与位置。
   * 复检里对脱敏后文本的归一化按文本缓存。
   * 以上只用于闭环；网关发送前的复检不走缓存。
2. **实体识别缓存键**：每段都把数 MB 的固定前缀重新哈希一遍，改为复用前缀的哈希状态，摘要相同。
3. **每次确认都整份重算**：
   * `ensure_default_replacements` 把“按记忆或本机判断保留”的待处理项当成升级前遗留，每次确认都整份重算（该任务一次 45～67 s）。
   * 现在与页面 `kept_by` 用同一判断排除这类项（V31Q-104）。
4. **确认时外发全文扫两遍**：02 的 `refresh_if_blocked` 先扫一遍，正式预检再扫一遍。改为先预检，被拦才重算再查。拦截时行为不变。

另外：
* app 启动后在后台预热实体识别与向量模型（原来第一次决定时才加载，约 40 s）。
* 思考内容字数计入“已收到”。

**核对**：
* 本机开发库 20 个待确认任务改前 / 改后各重算一次（回滚），外发全文摘要逐一比对：15 个确定性任务全部相同。

## 一次决定的增量重算（2026-11-06，续做）

**结论**：不拆 `compute()`，也不推算“受影响的段”。一次决定之后，绝大多数段的文字、段内代号和可能命中的值都没变，把只取决于这些输入的计算按输入缓存，重算时这些段直接复用。结果与全量重算逐字相同，没有引入新的不变量。

剖析：热进程一次决定约 10 s，`compute()` 跑两遍（第二遍来自向量辅助）。几乎全部时间都花在对每段无条件重做、而段文字从不变化的计算上：
* 自检闭环逐段比对真实值、遮盖代号、计算保留键，约 30%；
* `find_narrative_persons` 约 14%，以及金额、人名、格式化信息、地址识别；
* 引擎传播步骤里的归一化，以及“已识别值 × 全部段”约 23 万次逐段匹配。

改法（`backend/app/redaction/`）：
1. **逐段识别缓存**（新 `memo.py` 的 `by_text`）：
   * 范围：`detect` 的八个 `find_*`、`parties` 的签约方 / 简称 / 宽泛后缀 / 其他企业名、`suspects.plain_content_spans`、`dictionaries.public_institution_spans` 与 `is_known_place`、`engine._broad_names_with_alias`、标签判断、表格提示。
   * 依据：这些函数只取决于参数与固定词典。
   * 约束：只在进程内、有上限，每次返回新列表。
2. **闭环逐段复检 `SegmentChecker`**（取代 02/03 的 `cache=True` 与 `_RESCAN_CACHE`）：
   * 一轮之内真实值、代号、保留项只预处理一次。
   * 每段只比对骨架可能出现在本段的值（与 `present_values` 同一依据），数字类值一律比对。
   * 只按段内出现的代号遮盖。
   * 比对与重扫命中按“段文字 + 段内代号 + 可能命中的值”缓存；保留项在取出缓存后才过滤，所以保留一项不会使全部段失效。
   * 缓存只存类别、位置和保留键摘要。
   * `recheck()` 拆成同语义的几个函数；网关发送前的复检不走缓存。
3. **全文整体匹配**（`engine._Joined` 与传播步骤的 `matches`）：
   * 各段以 `\x00` 连接，每个词条、已识别值在全文上只匹配一次，再按段分组。
   * 这些正则不匹配 `\x00`、没有行首行尾断言，命中和处理顺序与逐段相同。
   * 可能匹配空串或含 `\x00` 的正则仍逐段匹配。

**核对**：
* 本机开发库 40 个待确认任务，新旧两版各做“重算 / 保留一项 / 替换一项”（回滚），比对外发全文、替换项、不确定项、对照表的摘要：全部相同。日期平移的随机偏移在脚本中固定，40 个任务均稳定可比。
* 测试机两个真实任务（助手会话 f0a6954b、审核任务 acfa6f94），各做 7 步，同样比对摘要：全部相同。
* 测试：复检、golden、A-03、脱敏引擎、脱敏接口、轮次接口、审核任务、助手、实体识别全部通过（418 通过，实体识别的 3 个模型评测按规定跳过）。

### 压到 1 s（同日续做）

剖析：一次页面请求要用 ORM 读三遍 2290 段正文。每遍约 70 ms，同样的数据用 Core 只要 10 ms，多出来的主要是两个用不到的 JSONB 列的解析和对象构造。实体识别缓存每次都取回并解密全部 2290 行；写回时，刷新要逐个检查 2290 个被赋值的正文对象。`compute()` 里的不确定项识别和闭环逐段复检仍各占一成以上。

改法（结果不变）：
1. **只读原文改用 Core**（`engine.task_texts`）：
   * 决定、不确定项列表、记忆与统计等只需要“位置 → 原文”，不再构造 ORM 对象。
   * `_run` 也用 Core 读取，只写回脱敏文本真正变了的段（`_write_redacted`）。
   * 本会话已载入的同一行用 `set_committed_value` 同步新值，之后的 ORM 读取不会拿到旧文本。
2. **实体识别缓存**（`_ner_entries`）：
   * 解密结果按（行 id, 更新时间）缓存在进程内，只含位置、类别、分数与缓存键摘要。
   * 每次只取回、解密变了的行；写回改为按主键批量更新变了的行。
3. **计算缓存**：
   * `find_suspects` 按（段文字, 已替换区间, 派生名, 小写词集, 是否表头）缓存；
   * `lowercase_evidence` 按全文缓存；
   * 闭环复检加“整轮指纹 + 段文字”一级缓存：同一组代号与值之下，段文字相同即直接复用。
