## 一、词库与本地不敏感内容识别（V31-S-01，GPT-6.1 Sol，high）

### 1.1 外部数据（V31Q-06、V31Q-15）

| 文件 | 来源 | 许可 | 取用 |
|-|-|-|-|
| `resources/zh_words.txt` | jieba 主词典 `jieba/dict.txt`（不取 extra\_dict），固定标签 `v0.42.1`（github.com/fxsjy/jieba） | MIT（Copyright 2013 Sun Junyi） | 2～4 个汉字、词频 ≥ 1000、词性不属于 `nr nrfg nrt ns nt nz j`（人名、地名、机构名、其他专名、简称）的词，每行一个，按词排序 |
| `resources/zh_legal_finance.txt` | THUOCL（github.com/thunlp/THUOCL）的 `THUOCL_law.txt`（9,896）与 `THUOCL_caijing.txt`（3,830），固定提交 | MIT | 只取第一列（词），2～8 个汉字，合并去重排序 |

* 两份文件各配一个 README（同 `en_words.README.md` 的写法）：来源 URL、标签或提交、原文件 SHA-256、生成口径、生成结果的行数与 SHA-256、上游许可全文。生成脚本放 `backend/scripts/`（只用标准库），不进镜像运行路径。
* **剔除表**：生成后若 golden 的 `must_replace`、`must_suspect` 出现回退，把引起回退的词写进 README 的“剔除表”并由脚本剔除，不降低词频门槛、不改规则。

### 1.2 用途（`dictionaries.py` 新增 `zh_words()`、`zh_legal_finance()`，均缓存）

| 位置 | 规则 |
|-|-|
| 实体识别（高置信与中置信） | 整段文字等于法律或财经词时不采用（与 `ner_stopwords` 同一层过滤） |
| 实体识别中置信 → 疑似 | 整段是中文且等于常用词时不列 |
| 疑似：`person_like`、`person_name` 中由动作词锚定的（“表示 / 说 / 确认”等） | 候选等于常用词时不列；后接称谓（先生、女士、经理……）或前接角色词（联系人为……）的不受影响 |
| 疑似：`before_company`、机构后缀 | 后缀前的部分等于法律或财经词时视为泛称（“保险公司”“仲裁委员会”）；**不用常用词表**（“苹果公司”“联想公司”是名称） |
| 疑似：其他原因 | 整段等于法律或财经词时不列 |

常用词表不用于企业后缀、签约方、词条、地址与格式化信息；不撤销任何已有替换。

### 1.3 本地不敏感内容（`suspects.py`，与 `public_institution_spans` 同样先遮盖再识别；实体识别中置信结果落在其中的同样不列）

| 类 | 规则 |
|-|-|
| 标准号 | 标准代号（GB、GB/T、GB/Z、JB/T、HG/T、YB/T、SH/T、DL/T、NB/T、QB/T、JGJ、CJJ、ISO、IEC、EN、ASTM、DIN、JIS、ANSI、API、BS、ASME、AWS、SAE、IEEE、GOST）+ 编号，可带 `-年份`、`:年份`、字母前缀（ASTM D388）与 `/` `.` 分级；现有长串数字的标准号排除并入此规则 |
| 化学式 | 元素符号与数字组成、至少含一个数字的串（SiO2、Fe2O3、Al2O3、CaCO3、H2SO4），另加不含数字的常见式小表（NaOH、NaCl、HCl、KOH、CaO、MgO）；不含数字的全大写串不按化学式处理（CNOOC） |
| 贸易术语 | Incoterms 11 个术语（EXW FCA FAS FOB CFR CIF CPT CIP DAP DPU DDP）及“Incoterms 2020 / 2010”写法 |
| 行业缩写与单位 | 新资源 `resources/plain_terms.txt`（开发方起草、待业务人员审阅，同 common\_terms 的写法）：MOQ、OEM、ODM、L/C、T/T、D/P、D/A、B/L、AWB、COA、COO、MSDS、SDS、TDS、QC、QA、FAT、SAT、PI、PO、HS 等，以及计量单位与参数名（MT、kg、mm、ppm、mesh、MPa、℃、Fixed Carbon、Volatile Matter、Ash Content、Particle Size、Real Density 等）；按单词边界、不区分大小写匹配 |
| 表头参数名 | 表格第一行的单元格（`-R1-C` 的 table\_cell；XLSX 为该工作表含 2 个以上非空单元格的最上一行）中，原因为 `capitalized` 或 `ner` 的候选不列；`org_suffix`、`before_company`、人名、长串数字照常 |

表头判断需要节点位置：`find_suspects()` 增加 `header: bool = False` 参数，由 `engine.compute()` 按 loc 计算后传入（XLSX 的“最上一行”在 compute 中按工作表预先算好）。

## 二、默认替换与类型代号（V31-S-02，GPT-6.1 Sol，high）

### 2.1 代号

| 类别 | 代码 | 代号 | 中性代号（智能助手） |
|-|-|-|-|
| 名称（像机构、人名） | NAME | `[名称_1]` | `[[NAME_1]]` |
| 专有名词（像缩写、术语、型号） | TERM | `[专有名词_1]` | `[[PROPN_1]]` |

加进 `placeholders._NUMBERED` 与 `_NEUTRAL_LABELS`，回程文法自动生效（V31-R 1.2）。长串数字的不确定项用现有 REFNO（`[编号_n]`）。同一任务内同一文字（规范形式）同一代号。

**默认类别**（`suspects.default_category(text, reason)`）：原因为 `long_digits` → REFNO；文字含汉字 → NAME；拉丁字母文字中有 2 个及以上字母的全大写词或含数字的词 → TERM；其余 → NAME。

### 2.2 计算（`engine.compute()`）

疑似识别从 `_assemble` 之后移到之前：

1. 全部规则、词条、签约方、实体识别的替换区间确定后，按现有规则识别疑似（结果仍为 `result.suspects`，即“不确定项清单”）。
2. 新参数 `keeps: Sequence[str]`（原文文字，函数内取规范形式）：规范形式在其中的不确定项**不替换**，仍留在清单中。
3. 其余不确定项按文字去重、取默认类别，在全部节点的未替换文字中按 `P.name_pattern` 找出该文字的每一处（跳过撤销记录的区间；不只是被列出的那一处，否则对照表中的真实值会被出口复检拦截），长者优先加入替换区间，`detected_by="uncertain"`。
4. 再执行 `_assemble`（代号分配、对照表、比例注记不变）。

`SuspectOut` 增加 `category`（默认类别）。`keeps` 为空时，结果与“全部选替换”一致；不确定项被替换后同一位置不会再被列出第二次。

### 2.3 决定（`redaction_suspects.decision` 取值不变，含义改变）

| 值 | 含义 |
|-|-|
| `pending` | 用户未操作：默认替换（术语记忆中有该词时为“按记忆保留”，3.3） |
| `ignore` | 用户选“保留原文”：本任务同文字全部保留（同 V2Q-145） |
| `replace` | 用户指定类别替换：作为用户词条全文替换（现有逻辑） |

* `_run()` 在调用 compute 前组装 `keeps` = 本任务 `ignore` 行的文字 ∪ 术语记忆（3.3）。
* `decide_suspect` 的 `replace` 允许类别 NAME、TERM（手动补充的类别表不变）。
* 新增决定 `reset`：`ignore` → `pending`（改回默认替换）；单条与批量接口都支持。批量接口 `decision` 改为 `ignore | reset`，每次最多 200 组不变。
* `_write_suspects` 中“选了替换却仍被列出就退回 pending”的逻辑保留。

### 2.4 提交条件

删除 `create_run` 的 `SUSPECTS_PENDING` 检查与智能助手确认的同类检查（`assistant/service.py`）。其余条件（我方、文件类型、出口复检预检等）不变。

### 2.5 其他

* `learn_confirmed_names` 不变：只学签约方与用户词条中的 ORG / OUR / PERSON；`uncertain` 项与 NAME、TERM 类别的用户词条都不学。（S-03a 起改为：`uncertain` 项仍不学；用户词条除 AMOUNT 外全部按条件学习，见 12.2。）

## 三、术语记忆（V31-S-03，GPT-6.1 Sol，medium）

### 3.1 表 `keep_terms`（迁移新建）

| 字段 | 说明 |
|-|-|
| id | uuid |
| term\_hash | 规范形式的 SHA-256（与 `engine.term_hash` 相同） |
| term\_enc | 原文文字，主密钥加密 |
| user\_id | 保留过它的用户；为空表示业务管理员认可的公司共享行 |
| approved\_by | 认可人（仅公司共享行） |
| hit\_count、last\_hit\_at | 命中统计 |
| created\_at | |

唯一约束 `(term_hash, user_id)`（user\_id 为空的行另建部分唯一索引）。删除用户时其个人行一并删除。

### 3.2 写入（确认发送时，与 `learn_confirmed_names` 同事务，预检拦截时不写）

本任务 `decision=ignore` 的不确定项中，同时满足以下条件的文字写入本人一行（已存在则跳过）：

* 默认类别为 NAME 或 TERM（长串数字不记）；
* 不含企业后缀、机构后缀（中英文后缀表，与签约方识别同一份）；
* 不是人名结构（`suspects._is_person_name` 为真，或原因为 `person_name` / `person_like`）；
* 规范形式不等于任何启用中的已记住名称、自定义敏感词；
* 去掉首尾空白后 2～50 个字符。

智能助手确认（`assistant.service.confirm`）同样写入。

### 3.3 生效（`engine._run` 组装 `keeps` 时）

对任务所有者生效的词 = 本人行 ∪ 被 2 个及以上不同用户保留过的词 ∪ 公司共享行；使用时再减去当时启用中的已记住名称、自定义敏感词。命中（某不确定项因记忆而保留）时 `hit_count + 1`，只在解析阶段统计（同 `_count_hits`）。

用户把“按记忆保留”的项改为替换（`replace`）时，删除本人对该词的行（公司共享行与他人的行不动）。

### 3.4 管理接口（业务管理员，SPEC 19.7 风格，写审计，审计只记数量与动作）

* `GET /api/v1/admin/keep-terms?q=&page=`：按词聚合列出：文字、保留人数、状态（个人 / 已共享（2 人以上）/ 已认可）、命中次数、最近命中时间。
* `POST /api/v1/admin/keep-terms/{term_hash}/approve`：建公司共享行（认可）。
* `DELETE /api/v1/admin/keep-terms/{term_hash}`：删除该词的全部行。

界面在 V31-U4 的设置“脱敏”一节；确认页“按记忆保留”的显示在 V31-U2。

### 3.5 测试

代表用例 4 条：个人立即生效；两人后共享；带企业后缀与人名结构不写入；已记住名称覆盖记忆（该词照常替换）。

## 四、草稿任务与拖入即解析（V31-S-04，GPT-6.1 Sol，high）

V31Q-02：第一次拖入即建草稿任务并解析，页面不跳走；多次拖入加入同一任务、共用代号并自动重算；文件可删除（5 秒撤销在前端：延迟 5 秒才发删除请求，离开页面时立即发出）；更换主文件自动重算；至少一份解析完成后按钮变为“下一步”，永不自动跳页；确认页也可继续拖入。

### 4.1 状态

`tasks.status` 增加 `draft`（迁移改检查约束）：首页阶段，可增删文件、改主文件；后台解析与脱敏照常进行，但不进入第二步。

| 从 | 动作 | 到 |
|-|-|-|
| — | `POST /tasks`，`draft=true` | draft |
| draft | `POST /tasks/{id}/proceed`，外发策略 ai | awaiting\_confirm |
| draft | `POST /tasks/{id}/proceed`，外发策略 local\_only | completed\_local |

* 不带 `draft` 的 `POST /tasks` 保持现有行为（parsing → awaiting\_confirm / completed\_local），现有测试不改。
* 文件的增删与改主文件只在 `draft` 或 `awaiting_confirm` 且 `latest_run_id` 为空（从未提交过审核）时允许，否则 409 `TASK_STATE_CONFLICT`。
* 保留期：`draft` 与从未提交的 `awaiting_confirm` 同属“未完成”层（`retention._layer_conditions`、`tasks.service._expiry_fields`）。
* 审核历史照常列出草稿；重复文件检查照常（第一次拖入时比较主文件，打开上次的可能是草稿）。

### 4.2 文件解析状态

`task_files` 增加 `parse_error TEXT NULL`（迁移）。文件状态由接口派生：`parse_error` 非空 → `failed`；`parser_version` 非空 → `done`；否则 `parsing`。`TaskFileOut` 增加 `parse_state`、`parse_error`（原因文字，不含原文；文件名由页面自己显示）。`TaskDetail` 增加 `busy: bool`（本任务有 queued / running 的 parse job）。

### 4.3 接口

| 接口 | 规则 |
|-|-|
| `POST /tasks`（multipart，新增表单字段 `draft`，默认 false） | `draft=true` 时：建任务 `draft`，文件 1～10 个，`stance`、`source` 照常必填（首页当前值），`policy` 可选、到 proceed 时为准；入队 `parse`，payload 带全部 `file_ids`；记 `task_create` 审计 |
| `POST /tasks/{id}/files`（multipart `files`） | 合计不超过 10 个；与本任务已有文件 SHA-256 相同的 422 `DUPLICATE_IN_TASK`“该文件已在本任务中”；新文件 `seq` = 现有最大值 + 1（删除后不重新编号，位置编号不变）；入队 `parse`（新文件的 `file_ids`）；返回 `TaskDetail` |
| `DELETE /tasks/{id}/files/{fid}` | 最后一个文件 409 `LAST_FILE`（页面改为删除任务）；删原件与转换件，删该文件的节点、`F{seq}-` 前缀的脱敏项、疑似、撤销记录、实体识别缓存与条款向量；删的是主文件时 `seq` 最小的剩余文件成为主文件并更新标题；入队只重算的 `parse`（`file_ids=[]`）；记 `task_file_delete` 审计（只记数量）；返回 `TaskDetail` |
| `PATCH /tasks/{id}/files/{fid}` | 请求体改为 `doc_type`、`is_main` 二者至少一个：`doc_type` 现有逻辑（允许 draft 与 awaiting\_confirm）；`is_main: true` 设为主文件、标题改为该文件名、入队只重算的 `parse` |
| `POST /tasks/{id}/proceed`，请求体 `{stance, source, policy, user_note}` | 只在 `draft`；至少一个文件 `done`，否则 409 `FILES_NOT_READY`。ai：写入设置与补充说明（补充说明的脱敏同 `patch_task`），按当前设置重算脱敏（4.5），置 `awaiting_confirm`；其余文件仍在解析也可以（确认页显示）。local\_only：要求全部文件 `done` 且不 busy，否则 409 `FILES_NOT_READY`；删除本任务的全部脱敏数据（签约方、脱敏项、对照表、疑似、撤销记录、实体识别缓存、节点的 `redacted_text`、`user_note_redacted`），置 `completed_local` 与 `last_completed_at`。两者都记住用户本次的立场与来源；返回 `TaskDetail` |

全部接口校验 owner\_id（非本人 404），修改类与确认发送共用任务行锁、取锁后重读状态（同 `_lock_awaiting`）。

### 4.4 解析（`pipeline.parse_task` 的草稿分支）

任务状态为 `draft` 或 `awaiting_confirm`、且 payload 带 `file_ids` 键时进入草稿分支（与智能助手分支并列）：

1. 取 payload 中仍存在且未解析的文件；OCR 预算计入本任务其他文件已用的页数（同 `_parse_assistant` 的算法）。
2. 逐个文件在保存点中解析（先删该文件旧节点）：`ParseError` 时回滚该保存点、写 `parse_error`，继续下一个；成功的写节点与解析信息、识别文件类型。
3. 锁任务行并重读：任务已删除、状态已不是 draft / awaiting\_confirm、或已有轮次时放弃（回滚）。
4. 重算（4.5），提交。
5. 意外异常：回滚，把本次的文件写 `parse_error` = 内部错误提示后单独提交，再抛出（job 记 failed）；只重算的 job 失败时任务保留原数据，用户下一次增删文件会再次重算。`jobs.finalize_failed` 对 draft / awaiting\_confirm 的 parse job 做同样的收尾（未解析的文件写内部错误）。

两个 job 同时处理同一任务时，各自解析不加锁，第 3 步起串行；后提交者的重算能看到先提交者的节点，结果完整。

### 4.5 重算（`pipeline.recompute_task(db, task)`，草稿分支、proceed 与只重算的 job 共用）

1. `run_checks`（全部已解析文件）。
2. 脱敏：有 `confirmed` 为真的签约方时沿用签约方设置（同 `apply_party_changes(db, task, [])`），否则 overrides 为 None、按立场重新预选我方；**不删除疑似行**（保留用户的保留 / 替换决定）；样式 review、不固定代号。草稿阶段不论外发策略都计算（只在本机、加密存储，local\_only 在 proceed 时删除）。
3. 条款向量：保存点中重算，失败只记警告（同现有）。

### 4.6 确认发送的新增前置条件（`create_run`）

* `busy` 为真：409 `FILES_PARSING`“还有文件正在解析，请稍候”；
* 有 `failed` 文件：409 `FILE_PARSE_FAILED`“请先删除解析失败的文件”。

### 4.7 测试

代表用例：草稿建任务 → 追加文件 → 两文件共用代号；删除文件后对照表不含仅属于它的名称且原件已删；改主文件后标题与总价比例按新主文件；单个坏文件只标该文件；proceed 两种策略；有轮次后不能增删；非本人 404。

### 6.1 评测（工具放 `backend/scripts/`，不进产品路径）

* 数据：S-01 至 S-05 完成后的 golden 全部样本；标签取 `must_suspect`、`must_replace`（真名称）与 `plain_uncertain`（普通）。

### 12.2 确认替换全量记忆（V31-S-03a，GPT-6.1 Sol，high）

现状：`learn_confirmed_names` 只记签约方主写法与用户词条中的 ORG / OUR / PERSON。用户手动补充或指定替换的项目名称、无标签地址、编号、名称、专有名词下次还会漏；简称和另一种语言的写法也不记。

**写入**（确认发送时，与现有逻辑同一事务；预检拦截时不写；智能助手确认同样写入）：

| 来源 | 写入类别 | 说明 |
|-|-|-|
| 签约方与用户补充的主体：主写法 | ORG / PERSON（现状） | `is_our_party` 规则不变 |
| 同一主体在本任务中的其他写法：中英文名、简称结构（9.3 第 3 步）得到的简称 | 同主体，`alias_of` = 主写法的 `term_hash` | 9.3 第 2 步派生的字号与“主体部分”仍不记（SPEC 9.10 原规则） |
| 用户词条（手动补充、不确定项选“替换”）类别 PROJECT、ADDR、REFNO、ACCOUNT、IDNO、IM、NAME、TERM、CUSTOM | 原类别 | AMOUNT 不记：同一数字在别的文件里另有含义 |

全部满足才写入：

* 去掉首尾空白后 2～100 个字符；纯数字与标点的不足 8 个字符不记（“2023”“10%”）；
* 规范形式不在 `zh_words`、`en_words`、`common_terms`、`plain_terms`、`zh_legal_finance`、`chem_names` 中（常用词全公司共享后会到处误替换）；
* 已存在同 `term_hash` 的已记住名称或自定义敏感词时跳过（`is_our_party` 只升不降，现状）。

用户词条在加入时已通过 TERM\_IN\_PROMPT 检查（`engine` 手动补充路径），不重复检查。

**生效**（第 1 步）：

* 类别 ORG / PERSON 照旧；带 `alias_of` 的行登记为该主写法对象的别名，同一任务中共用一个代号（主写法不在本文件中出现时，别名照样用该对象的代号）。
* 其他类别按手动补充同一类别的路径登记对象、分配代号（地址的国家按 9.4 查找，找不到写“国家未知”）。
* 术语记忆（第三节）的“使用时减去启用中的已记住名称”自然覆盖新增类别；用户在某任务中撤销某个记住项的替换，仍只记入本任务的撤销记录，不删全局行；记错的由业务管理员在设置中删除（列表已显示类别与记录人）。

**迁移**：`redaction_terms.category` 检查约束加 PROJECT、ADDR、REFNO、ACCOUNT、IDNO、IM、NAME、TERM；新列 `alias_of char(64)` 可空。管理接口返回 `alias_of` 对应主写法（解密后），界面在 V31-U4。

**“以后自动替换”勾选**：接口不变（仍立即写自定义敏感词）；确认后已自动记住，确认页是否保留此勾选由 V31-U2 定（建议去掉）。
