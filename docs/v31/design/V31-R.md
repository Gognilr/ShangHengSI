## 一、完整性检查（V31-R-01，GPT-6.1 Sol，high，测试先行）

### 1.1 接口

在 `backend/app/redaction/restore.py` 新增，`restore()` 保持原样不动（智能助手的流式输出依赖它的偏移，见 4.6）：

```python
@dataclass(frozen=True)
class Mark:
    start: int   # 在返回文字中的位置（Python 字符串下标）
    end: int
    kind: str    # "variant" | "unknown" | "shared" | "note"
    raw: str     # 被标出的原样文字；只会是代号写法或系统标记，不含真实值

@dataclass(frozen=True)
class Checked:
    text: str                 # 还原后的文字
    marks: tuple[Mark, ...]   # 按 start 排序，互不重叠
    restored: int             # 换成真实值的处数（含自动修正的变体）
    fixed: int                # 其中属于变体写法、被自动修正的处数
    removed: int              # 删除的比例注记处数（只在 clause=True 时）

def check(text: str | None, mapping: dict[str, str], *, clause: bool = False,
          locations: Mapping[str, str] | None = None) -> Checked: ...
```

* `clause=True` 表示这段文字会写进合同（目前只有 `suggested_text`）。
* `locations`：位置编号 → 可读位置（如“合同.docx 第三条”），由调用方提供（4.1）；为 None 时不替换位置编号。
* 一次扫描完成：先找出全部候选片段，逐个判定，再拼出结果；已换上的真实值不再参与匹配（与 `restore()` 相同）。
* 对照表中带 `#` 的键只用于出口复检，不参与还原（与 `restore()` 相同）。

### 1.2 代号写法

检查函数只认下列写法，称为“代号文法”。类别标签从 `placeholders.py` 导入，不另写一份（V31-S 新增的 `名称`、`专有名词` 加进 `placeholders.py` 后自动生效）：

| 族 | 写法 | 例 |
|-|-|-|
| 主体 | 角色标签 + `_` + 大写字母 | `客户_A`、`[客户_A]`、`收货人_AB` |
| 编号 | 编号标签 + `_` + 可选 `Q` + 数字 | `人员_1`、`[金额_3]`、`[公司_Q2]` |
| 我方 | `[我方]`；旧任务为不带括号的 `我方` | |
| 共用 | `[电话]`、`[邮箱]`、`[网址]`、`[证件号]`、`[邮编]`、`[联系方式]`、`[地址：{国家}]` | |
| 助手 | `[[ORG_1]]`、`[[OUR]]` 等（`placeholders.NEUTRAL`） | |

英文角色名只在下表中列出（不区分大小写），用于识别模型把代号译成英文的写法：

| 中文标签 | 英文写法 |
|-|-|
| 客户 / 供应商 / 买方 / 卖方 | Customer、Client / Supplier、Vendor / Buyer / Seller |
| 收货人 / 通知方 / 受益人 / 银行 / 公司 / 其他 | Consignee / Notify、Notify Party / Beneficiary / Bank / Company / Other |
| 人员 / 项目 / 编号 / 账号 | Person / Project / Ref、No / Account |
| 金额 / 单价 / 数量 / 敏感词 | Amount / Price、Unit Price / Qty、Quantity / Term |

**位置编号**：`F` + 文件序号，后接 1～4 段“`-` + 大写字母 + 数字”，前后不紧挨字母、数字或连字符（与 `app/parsing/` 各解析器生成的 loc 一致，如 `F1-P23`、`F1-T2-R3-C4`、`F2-PG3-B5`、`F1-S1-E8`、`F1-TB2`），可带方括号。

**系统标记**：金额比例注记 `（=合同总价的 {数字}%）`（半角括号也算）；`【主体说明】`；`【报价明细表：…】`（到对应的 `】` 为止）。

### 1.3 判定规则

先归一再查对照表：去掉括号内的空格，全角字母、数字、下划线转半角（NFKC），括号内字母转大写，英文角色名换成中文标签。归一后与对照表的键（新写法或旧写法）一致，才算“对照表中的代号”。

| 模型写出的文字 | 普通字段 | 建议条文（clause=True） |
|-|-|-|
| 对照表中的代号原样：`[客户_A]`、`客户_A`（旧任务）、`[金额_1]` | 还原 | 还原 |
| 带括号的变体：开括号 `[［【〔`、闭括号 `]］】〕` 任意组合；括号内多空格；全角下划线或字母；括号内漏下划线（`[客户A]`）；括号内英文（`[Customer_A]`、`[Customer A]`） | 还原（计 fixed） | 还原（计 fixed） |
| 有下划线、没有括号：`客户＿Ａ`、`金额_1`（方括号代号漏了括号）、`Customer_A`、`Person_1` | 还原（计 fixed） | 还原（计 fixed） |
| 主体代号漏了下划线和括号：`客户A`、`客户 A`、`Customer A`（只在归一后对照表中有此代号时） | 不替换，标 `variant` | 同左 |
| 编号代号漏了下划线和括号：`人员1`、`项目 1`、`编号1`、`Person 1`（只在对照表中有此代号时） | **不替换、不标**（可能是普通词，如“技术人员1名”） | 不替换，标 `variant` |
| 合乎代号文法、对照表中没有：`[客户_C]`、`客户_C`、`[金额_9]`、`[[ORG_7]]` | 不替换，标 `unknown` | 同左 |
| 共用代号：`[电话]`、`[地址：中国]` 等 | 原样，不标 | 原样，标 `shared` |
| 金额比例注记 | 保留 | 删除（计 removed） |
| 位置编号 | `locations` 中有 → 换成可读位置；没有 → 原样，标 `note` | 原样，标 `note` |
| `【主体说明】`、`【报价明细表：…】` | 原样 | 标 `note` |

* **我方**：新任务只认 `[我方]` 及其括号变体；正文里自然出现的“我方”二字是普通词，不替换（顺带解决 V2Q-178 的“我方我方”）。旧任务对照表的键是 `我方`，按原样还原，保持旧行为。
* **助手代号**：只做原样还原和现有的括号变体（与 `restore()` 相同），**不自动修正**；单层括号 `[ORG_1]`、不带括号 `ORG_1`、对照表中没有的 `[[ORG_9]]` 只标出。因此对已结束的助手消息，`check(...).text` 与现有 `incremental(..., finished=True)` 的结果逐字相同（4.6 依赖这一点）。
* 判定不用到上下文语义，不调用模型。

### 1.4 修订是否可写

`check(text, mapping, clause=True)` 返回的 `marks` 为空，才允许把这段文字写成修订（4.5）。

### 1.5 不做

* 不处理日期（日期平移与“未知日期不写入”闸门在 V31-P，届时在本函数加一条规则）。

把 `review/service.py` 中 `_View.locations()` 的“位置 → 可读位置”算法抽成 `_View.readable(locs)`，供问题的第一个位置和文字中出现的位置编号共用；`_View` 增加 `checked(value, *, clause=False)`，内部调用 `check(value, self.mapping, clause=clause, locations=…)`，`locations` 只查文字中实际出现的位置编号。

### 4.2 结果页接口（`GET` 轮次详情）

* `FindingOut` 增加 `marks: dict[str, list[MarkOut]] = {}`（键为字段名：title、problem、impact、suggestion、suggested\_text、basis；只列有标记的字段）和 `unresolved: int = 0`（各字段标记数之和）。`MarkOut` 为 `{start, end, kind}`，位置是返回文字中的 Python 字符串下标（码点），前端按码点切分（V31-U3）。
* `suggested_text` 用 `clause=True` 检查（比例注记删除、共用代号与位置编号标出）；其余字段 `clause=False`。
* `RunDetail` 增加 `doc_summary_marks: list[MarkOut] = []`。覆盖说明中“无法判断”的备注只用 `check().text`，不返回标记。

### 4.3 追问回复

`chat/service.py` 的 `message_out` 对模型回复用 `check()`（`clause=False`，带可读位置），返回增加 `marks: list[MarkOut] = []`；用户消息不检查。

### 4.4 Word 报告与批注版

* **报告**（`report_docx.py`）：问题各字段按 `marks` 把对应文字设为黄色突出显示；有标记的问题在该问题末尾加一行“注：本问题有 N 处文字未能还原（已标黄），请核对。”
* **批注版**（`annotated_docx.py`）：有标记的问题在批注末尾加一行“※ 有 N 处文字未能还原（如“客户A”），请核对。”，举例取前 3 个不同的 `raw`。

两者都从 `run_detail` 取已检查的文字与标记，不再自行还原。

### 4.5 修订版闸门

`revised_docx.py` 删去 `_CODES` 正则。建议条文按库中原值做 `check(raw.suggested_text, mapping, clause=True)`：

* `marks` 非空 → 不写修订，转批注（首行仍为“【未能写成修订，请人工修改】”，并带 4.4 的“未能还原”一行）；
* 否则用 `check().text`（比例注记已删除）参与原有的定位与写入规则，其余规则不变。

引用（quote）仍用 `restore()` 还原后精确定位，不变。

### 4.6 智能助手（只标出）

`assistant/service.py` 的 `message_out`：对已结束（非 queued / streaming）的助手消息，按其对照表计算 `check(content_redacted, neutral).marks`，返回增加 `marks: list[MarkOut] = []`；`content` 仍用现有的 `incremental()` 生成，流式接口 `get_delta` 不变。测试断言两者文字相同（1.6）。翻译、比对等模板的附加结果不检查。

### 4.7 测试
