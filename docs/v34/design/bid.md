# V3.4 设计：标书初审

状态：**草案，待用户确认**（2026-11-15，Opus 起草）。来源：与用户的讨论（docs/v34/open_questions.md V34Q-01～10）与分析 docs/proposals/商衡SI-标书初审与导航设计分析-2026-11-15.md（下称“分析”）。页面的视觉以 docs/v34/design/visual.md 为准，本文只写功能、数据与处理。

## 一、定位与边界

* 公司作为**招标方**，企业自主招标、邀请招标（设备、物资、服务），每次 3～5 家投标，每家几十到几百页；开标当天由采购部、招标办员工使用，结果是一份交给评标委员会的《初审疑点报告》（评委不登录）。
* 只做**资格审查、符合性审查、串标线索**三件事。不打分、不推荐中标人；投标人按录入顺序排列、不提供按价格排序，报价只在总价旁标“最高”“最低”并给出差额（V34Q-27）；界面与报告不出现“第一名”“推荐”“中标”“合格”“通过”；结论一律写“疑似”“线索”“未找到”，每条附依据（招标文件出处 + 投标文件位置）。
* 串标线索按《招标投标法实施条例》第四十条六种情形归类，否决情形参照第五十一条；企业自主招标未必属依法必须招标项目，条文作“参照依据”写入报告，最终以招标文件约定为准。条文入库前对照法规库原文核对。
* **一次设计、整体实施**（V34Q-02），不分期；任务在 V3.4 内排序。
* 不做：印章 / 签名图像识别（改“签章页速览”人工核对）；目录结构比对；外部工商、股权、制裁数据；评委在线评审；项目内自由追问与多轮重审（需要追问时用工作台）。

## 二、用户流程

项目页顶部四步条（可点击回看，不自动跳页）：**招标文件与要求 → 投标文件 → 初审结果 → 导出**。

```
开标前（可提前数日，约 10 分钟）          开标当天
① 新建项目、上传招标文件            ③ 按投标人分组拖入投标文件（带密码的 PDF 输入密码）
② 确认关键参数与要求清单 → 待开标   ④ 本地检查（几分钟）→ 总览先出
                                  ⑤ 确认将发送的片段 → 模型核对（随后补上）
                                  ⑥ 逐条核对、标注 → 导出 Word 报告
```

没有提前准备也能当天从 ① 做到 ⑥。项目外发策略可选“只做本地检查”：② 只用规则抽取加人工补充，⑤ 不做，其余照常。

### 2.1 首页 `/bid`

一句说明（“招标文件与各家投标文件在本机比对，找出不符合项与串标线索；不打分、不推荐。”）、“新建初审项目”、最近的项目（名称、阶段与进度、时间），右上一句“只是比较几份报价单？用工作台的‘比价’”。

### 2.2 第 1 步：招标文件与要求清单

* 项目名称、开标日期（默认今天，用于有效期比较）、外发策略。
* 招标文件：Word 或 PDF，可多份（正文 + 答疑、补遗、澄清，最多 5 份）；后发的澄清改动原要求，清单以最新为准并标出出处。招标文件走现有解析与确认脱敏流程（是本公司文件，可整份脱敏）。
* **关键参数**小表单（系统预填、用户改正，驱动本地确定性检查）：最高限价（含币种，Decimal）、投标有效期（天）、保证金金额与形式、是否接受联合体、报价币种与是否含税。
* **要求清单**：左为招标文件原文画布（复用现有画布），右为清单。分组：资格条件 / 实质性条款（★）/ 否决条款 / 报价要求 / 有效期与保证金 / 签章与格式页 / “投标文件格式”章节范围（作范本白名单）。每行：要求文字（可改）、出处（点击定位）、检查方式（本地规则 / 模型判断 / 人工核对）、启用开关、来源标记（原文标记 / 模型提取 · 请核对 / 默认（第五十一条）/ 手工）。
* **快速确认**：
  1. 规则先行：★▲ 标记、含“否决 / 废标 / 无效投标 / 不予受理 / 必须 / 不得 / 应当”的句子、“投标人须知前附表”“评标办法”“投标文件格式”等章节，本地直接抓出。
  2. 模型补充：脱敏后的招标文件发模型做归并、分类、补漏（只做抽取，不做判断）；“只做本地检查”时跳过。
  3. 完整性计数器置顶：“原文 ★ 共 23 处，已全部进入清单”“含否决字样的句子 17 处，已进入 15，未进入 2（查看）”，用户只处理差额。
  4. 默认全部启用，用户删错的；J / K 上下、X 停用、E 改文字；原文划选 →“加入要求清单”。
  5. 第五十一条否决情形作为默认行列出（未盖章签字、不符合资格条件、两份以上不同报价、超最高限价、未响应实质性要求等），可关掉。
* 确认后项目为“待开标”。开标后改清单只重跑受影响的行。

### 2.3 第 2 步：投标文件

* 每个投标人一张卡片：名称（必填；封面、投标函中识别到的名称作为建议）+ 文件列表。可把多家的文件夹一起拖入，按文件夹名自动分组建卡（建卡前名称可改），也可逐卡拖入。不要求标注商务标 / 技术标 / 报价表，系统按内容自己认报价表（SPEC 10.1）。
* **带密码的 PDF**（V34Q-03）：上传后检测到加密，文件行显示“需要密码”和输入框；密码错误提示“密码不对，请核对投标方提供的密码”。密码用主密钥 AES-256-GCM 加密保存，重新解析不再询问；本人可在文件行查看（默认遮盖，点“显示”）。日志、导出报告不写密码。
* 限制（V34Q-10，可在计划确认时改）：投标文件每项目最多 20 个（招标文件另计，最多 5 个）；单文件 100 MB；单个 PDF 600 页；每项目 OCR 合计 500 页；同一时间只解析一个标书项目。
* 至少 2 家才做串标比对；只有 1 家时只出符合性检查。主按钮“开始初审”。

### 2.4 第 3 步：初审结果

顶部状态条：`本地检查 已完成 · 扫描页识别 312 / 500 · 模型核对 3 / 5 家`。五个页签：

1. **总览**（默认，一屏）：每家一行——疑似否决项、其他问题、待人工核对、报价（总价与和最高限价的关系）、涉及串标线索（强 / 中）；下方串标线索计数与两两关系（甲–乙 强1 中1…）；**覆盖说明**写清未解析、低置信、未比对的范围（避免“没报问题”被当成“没有问题”）。每个数字可点，跳到对应页签并筛选好。
2. **要求响应矩阵**：行为要求（★ 与否决条款在前），列为投标人，首列固定；单元格四种：响应 ✓、疑似不响应 ✕、未找到 ？、人工核对 —；本地规则与模型判断用不同底纹。“只看有问题的行”默认开。点单元格在右侧抽屉看：要求原文与出处、该家对应片段（可跳原件页）、判断理由、核对状态与备注。
3. **各投标人**：每家一份问题清单（沿用问题卡片，等级为“疑似否决项 / 一般问题 / 提示”）；分区“签章页速览”：把要求盖章签字的格式页（投标函、授权委托书、报价表、承诺函……）逐张缩略图排开，人工标“已盖章 / 缺章 / 看不清”。
4. **串标线索**：按强 / 中 / 弱分组，卡片写涉及哪几家、类型、对应第四十条第几项、证据摘要；展开为**左右并排对照**（两家原文并列，相同文字高亮；属性类为两列属性表；图片类并排两图）。“正常重复”（招标范本、厂家资料）单独一组、默认折叠。
5. **报价分析**：各家总价旁标“最高”“最低”，列“比最低价高”（金额与百分比）、“偏离平均”；低于其余各家平均 20% 以上提示异常低价（参照第五十一条（五），阈值 B-08 校准）；三家及以上总价等差 / 等比记第四十条（四）线索；分项对齐表、合计与大小写核对、两两分项比值及离散程度。只有唯一总价的投标人参加比较；未填最高限价时不显示任何限价内容，填了才有“与限价”差额。仍按录入顺序排列，不提供按价格排序（V34Q-27）。

每条问题与线索有核对状态“待核对 / 已核实 / 已排除”与备注（乐观更新，失败回滚）。否决性结论须人工点“已核实”才以肯定语气进报告。

### 2.5 第 4 步：导出（Word，服务器内存生成、不留存）

1. 封面与说明：项目名称、开标日期、初审人、生成时间；方法说明（本机比对 + 脱敏后模型核对、模型名称、清单版本）；固定声明“本报告为初审线索，不构成对串通投标或否决投标的认定，由评标委员会核实后决定”。
2. 总览表与覆盖说明。
3. 要求响应矩阵（只列有问题的行，完整矩阵作附录）。
4. 各投标人问题清单（出处、位置、原文摘录、说明、核对状态与备注）。
5. 串标线索（强中弱，两家原文对照摘录、对应条文）。
6. 报价分析表。
7. 附录：要求清单全文、文件清单与属性、签章页核对结果；末尾“初审人 / 复核人 / 日期”签字栏。

“已排除”的条目不进正文。投标人用真实名称（本地还原）。另提供“只导出串标线索”。

## 三、处理过程

### 3.1 A 段：本地检查（不调用模型，目标几分钟内出总览）

顺序按“先出结果的先做”：文字页解析 → 文件属性与图片哈希 → 规则识别的联系信息交叉 → 报价表计算 → 确定性符合项 → 相似段落 → 向量写入；扫描页 OCR 后台排队，做完一页补一页，相关检查显示“扫描页识别中 n / N”。

**基线剔除（最重要的误报来源）**：各家都从招标文件 Word 里复制格式页，修订会话标识（rsid）、样式、作者、图片、段落会一起带过去。凡在招标文件中出现过的 rsid、图片哈希、句子，一律先剔除；招标人、招标代理的名称、电话、账号等也加入白名单。

| 检查 | 做法 | 第四十条 | 分级 |
|-|-|-|-|
| 混装 | 甲的文件里出现乙的名称（卡片名称及识别到的简称）、乙的联系人或乙的封面 / 印章页 | （五） | 强 |
| 联系信息相同 | 复用脱敏的规则识别器（`redaction/detect.py` 的 `find_formatted`、带标签的 `find_persons`），取电话、邮箱、银行账号、证件号、地址及“项目经理 / 联系人 / 授权代表”等带标签人名；归一化后在 ≥ 2 家间重复、且不在白名单 | （一）（二）（三）（六） | 账号、证件号、电话、邮箱、项目经理相同为强；地址、联系人为中 |
| 文件属性 | Word：core.xml 作者、最后保存者，app.xml 公司、模板，settings.xml 的 rsid 集合；PDF：trailer /ID 第一项、XMP DocumentID / OriginalDocumentID、Producer / Creator、创建与修改时间 | （一） | PDF 原始文件标识或 XMP 文档标识相同、作者相同且非招标方为强；剔除招标文件后 rsid 重合为中；生成软件相同且创建时间 10 分钟内为弱 |
| 相同图片 | Word 媒体文件、PDF 图片对象的字节 sha256；剔除招标文件中的图片 | （一）（四） | 印章、签名、授权书、业绩合同页为中；所在页含“检测报告 / 产品彩页 / 说明书 / 认证证书”等厂家资料字样的归“正常重复” |
| 相似段落 | 句级归一化（复用 `redaction/normalize.py`）；先剔除与招标文件（含“投标文件格式”章节）完全一致或二元组 Dice ≥ 0.9 的句子、20 字以下的句子与法条引文；再在各家间找完全相同句与 Dice ≥ 0.85 的近似句，相邻命中合并为段 | （四） | 自写部分连续相同 ≥ 200 字、或只有两家共有的完全相同句 ≥ 5 处为强；其余长段相似为中；技术参数章节降一档（同一厂家产品参数本就相同），报价章节升一档 |
| 报价规律 | 识别报价表（SPEC 10.1）；分项按品名规格归一化对齐（B 段可用模型对齐，同比价）；两两计算分项单价比值，比值的变异系数 < 0.5% 且 ≥ 5 项，或呈等差、同一尾数习惯；三家及以上总价从低到高等差（相邻差额之差 ≤ 1 元）或等比（相邻比值之差 ≤ 0.00005）；Decimal（ROUND_HALF_UP） | （四） | 比值恒定为强，其余为中（总价规律为中） |
| 确定性符合项 | 报价大小写一致、分项合计与总价、出现两个以上不同总价、超最高限价；投标有效期天数、保证金金额与关键参数比较；证书“有效期至”早于开标日（OCR 置信度低时只提示人工核对）；复用 L-01、L-02、L-04、L-14 的计算 | 第五十一条相应情形 | 疑似否决项 / 一般问题 |
| 写给 AI 的指令 | 复用 L-21；投标文件中出现即为一条疑点 | — | 提示 |

正常原因提示：每条线索附“常见的正常原因”（同一代理机构的模板、同一厂家资料、招标范本），由人判断。

### 3.2 B 段：模型核对（随后补上，可关闭）

* 对每家、每条“模型判断”类要求：用 bge-m3 向量加关键词检索该家最相关的 2～3 个片段（向量写入 `task_clause_vectors`，按 file_seq 区分投标人），连同要求原文发模型，返回“响应 / 疑似不响应 / 未找到 / 无法判断”与所引片段位置；偏离表对应行一并给出，偏离表与正文矛盾在同一次判断中报出。引用校验沿用 SPEC 11（quote 校验，不符记“待核实”）。
* 一家的若干条要求合并为一次调用，一个项目约 25～40 次；全部经模型网关（上限 → 出口复检 → 发送 → llm_calls，purpose 新增 `bid`），不新增外发路径。开始前确认页写明“本次约 n 次调用，本月剩余 x 次”，不足不开始。
* **只对待发送片段做完整脱敏**：全文 60 万字跑实体识别要 15～30 分钟以上，不可行。检索出的片段去重后（约 10 万字）跑完整脱敏（规则 + 实体识别 + 词条），投标人名称在建卡时作为词条，必替换为 [投标人A]、[投标人B]……；不确定项按现行规则默认替换。可在用户看 A 段结果时后台进行。
* **片段模式确认**：只显示将发送的片段，按投标人分页签，可切 AI 视野；回执“将发送 n 个片段、约 m 字，已在本机保护 k 处；不发送：原件、图片、报价金额、文件名”。一个按钮“确认并开始模型核对”。确认时后端重新生成并复检。
* 模型只看到代号，不知道哪家是哪家——写入报告的方法说明（客观上也是“盲审”）。
* B 段失败只影响“模型判断”类单元格，显示“未核对”；A 段结果与报告始终可用。

## 四、数据结构（Alembic 迁移，实施时细化）

* `tasks.kind` 增加 `bid`；标书项目复用任务的 owner、存储、doc_nodes、对照表、保留期与删除。
* 新表 `bid_projects`（task_id 主键）：开标日期、阶段（preparing / ready / checking / checked）、关键参数（加密）、清单版本、外发策略沿用 tasks.policy。
* 新表 `bid_bidders`：task_id、序号、名称（加密）、代号字母。
* `task_files` 增加：`bidder_id`（空 = 招标文件）、`password_enc`、`meta_enc`（文件属性 JSON，加密）。
* 新表 `bid_requirements`：分组、文字（加密）与脱敏文字、出处 locs、检查方式、启用、来源、排序。
* 新表 `bid_items`：问题与线索统一存放——种类（issue / clue / normal_dup）、涉及投标人数组、关联要求、类型、等级、条文项、证据（locs 与摘录，加密）、来源（local / model）、核对状态、备注（加密）。
* 新表 `bid_cells`：要求 × 投标人的判断（结论、locs、理由加密、来源、核对状态）。
* 新表 `bid_images`：file_id、页码、sha256、尺寸、类别（只存哈希，不另存图片）。
* 报价对齐与计算结果存 `bid_projects` 的加密 JSON 字段，展示时本地计算。

## 五、与现有系统的衔接

* **侧栏与入口**：独立菜单“标书初审”（V34Q-01），归“文件审查”组；工作台入口卡片；全局搜索加“新建标书初审”与项目；历史记录合并列表加类型“标书初审”并可筛选。
* **权限**：新增 `use.bid`（“标书初审”，组“使用”），默认不给普通用户（V34Q-04）；导出另需 `use.export`；接口校验 owner，非本人 404。
* **解析**：`parsing/pdf.py` 的 `_open` 支持密码（pdfplumber / pypdfium2 均可传密码）；解析时顺带读取文件属性与图片哈希。PDF 页数、OCR 上限按标书项目单独的配置。
* **安全**：日志不写投标人名称、报价、密码；导出在内存生成；原件不改。
* **技术栈**：不新增依赖与模型；参考开源项目只借思路，不拷代码（youmeng-bid-tools 许可证不明，OpenBidKit 为 AGPL）。

## 六、测试（少量代表性）
