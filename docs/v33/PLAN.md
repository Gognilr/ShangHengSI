## 一、A 批：发布改进

### V33-A-01 构建脚本自动找 Python（V33Q-01）

* **文件：** deploy/scripts/build_release.sh；docs/ops/运维说明.md 第 13 节“构建机需……Python 3.11+（命令 `python3`）”一句。
* **做法：**
  1. 依次试 `python3`、`python`、`py -3`，第一个能执行 `-c 'import sys; sys.exit(sys.version_info < (3, 11))'` 并返回 0 的就用它。只看“能不能真跑”，应用商店占位程序执行失败，自然跳过；不查注册表、不猜安装路径。
  2. 允许用环境变量 `PYTHON=<命令>` 指定，指定了就只用它，不可用即报错。
  3. 都不可用时报错，写明试过哪几个命令、需要 3.11 以上；`require_cmd` 中去掉 `python3`。
  4. 运维说明改为“Python 3.11+（自动在 python3、python、py -3 中查找，也可用 PYTHON 指定）”。
* **验收：** 本机 Git Bash（`python3` 是占位程序）不加任何临时函数，`build_release.sh` 能越过模型校验一步（用 `--models` 指向离线目录，跑到第一个 `docker build` 即可中止）；`PYTHON=nope` 时报错文字正确。不加测试，不跑全量。

### V33-A-02 增量升级包（V33Q-02）

* **文件：** deploy/scripts/build_release.sh、lib.sh（`load_release_images` 与新函数）、upgrade.sh、install.sh；docs/ops/运维说明.md（升级与构建两节）。SPEC 20.5 的改动写进报告，由 Z 合并。
* **判断哪些镜像要重建：按源码，不按镜像 ID。** Docker 构建不可复现，同一份源码在缓存清掉后重建会得到新的 ID；按源码判断结果确定，也省掉不变镜像的构建与冒烟时间。
  * 每个镜像对应一个构建目录：backend → `backend/`，web → `frontend/`，converter → `converter/`，db → `deploy/db/`，transcriber → `transcriber/`，translator → `translator/`。模型文件不进仓库，但 MANIFEST 在目录里，模型一换 MANIFEST 必变，因此也被覆盖。
  * `git diff --quiet v<基准版本> HEAD -- <目录>` 无差异的沿用，有差异的重建。backend/tests 的改动也会触发重建，宁多勿漏。
* **构建：** 新参数 `--base <上一版发布包目录>`，读其中的 `VERSION` 与 `images/images.txt`；要求本地有标签 `v<基准版本>`。不给 `--base` 时与现在一样打完整包。
  * 沿用的镜像不构建、不冒烟，写入新文件 `images/reuse.txt`，每行“镜像名 基准版本 镜像 ID”（ID 取自基准包的 images.txt）。
  * 重建的镜像照常冒烟，写入 images.txt 和镜像 tar。
  * 包名写成 `aireview-3.3.0-from-3.2.1.tar.gz`，一看就知道是增量包；VERSION 仍是 3.3.0。reuse.txt 由 SHA256SUMS 覆盖。
  * 没有一个镜像需要重建时也照样出包（只有部署文件变化）。
* **升级：**
  1. 前置检查阶段（快照确认与备份之前）逐行核对 reuse.txt：服务器上必须有该镜像 ID。缺任何一个就停下，提示“此增量包需要服务器上已有 3.2.1 的 converter 镜像（ID 前 12 位）；请改用完整包”，不备份、不改任何文件。
  2. 导入 tar 后，对沿用的镜像执行 `docker tag <镜像 ID> aireview-<名>:<新版本>`。
  3. 按本次启用的 profile 核对全部所需镜像都在（顺手补上现在只查四个主线镜像、不查 transcriber / translator 的缺口）。
  * 只按 ID 判断，不要求已装版本恰好等于基准版本：只要那份镜像还在，从 3.2.1 升过 3.3.0-rc1 的服务器同样能用 3.2.1 基准的增量包。
* **安装：** install.sh 发现 reuse.txt 非空即拒绝，提示“增量包只能用于升级，全新安装请用完整包”。
* **运维说明：**
  * 构建一节加 `--base` 用法与包名规则。
  * 升级一节说明两种包的区别，以及增量包缺镜像时的提示。
  * 清理旧版本时用 `docker rmi aireview-xxx:旧版本` 只删标签；沿用的镜像带着新版本标签，不会被删。不要用 `docker image prune -a`。
* **验收：**
  1. 本机以 3.2.1 包为基准、按当前 main 构建 `3.3.0-rc1` 增量包，核对 reuse.txt 与实际差异一致，记录包大小。
  2. 服务器（未正式启用，可直接做）由 3.2.1 升到 3.3.0-rc1：沿用的镜像打上新标签，HTTPS 200、未登录 401、数据计数不变。
  3. 在服务器上对增量包跑 install.sh，确认被拒绝。
  4. 再构建一次完整包（不给 `--base`），确认与现在的产物一致。
  * 结果交用户后再往下做。

## 二、B 批：V3.2.1 遗留验证

### V33-B-01 会议纪要旧数据兼容验证（V33Q-03）

* **背景：** 会议纪要后端（assistant/meeting.py）从 3.1.0 起没改过，但它经过的共用路径改动很多：会话接口、`message_out` 新增的 sources / cites、脱敏引擎、0040～0043 迁移、E-08 的会议只读放行。V321-Z 因为没有录音样本，没有验证。
* **录音：** 用本机 Windows 自带的中文语音（Microsoft Huihui）把一段虚构的会议对话合成 wav，约 1～2 分钟，用 SSML 调语速、音高分出两位“发言人”。人名、公司名、金额全部虚构。录音放仓库外的临时目录，不进仓库；合成脚本也不进仓库，报告里写清做法即可。
* **做法：** 本机在仓库外 clone 两份，不碰开发用的 compose 项目。
  1. 在 `v3.1.0` 标签（或 3.1.1 补丁 d619a09）上，用独立的 compose 项目名和端口、启用 asr、接 `backend/tools/mock_llm_server.py` 模拟模型，整套起来。
  2. 造旧数据：上传录音 → 转写 → 改发言人名 → 生成纪要 → 追问一轮 → 导出 Word。另造一个转写到一半就删除的会议。
  3. 换成 main 的镜像，在同一数据卷上启动（迁移自动执行）。
  4. 逐项打开旧会议，检查：转写全文与发言人、纪要正文、追问历史（含依据行不报错）、再追问一轮、导出 Word、删除会议；历史记录与全局搜索里能看到、能打开；他人账号打开返回 404。再新建一个会议，从头走一遍。
* **修正：** 发现问题就地修，只改会议纪要相关文件（assistant/meeting.py、assistant/router.py 中的会议分支、Meeting.vue 及其组件）。涉及共用路径的停下报告。
* **验收：** 报告列出上面每一项是否通过；有修正时补一条代表性用例，放进现有的会议测试文件。走查后删除两份 clone 的容器与数据卷。

### V33-B-02 真实模型下的回复依据锚点（V33Q-04）

* **背景：** E-13 让模型在回复里写 `[F1-P12]`、`[KB1]`、`[H1]` 和法条，本地只认登记过的编号，再换成可定位的锚点；当时只用了模拟回复，真实模型会不会照写、会不会写成变体都没看过。
* **样本：** 全部虚构。用 fixtures 里的虚构合同建一个工作台会话；准备两段虚构的知识库片段、一份虚构的本人历史合同；再做一次审核，拿到带法条依据的问题。
* **调用计划：** 约 12～16 次。
  * 直接问答 5 次：问条款内容、问两处是否矛盾、要求引用原文。
  * 带知识库的问答 3 次，带历史合同的问答 2 次。
  * 按问题讨论 2～3 个问题，含法条依据。
  * 同一问题可重问一次，看稳定性。
  * 开工前把次数告诉用户，由用户自己在本机设置页录入密钥。
* **统计：** 写成计数表，不贴回复原文。
  1. 应带引用的回复中，至少一处锚点能定位的比例。
  2. 写出、但没有被识别的变体写法，例如 `【F1-P3】`、`[F1-P3、P5]`、`F1-P3` 不带括号、`[KB 1]`、法条写简称。
  3. 定位错的锚点：编号能识别，但指到的段落与回复内容无关（人工抽查）。
  4. 未登记编号（如 `[KB7]`）是否仍按原文显示。
* **改进（只在数字不好时做）：**
  * 变体写法集中的，在 assistant/sources.py 放宽识别，仍只认本条回复登记过的编号和本会话存在的 loc。
  * 模型不爱写编号的，改 resources/prompts/assistant.md 第 8 条的说明文字，提示词版本号加一。
  * 两者都不增加外发数据，出口复检不变。
  * 改后只重跑没过的那几项。
* **达标：** 第 1 项不低于 80%；第 3 项为 0；第 4 项全部按原文显示。未达标时把数字交用户决定。
* **验收：** 报告给出计数、改了什么、调用次数；有修正时在 test_assistant_history 补一条变体写法的代表性用例。

### V33-B-03 统一的“页面不存在”页（V33Q-05，用户 2026-11-15 确认做）

* **现状：** 前端未知路径直接跳回首页、不提示。打开不存在、已删除或他人的任务 / 会话时，各页就地显示“不存在或已被删除”，不区分他人与不存在，这一做法保持不变。
* **建议做，只管未知路径。** 输错的地址、收藏夹里已经移除的旧页面地址，现在会悄悄跳回首页，用户不知道发生了什么。
* **方案：** 这是新增页面，确认本计划即确认此方案；不做则 Q-05 记为“不加”、关闭。
  * 未知路径在主框架内（侧栏照常显示）打开一个“页面不存在”页：标题“页面不存在”，一句“地址可能输错了，或这个页面已经移除。”，主按钮“回到工作台”。
  * 不回显地址、不加插图，用现有空状态样式。
  * 未登录时仍先去登录页，登录后再显示此页。
  * 不加侧栏菜单，不改各页就地的“不存在或已被删除”。
* **文件：** frontend/src/router/index.ts（catch-all 由 redirect 改为该页）、新增 frontend/src/views/NotFound.vue。
* **验收：** 按 frontend.md 自检；浏览器走 http://localhost:5173：打开 `/abc` 显示该页并能回到工作台；打开随机 id 的会话仍是就地提示；`npm run build` 通过。
