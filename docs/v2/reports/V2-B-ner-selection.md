## 样本、计分与阈值

[samples.json](ner-selection/samples.json) 为推理前固定的 8 份虚构叙述：6 份中文、2 份英文，包含函件、会议纪要、索赔、法律文书、交接和邮件。每份标注 2 人名、2 机构、1 地址，共 40 个实体。前四份校准、后四份留出，各有 16 个核心 PERSON / ORG；样本 SHA-256 为 `e775e7890b555c305880130a4279790bc3203a2c7773fa045c866daee81e91d8`，未按预测修改。

使用本基线真实 `compute` 先运行规则，再以等长空格遮盖已替换区间，只将剩余文字传给模型。现有全部 golden（含本批四份新增样本）加上述叙述共 391 个节点，残余 PERSON / ORG 共 45 个；核心叙述分母 32 个。完全被规则覆盖的实体不重复计数；部分规则重叠的实体单列 `partial_rule_overlap`，不混入完整残余实体分母。8 个叙述地址中只有 2 个属于完整残余，其他已被规则完全或部分覆盖；地址单列，不以其结果冒充人名 / 机构名门槛。

严格召回要求类别、起点、终点三者相同；扩大区间包含真实实体只计覆盖率，不算严格命中。golden 的数字账号疑似不计入 NER 指标；人名原因映射 PERSON，其他名称疑似映射 ORG。`must_keep` 所有出现位置均纳入，任何区间与高置信预测重叠即计误替换；既有文本、标注均未修改。最后核对时去掉了评测脚本中“位于应替换实体内的保留片段排除”条件，恢复 quotation 的 Germany 一处保留标注；模型输入与实体分母完全不变，对同一原始预测重新计分，所有门槛结论不变。具体映射可在 `prepare_corpus.py` 和 corpus 复核。

中阈值仅在校准部分按固定网格选择满足严格召回 ≥90% 的最高阈值；无阈值满足时以 0.01 展示诊断数据，同时标记 `calibration_medium_satisfied=false`，**不得作为可用推荐阈值**。高阈值在校准 + golden 的保留项上选 ≥max(0.9, 中阈值) 的最低零重叠阈值；留出部分独立计分，不反调阈值。分词策略之间的比较属于探索性模型选择，8 份样本规模有限，后续正式验收还需新的留出样本。

## 导出正确性与限制

BERT 从本地 safetensors 导出 opset17；动态 INT8 采用 QInt8、per-channel、reduce-range。实体分数取 BIO 实体各 token 的最低概率；LOC 暂映射 ADDR，不能把城市自动等同于完整地址，全部保留项仍检查。384 token 窗、48 token 重叠。

GLiNER 使用官方 0.2.24 的 ONNX 导出接口，opset19，默认动态 QUInt8；详见[官方导出示例](https://github.com/urchade/GLiNER/blob/v0.2.24/examples/convert_to_onnx.ipynb)。标签固定 person / organization / street address；320 字符窗、步长 288。默认空白预切分会把中文长片段当作一个词，另测中文逐字、拉丁词、标点预切分。

原始 GLiNER PyTorch 与 FP32 ONNX 在三句独立诊断上相符（概率差约 10^-6）；独立 strict=True 加载通过。最初实际导出沿用默认非严格加载，后以 strict 检查补证，最终脚本已显式 strict=True；不隐瞒此顺序。中文默认预切分在两种 FP32 引擎上都可产生整句人名；INT8 对 `Nora Vale` 改判 ORG、机构分数大幅下降，表明本次默认量化有严重退化。三句对照不足以证明所有输入数值一致，但足以否定“FP32 结果差完全由 ONNX 导出损坏造成”的判断；也不能把默认 INT8 的坏结果当作原始 GLiNER 的准确率。

导出时有 trace / LSTM、部分节点未量化等警告；分词器有 byte-fallback 转换、无最大长度和通用 regex 提示。日志保留，未将其描述为无警告通过。最初 BERT 导出因 onnx 量化模块缺 ml_dtypes 失败（export-bert.exit=1）；补齐 onnx1.19.1、ml_dtypes0.5.3 后 export-bert-repair.exit=0。最终 pip check 成功。

评测环境 Python3.12、CPU PyTorch2.5.1+cpu、GLiNER0.2.24、Transformers4.57.3、ONNX1.19.1，完整版本见 audit。GLiNER 的 ONNX 包装仍导入 Torch / Transformers 做前后处理，其内存与镜像开销已经计入；“移除 Torch 或更换量化就能通过”尚无实测依据。运行脚本显式关闭 ORT 遥测并使用离线环境变量；候选非 root smoke 出现不能持久化 telemetry device ID 的提示，network none 仍阻断全部外联。

Docker Desktop 分配 16 CPU、约 16.61 GB 内存；每个测量容器限制 2 CPU 时间配额、ORT 2 个计算线程 / 1 个跨算子线程，未独占物理核，未设内存硬上限，以进程峰值 RSS 减导入前基线衡量内存增长。开发机后台环境可能影响耗时，**不是 101 或正式机器验收**。没有调用真实云端模型；这些是公开本地 NER 权重实测，不是业务合同试审。

## 用户补充硬件与资源门槛审议

用户提供拟运行硬件：**28 vCPU（2 sockets × 14 cores）、38 GiB 内存、balloon 下限 16 GiB**，并选择“先补测多核表现，由 Opus 提出适合该硬件的新门槛供我确认”。因此后续优先评估已达到召回要求的 GLiNER FP32，而不是因体积直接换成当前低召回 BERT。此决定授权补测和提出新门槛，不等于已批准具体资源上限或接入模型。

用户进一步明确：选型要结合系统功能的完善程度与服务器承载力，不为轻量化牺牲软件功能表现。按此要求，模型体积不作唯一淘汰依据；应以完整业务链的识别缺口、用户确认 / 出口复检、实际处理时延与并发容量共同验收。31/32 不是功能零遗漏：剩余人名与两个完整残余地址仍需处理，B-08 的完整安全链及回归漏掉数要求不能由本轮召回率代替。

2.280 GB 增量约为 2.124 GiB / 进程；若 worker 与两个 app 进程均加载，单按该增量粗算约 6.37 GiB，尚未计进程原有内存、数据库、OCR、解析并发及系统服务。该估算不是实测总容量；需分别按 38 GiB 正常状态和 balloon 16 GiB 下限验收。也不能用 28/2 比例线性推算 15.90 秒会降低到多少，单条推理的可并行部分有限。

开发机 Docker 只有 16 CPU，补测采用同一 FP32 ONNX、同一 10,000 字输入，分别分配 2 / 8 / 14 CPU 配额，ORT 线程数同步调整；补测还显式设置 Torch 线程数及跨算子线程 1（原门槛测量未显式设置 Torch 线程）。因此这是新的诊断组，与原门槛表分别记录。未连接目标主机，也没有伪造 28 CPU 的测量。

这组数据说明当前逐窗推理不能靠增加核心线性提速；8 线程为本机后续验证的优先候选，14 线程没有进一步收益。目标机 28 vCPU、双 socket / NUMA 拓扑与本机不同，不能从这里推算目标时延。建议 Opus 为测试环境制定完整容量场景：两个解析任务并行、同时追问、app 两个进程均已加载、OCR / 数据库同时工作；统一核算所有模型调用的 CPU 预算，并测请求排队、峰值总内存和 balloon 16 GiB 下是否出现交换 / OOM。现有 worker / app 的并发限制不得擅自放大。

当前工程判断是**保留 GLiNER FP32 继续验证资源适配**，而不是仅按 2 vCPU / 1 GB 原限制淘汰；尚不能承诺服务器承载通过。新的耗时、内存与镜像门槛应由 Opus 基于完整场景提出，用户确认后再更新设计及接入许可。
