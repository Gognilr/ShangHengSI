## 一、法规库（E1～E3）

### 1.1 数据来源

国家法律法规数据库（flk.npc.gov.cn，全国人大运营）2025-08 升级后：

* 每部法规标明时效性：尚未生效、有效、已修改、已废止，可按类别、制定机关、时效性、公布年份筛选；
* 检索结果可导出为表格，可每次批量下载最多 100 部 Word 原文（压缩包）；
* 类别：宪法、法律、行政法规、监察法规、地方性法规、司法解释；**不含部门规章**。

法规正文不受著作权法保护（著作权法第五条），可以存储和发送。LawRefBook/Laws（GitHub，1.9k 星）只作参考：仓库未声明许可证，代码不得复制；它靠抓取网页，官网 2025 年改版后能否使用未经核实。

V2-E-00 需要一份真实的导出表格和一个批量下载包来确定列名与文件结构：**下载前把文件名、来源、大小告诉用户并取得同意**，只在开发机下载，样本不进仓库（含真实法规全文，体积大），测试用虚构的小样本。

### 1.2 数据结构（新表，迁移 0014 起）

| 表 | 主要字段 | 说明 |
|-|-|-|
| laws | id、title、category、office、status（not\_yet / valid / amended / repealed）、published\_on、effective\_on、source\_key、replaced\_by（人工填写，可空）、updated\_at | 一部法规的一个版本一行。官方对同名法规的不同版本分别列出（如 2018 年与 2023 年的公司法），所以 title 不唯一，source\_key 唯一 |
| law\_articles | id、law\_id、article\_no（“第五百八十五条”）、seq、text、embedding vector | 只给有全文的法规建；法条是公开文本，不加密 |
| law\_imports | id、kind（catalog / fulltext / sync）、file\_name、added、changed、unchanged、status（pending / applied / discarded）、diff（jsonb）、created\_by、created\_at、applied\_by、applied\_at | 每次导入或自动同步一行，差异确认后才写入 laws |

### 1.3 手动导入（E2）

设置 → 审核要求 → 新增“法规库”分页，业务管理员可见。

1. **导入目录**：上传官方导出的表格（xlsx，沿用 17.6 上传检查与 openpyxl 解析限制）。按表头名称识别列，缺少必需列（标题、时效性）时整份拒绝并说明缺哪一列。
2. **差异预览**：显示新增 N 部、时效性变化 M 部（逐条列出“某法：有效 → 已废止”）、未变 K 部。业务管理员点“确认生效”后写入；点“放弃”则不写。
3. **只增改、不删除**：文件里没有的法规保持原样。分批导出（如只导出“法律”一类）不会误删其他类别。
4. **导入全文**：上传批量下载的压缩包（zip，沿用解压大小与文件数限制），逐个 docx 用现有 DOCX 解析器按“第…条”拆分，与目录按标题 + 公布日期对应；对不上的列为“未匹配”，不写入。全文写入后排一个向量化任务（维护线程组）。
5. 审计：law\_import\_apply（只记类别和数量）。

建议的全文范围：有效的法律与司法解释全部导入，行政法规按需导入。地方性法规只导目录，不导全文（数量大，与公司合同关系小）。

### 1.4 L-10 改为读法规库（E3）

1. 匹配规则沿用 V2-A：只认书名号内的完整标题。别名自动派生：去掉开头的“中华人民共和国”；其他别名不派生。
2. **同名多版本**：一个标题对应的全部版本都是“已废止”时才报 L-10；只要有一个版本是有效、已修改或尚未生效，就不报。避免把“已修改”（被新版本替换的旧版本）误报为废止。
3. 说明文字：“引用《{原写法}》，该法已于 {废止日期} 废止”。官方目录不一定给出废止日期，没有日期时写“该法已废止”。replaced\_by 有值时加“，现行规定见《{replaced\_by}》”。
4. 现有 `abolished_laws.yaml` 作为初始数据，由迁移写入 laws（含 replaced\_by），之后不再读取文件。新安装、未导入任何目录时，L-10 的效果与 V2-A 相同。
5. 法规库为空或读取失败时 L-10 跳过并记一条警告日志（不含标题），不影响其他校验。

### 1.5 可选自动更新（E4）

1. 新模块 `backend/app/lawsync/`。只有 `lawsync/client.py` 可以发出网络请求：目标域名写死为国家法律法规数据库，只允许 HTTPS GET 或检索所需的请求，请求参数只有类别、时效性、日期范围这类固定条件；函数签名不接受任何任务数据，测试断言这一点（T-20 扩展）。
2. 设置 → 数据（系统管理员）增加“法规库自动更新”开关，**默认关闭**；可选每月或每周；企业网络需要代理时读环境变量 `LAWSYNC_PROXY`。
3. 每次同步的结果与手动导入相同：生成一条 pending 的 law\_imports，提醒业务管理员确认，**不自动生效**。理由：时效性变化会直接改变审核结果，官网数据也可能出错或改版。
4. 只拉目录变化和新增法规的全文，单次最多 200 部；请求间隔不少于 2 秒。
5. 失败（网络不通、官网改版、返回格式不符、遇到验证码）时停止本次同步并提醒系统管理员“法规库自动更新失败，可改用手动导入”，不重试、不绕过验证码。
6. 返回内容按不可信输入处理：限制大小、只按预期结构解析，解析失败整体放弃。
7. 外发记录：每次同步在审计日志中记一条（时间、请求数、结果），不写入 llm\_calls。

## 二、向量检索基础（E5）

### 2.1 pgvector

* db 改为自建镜像：`postgres:16.15` + Debian 软件包 `postgresql-16-pgvector`（锁定版本），发布包的镜像清单同步。数据目录与 V1.0 相同（同为 PG 16），升级不需要导出导入。
* 迁移执行 `CREATE EXTENSION IF NOT EXISTS vector`。数据库账号没有建扩展的权限时，改由 db 镜像的初始化脚本和 upgrade.sh 执行（V2-E-00 核对 deploy 中的账号）。
* 索引用 HNSW（余弦距离）。备份照旧用 pg\_dump；恢复脚本必须用新的 db 镜像。V1.0 的旧备份可以恢复到 V2，迁移会补建扩展。

### 2.2 本地向量模型

选型方法同 V2Q-16（实体识别模型）：V2-E-04a 由 Opus 实测，**下载候选前取得用户同意**，只在开发机下载，在断网容器中评测，产出选型报告与规则修改稿，用户确认后 V2-E-04 才开工。

* 候选：bge-small-zh-v1.5、multilingual-e5-small、bge-m3（许可均需在选型时核实可商用）。外贸合同有英文，倾向多语言模型。
* 通过线（草案）：自建的 100 个“合同条款 → 应引用法条”样例上前 10 名召回 ≥ 85%；中英文条款对照范本时最佳匹配正确率 ≥ 90%；1 万字向量化 ≤ 5 秒；worker 内存增加 ≤ 1 GB；镜像增加 ≤ 1.5 GB。
* 运行：与实体识别模型共用 onnxruntime；worker 启动时加载，app 只校验文件与 SHA-256；校验失败拒绝启动；禁用遥测。

### 2.3 向量的安全定位

* 向量由原文计算，存在被部分反推出原文的可能，因此**与对应原文同等对待**：任务原文的向量随“原件与原文”层（C2，默认 30 天）删除；范本条款的向量随范本删除；法条向量是公开数据，不受限制。
* 向量无法加密后再建索引，因此只存放在本地数据库中，靠访问控制保护：所有检索都在服务端按 owner\_id 或资源范围过滤，接口不返回向量本身。
* 查询文本（如合同条款）的向量只在内存中计算，不落库。
* 日志不记录查询文本和检索到的范本内容。

### 2.4 资源估算（10 vCPU / 15 GiB）

有效的法律、行政法规、司法解释全文约 6 万条法条：向量化一次约几十分钟，在维护线程组后台执行；向量与索引约 300 MB。小型向量模型常驻内存约 0.3～1 GB。均在现有服务器能力内，V2-E-08 在测试虚拟机上实测确认。

## 三、法条依据（E6）

1. **开关**：设置 → 审核要求（业务管理员）“审核时附带相关法条”，默认关闭；V2-E-08 评测确认问题清单质量提升后再建议开启。外发策略为“不外发”的任务不受影响（本来就不调用模型）。
2. **检索**：构建外发文本时，用适用的审核要求文字与每个一级条款的原文（本地计算）检索有效的法律、司法解释法条，合并去重后最多 20 条、8000 字；分段审核（11.5）时每段各自检索。
3. **外发**：用户消息中正文之后增加一节“参考法条”，每条带编号，如 `[F3]《中华人民共和国民法典》第五百八十五条：……`。每条在拼接前先单独跑一次出口复检的规则；命中已记住的名称或自定义敏感词的法条直接丢弃，数量写进覆盖说明。之后整段外发文本照常出口复检。
4. **提示词**：系统提示词增加一条：引用法律时只能使用“参考法条”中的编号，不得凭记忆引用条号；提示词版本升级。输出 JSON 的 finding 增加可选字段 `law_refs`（编号数组）。
5. **本地核实**：`law_refs` 中不存在的编号丢弃；问题说明里出现的“《…》第…条”不在法规库中或已废止的，结果页标“引用未经法规库核实”。
6. **展示**：问题卡片显示“依据：《民法典》第五百八十五条”，可以展开原文；Word 报告在问题后列出依据条文。
7. **追问**：按问题文字检索最多 5 条附上，规则同上。
8. **成本**：每次审核约多 5 千个 token；覆盖说明写明本次附带的法条数。

## 四、公司范本库（E7）

1. **管理**：设置 → 审核要求 → “公司范本”分页（业务管理员）：上传 DOCX 范本，填写名称、文件类型、立场（与公司补充要求同一套维度），可以启用或停用。范本按一级条款拆分，每条可选填三项各 300 字以内：标准立场、可接受范围、需上报的情形。
2. **存储**：范本条款原文用主密钥加密存储（公司内部文件，17.3）；向量明文存储（见 2.3）。
3. **选择**：审核时按文件类型、立场找到启用的范本，自动选与本文件平均相似度最高、且达到阈值的一份；第二步显示“将对照公司范本：{名称}”，可改为“不对照”。没有合适范本时不显示。
4. **对照**：本文件每个一级条款找相似度最高、且达到阈值的范本条款，组成对照对。最多 30 对、1 万字；超过时按相似度取前若干对，写进覆盖说明。
5. **外发**：增加一节“公司范本对照”：本文件条款位置 + 范本条款原文 + 三项说明。范本文字与正文一样经过脱敏（我方主体预置 B5 会替换本公司名称），并照常出口复检。模型按“与范本相比”的口径输出问题，finding 增加来源标记“范本对照”。
6. **缺失条款（本地校验 L-12）**：范本中找不到任何达到阈值的对应条款时，本地报“公司范本中的『{条款标题}』在本文件中未找到对应内容”，严重程度为低，不需要模型。阈值在 V2-E-00 用虚构样本确定。
7. **记录**：审核轮次记录所用范本的 id 与内容哈希；范本修改后，旧结果仍显示当时的对照。
8. 这一项替代 PLAN“不在 V2”中的“我方标准条款库”。

## 五、智能助手知识库（E8，交 V2-D-00）

只先定约束，细节在 V2-D-00 中设计：

* 业务管理员上传公司制度、流程、产品资料，范围为全公司（“部门与共享”仍不在 V2）；分块后向量化，复用 E5。

## 八、风险

| 风险 | 应对 |
|-|-|
| 官网改版或增加反爬，自动更新失效 | 自动更新只是可选项；失败即提醒，改用手动导入；不绕过验证码 |
| 官网数据有误，导致误报废止 | 差异必须业务管理员确认；同名多版本只在全部废止时才报 |
| 附带法条后模型更爱引用法条、问题清单变长 | 默认关闭，评测对比后再开；条数和字数有上限 |
| 范本相似度阈值不准，误报缺失条款 | L-12 只报低；阈值用样本确定；第二步可以选择不对照 |
| 向量反推原文 | 与原文同等保留期，本地存放，按 owner 过滤，不经接口返回 |
| db 镜像改为自建，升级与恢复多一个环节 | 测试虚拟机上演练 upgrade.sh 与 restore.sh（V2-E-08） |
