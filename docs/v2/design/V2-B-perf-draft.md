# V2-B-08 性能：剩余优化评估与时延指标备选稿（草案，待用户确认）

2026-10-25 · Opus 5.5 · 依据 V2Q-55 · 代码与测量基线 `6a2f314` · 登记 V2Q-56（需决定）

**本文件只是草案。** 原 6.4 门槛（500 字热态 ≤ 1 秒、万字 ≤ 10 秒等）在用户确认前继续有效，B-08 的失败回执保留；B-08 未完成，B-09 未开始。本文件不改产品代码、线程、模型、FP32 精度、阈值、停用词、窗口参数或安全链，不改正式虚拟机，也没有连接服务器。硬件按 V2Q-55 保留：28 vCPU（2 sockets × 14 cores）、38 GiB、balloon 下限 16 GiB。

## 〇、结论

1. **现有证据不足以支持调整时延指标。** Q54 的四组试验统一限在 8 CPU 配额、4/8 线程、vCPU0～7，只说明“8 CPU 内调线程和绑定已无明显余地”，不能说明 28 vCPU 已用尽。还有三类空间完全没有测：① 虚拟化层（CPU 指令集暴露、vCPU 与物理核/超线程的映射、宿主超分与 steal）；② 8 线程以上的扩展曲线；③ 不改变识别结果的推理组织方式（多窗口成批、窗口并行、跨节点成批）。
2. **按算量估计，原门槛并非明显不可达。** 本次在本机用产品分词器只读算出：500 字问题切成 2 个窗口，共 **1,084 个 token**（中文每字约 2 个 token，是 GLiNER 预切分加词首标记造成的，属于对拍口径的一部分，不能改）；万字切成 35 个窗口，共 **10,434 个 token**。目标机 8 线程每 token 约 1.2～1.4 毫秒，要达标需要每 token ≤ 0.92 毫秒（500 字）和 ≤ 0.96 毫秒（万字），即还需快约 1.3～1.6 倍。若 8 线程实际只落在 4 个物理核的超线程上（28 vCPU 多于 E5-2630 v4 双路 20 个物理核，有这种可能），换到 12～14 个独立物理核或改成窗口并行，存在达到这个倍数的可能。所以应**先验证，再谈调指标**。
3. **建议的顺序**：先做只读核对 R1～R4（不施加负载，几分钟），再做一轮隔离实验 E1～E4（约 40 分钟，需授权）。只有满足第五节的全部证据条件、最佳合规方案仍未达标时，才启用第六节的方案乙；在此之前按方案甲（原数值不变、补齐缺失口径）推进。
4. **一个新发现的并发问题**：worker 两个解析线程共用一个 8 线程 ORT 会话，双任务并发时每个任务 61.2 秒，约等于单任务 30.2 秒的两倍，即实际是串行。原门槛只写了单任务增量，指标稿需要补并发口径（第六节 M7）。

## 二、未验证的优化空间评估

| # | 方向 | 是否改变识别结果 | 预期收益（估计，待实测） | 代价与风险 | 优先级 |
|-|-|-|-|-|-|
| O1 | 确认 CPU 暴露 AVX2/FMA（ORT 的 MLAS 按 CPU 指令集选内核） | 否 | 若缺失，补上后可达 2 倍以上；若已有，排除此项 | 改 CPU 类型需重启正式 VM，并考虑迁移兼容性 | 只读核对最先做 |

| O3 | 8 线程以上扩展曲线（10/12/14 同一 socket，20/28 跨 socket），配合自旋开关 | 否（线程数只影响浮点累加顺序，对拍已证明在 1e-4 内） | 若有独立物理核，500 字可能到 1.1～1.2 秒，万字到 9～10 秒 | 并发场景下线程超订会更慢，必须同时测线程预算（E3） | 高 |

## 五、什么证据足以支持调整指标

满足下列**全部**条件，且最佳合规方案仍未达到原门槛时，才可启用方案乙：

* **G1 平台**：R1 确认 AVX2/FMA 已暴露；R2/R3 确认测量时 steal ≤ 5%，且知道可用的独立物理核数。平台配置有明显缺陷时，先报告修复方案（需停机的另行授权），不调指标。
* **G2 线程**：E2 给出 8 线程以上的完整扩展曲线，最佳点之后再加线程收益 < 5%。
* **G3 推理组织**：E4 中所有不改结果的方案都已试过，报告各自的时延、内存与对拍结果。
* **G4 并发**：E3 证明选定的线程分配不会使 6.4 压力场景比现配置更差。
* **G5 效果**：所选方案 391 对拍、留出集、保留词误替换、类别召回漏掉 0 全部不变。

即使启用方案乙，新数值也来自第六节写明的产品体验依据，**不是“实测最好值加一点余量”**；并且现产品配置（app 4 线程 2.18 秒）在方案乙下仍不通过，必须先落实优化才能验收。
