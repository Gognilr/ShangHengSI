## 一、HTTPS 根证书（V2-Z-01，GPT-6.1 Sol，high，测试先行）

### 1.1 背景

公司没有 Windows 域、没有公司域名、没有可自行添加解析记录的 DNS，只能用 IP 访问（V2Q-160）。现在 Caddy 用 `tls internal` 自己的签发机构：根证书与私钥存在 `caddy_data` 数据卷里，不在备份中，数据卷丢失就会换成新根证书，所有电脑要重新导入；运维说明第 5 节和 SPEC 20.4 假设用组策略下发根证书，实际不可用；而导入电脑的 Caddy 根证书可以为任何网站签发证书，根私钥一旦泄露，影响所有网站。

### 1.2 证书结构

```
商衡SI 根证书（离线保管，不在服务器上）
  有效期 10 年；CA:TRUE、pathLen 1；名称约束（关键扩展）：
  允许的 IP = 公司内网段（默认 172.16.0.0/12，V2Q-163）；允许的域名 = invalid（使任何真实域名都不被允许）
  └─ 商衡SI 中间证书（放在服务器 deploy/secrets/ca/，Caddy 用它签发）
       有效期 10 年；CA:TRUE、pathLen 0；名称约束：允许的 IP = 服务器 IP/32；允许的域名 = invalid
       └─ 站点证书（Caddy 自动签发、自动续期，SAN 为服务器 IP）
```

* 算法 ECDSA P-256；主体名称写“商衡SI 本地根证书”“商衡SI 本地中间证书”。
* 员工电脑只导入根证书。服务器只有中间证书私钥：服务器被攻破时，中间证书受名称约束，只能冒充本服务器 IP。
* 服务器换 IP（仍在允许网段内）：用离线根证书重新签发中间证书，员工电脑不用重新导入。

### 1.3 生成工具

`python -m app.cli gen-ca --ip <服务器IP> [--net 172.16.0.0/12] --out <目录>`（`backend/app/security/site_ca.py`，用已有的 cryptography 库）：

1. 校验：`--ip` 为私有地址且在 `--net` 内；`--net` 为私有网段；输出目录中已有任一目标文件时拒绝（不覆盖，同 `gen-key`）。
2. 输出：`root.crt`、`root.key`（离线保管用）、`intermediate.crt`、`intermediate.key`、`root.sha256`（根证书 DER 的 SHA-256 指纹，冒号分隔大写）。私钥文件权限 600。
3. `gen-ca --reissue-intermediate --ip <新IP> --root-cert root.crt --root-key root.key --out <目录>`：只重新签发中间证书（换 IP 时用）。
4. 屏幕只输出文件名、指纹和下一步提示（“请密钥保管人取走 root.key 离线保存，并从服务器删除”），不输出私钥。

### 1.4 Caddy

* 生产：Caddy 使用自定义签发机构，加载 `secrets/ca/root.crt`（仅证书）与 `secrets/ca/intermediate.crt`、`intermediate.key`，站点证书由中间证书签发；关闭 Caddy 向容器内安装信任与自动更换中间证书。
* 开发：没有 `secrets/ca/` 时仍能用 `tls internal` 启动（本机 localhost 开发、`docker-compose.mock.yml` 不受影响）。实现方式自选（例如按环境变量 import 不同的片段），须用 `caddy validate` 验证两种模式。
* 若实测 Caddy 必须持有根私钥才能使用自定义签发机构：根私钥仍不放服务器，改为由中间证书直接充当 Caddy 的“根”（Caddy 只持有中间证书与其私钥），员工电脑仍导入离线根证书；两种都不可行时停下报告，作为问题提给 Opus。
* `secrets/ca/` 以只读方式挂载进 web 容器。

### 1.5 证书下载页

* 80 端口（http）上 `/cert/` 路径提供：说明页、`shangheng-si-root.crt`、`install-cert.cmd`；其余 http 请求照旧跳转 https。
* 说明页：根证书指纹；两种导入方法——双击运行 `install-cert.cmd`（按当前用户导入“受信任的根证书颁发机构”，不需要管理员权限；Windows 弹出安全警告时核对指纹后点“是”）、或双击证书文件按向导手动导入；导入后重新打开浏览器访问 `https://<服务器IP>/`。只写操作步骤，不写技术解释。
* `install-cert.cmd`：下载或使用同目录的根证书，导入前用内嵌指纹校验文件，不一致则拒绝并提示联系管理员；只写入当前用户的证书存储。
* 说明页与脚本中的指纹由 install.sh / upgrade.sh 从 `secrets/ca/root.sha256` 写入，不手工编辑。

### 1.6 部署脚本

* **install.sh**：安装前检查 `secrets/ca/` 下中间证书、中间私钥、根证书齐全，且**不存在** `root.key`；缺少时提示先运行 gen-ca 并说明步骤，拒绝继续。
* **upgrade.sh**：
  1. 目标目录没有 `secrets/ca/`（从 1.0.0 升级）时：用 `.env` 中的站点 IP 运行 gen-ca，暂停并提示密钥保管人取走 `root.key` 后输入确认语，确认 `root.key` 已不在服务器后继续；
  2. 目标 Caddyfile 与 1.0.0 发布包中的 Caddyfile 逐字一致时直接替换为新版；不一致（IT 改过）时停下，要求人工合并，不再只是另存 `Caddyfile.new` 后继续；
  3. 结束时提示“员工电脑需要导入一次新的根证书：http://<服务器IP>/cert/”。
* **restore.sh / 运维说明**：`secrets/ca/` 与主密钥同样不在备份中；恢复到新机器时由密钥保管人提供中间证书与私钥（或用离线根证书重新签发）。
* **build_release.sh**：发布包不含任何证书或私钥；包内带下载页模板与 `install-cert.cmd` 模板。

### 1.7 运维说明

第 5 节重写为“IP 访问与根证书”：生成（gen-ca）、离线保管（与主密钥同一保管人、同等级别）、指纹登记、员工电脑导入（下载页地址与两种方法）、核对、换 IP、证书过期前（10 年）的更换；删除“组策略导入”“配置内网域名”的写法；写明服务器必须使用固定 IP（静态地址或路由器地址保留），IP 改变会使员工书签失效。第 8 节“本地备份与密钥”、第 10 节“恢复”、第 11 节“升级”同步补充 `secrets/ca/`。

### 1.8 测试（T-54，写成自动化测试）

1. gen-ca：根证书与中间证书的 CA 标志、pathLen、有效期、名称约束（关键扩展，内容同 1.2）；私钥权限 600；目标文件已存在时拒绝；`--ip` 为公网地址或不在 `--net` 内时拒绝；屏幕输出不含私钥。
2. 用 cryptography 的证书验证接口：以根证书为信任锚，中间证书签发的“服务器 IP”站点证书验证通过；签发给其他 IP、任意域名的站点证书验证失败。
3. `--reissue-intermediate`：新中间证书由原根证书签发，换 IP 后旧 IP 的站点证书验证失败、新 IP 的通过。
4. 脚本静态检查（并入 test_scripts.py）：install.sh 检查 CA 文件与 `root.key` 不存在；upgrade.sh 含 1.0.0 Caddyfile 指纹比对与 gen-ca 流程；build_release.sh 不打包 `secrets/`；下载页与脚本模板中没有写死的指纹。
5. 文件范围之外的已有测试不得修改。

**文件范围**：`backend/app/security/site_ca.py`（新）、`backend/app/cli.py`（只加 gen-ca）、`backend/tests/test_site_ca.py`（新）、`backend/tests/test_scripts.py`（只追加）、`deploy/Caddyfile`、`deploy/caddy/`（新，片段与下载页模板，如需要）、`deploy/docker-compose.yml`（web 挂载 `secrets/ca`）、`deploy/scripts/install.sh`、`deploy/scripts/upgrade.sh`、`deploy/scripts/restore.sh`（只加提示）、`deploy/scripts/lib.sh`、`deploy/scripts/build_release.sh`、`deploy/cert/install-cert.cmd`（新，模板）、`docs/ops/运维说明.md`（第 5、8、10、11 节）。

4. 升级后检查：五服务健康、https 200 / 未登录 401、证书下载页可用、用一台已导入根证书的电脑访问无警告、管理员账号登录、手动备份一次并校验、管理员提醒正常；模型设置与已有任务、历史结果完整。
5. 失败时：按运维说明用 PVE 快照恢复到升级前，记录原因后再议。
6. 写入 `docs/acceptance/V2.0升级记录.md`：版本、包 SHA-256、根证书指纹、停服时长、检查结果、待用户完成事项（员工导入根证书、法条依据与知识库是否开启等管理员设置）。

## 十、风险

| 风险 | 应对 |
|-|-|
| Caddy 不支持只持有中间证书的自定义签发机构 | 1.4 的退路；两种都不行时停下，不把根私钥放上服务器 |
| 浏览器不执行根证书上的名称约束 | 中间证书同样带约束（所有浏览器都执行中间证书的约束），服务器上只有中间私钥 |
| 员工电脑没有及时导入新根证书，升级后打不开 | 升级前通知；下载页走 http 不受证书影响；指纹核对步骤简单 |
| 根私钥丢失 | 只影响以后重新签发中间证书（换 IP 或 10 年到期）；届时生成新根证书并让电脑重新导入 |
| 1.0.0 → 2.0.0 跨度大，升级失败 | Z-04 完整演练；PVE 快照；升级前备份 |
| 评测发现 V2 审核效果退化 | 写入报告，由 Opus 在 Z-05 判断是否阻止发布 |
