# 商衡SI V2 整体方案

2026-10-23 · Opus 5.5 起草，用户已确认（2026-10-23，含 V2Q-01～V2Q-03）

本目录是 V2 的全部文档，与 V1.0（docs/SPEC.md、docs/TASKS.md）分开存放，减少每个会话需要读取的内容。V2 的内容全部来自 2026-10-23 的功能讨论，用户已逐项确认放进 V2。

## 一、目标

V1.0 解决了“合同类文件能安全地交给云端模型初审”。V2 做三件事：

1. **审核更准**：内置要求贴合国内合同，减少外贸类条目的噪音；报价清单让模型看得到；补上三项确定性的本地校验。
2. **脱敏更全**：补齐规则的已知盲区，引入本地实体识别模型，处理叙述性文字中的人名、机构名。
3. **系统撑得住**：并发、数据保留与存储、权限分工、主密钥更换，满足全公司长期使用。

在此基础上，第四批“智能助手”把系统从“合同初审”扩展为“带脱敏与还原的文件会话”（翻译、起草、摘要、核对等）。

## 二、前提与顺序

1. **先完成 V1.0**：R4 收尾安全包 → M8-02～M8-05（部署、发布包、运维说明、全量验收与正式安装）→ 打 git 标签 `v1.0.0`。
2. **V2 在 `v1.0.0` 之后于 main 上开发**，按批次串行：V2-A → V2-B → V2-C → V2-D。V2-B 改变脱敏行为，排在 V2-A 之后，便于区分评测结果的变化来自审核要求还是脱敏；V2-C 基本独立；V2-D 依赖 V2-B 的实体识别和 V2-C 的权限、数据保留。
3. **设计可以提前写**：各批的细化（V2-A-00、V2-B-00、V2-C-00）只改 docs/v2/，可以在 GPT 实现 R4、M8 的同时由 Opus 完成，使 V2 开工时 GPT 能连续做完一整批。
4. 线上 V1.0 需要紧急修复时，在 `v1.0.0` 标签上开修复分支，修复合并回 main。

## 四、开发、测试与审核方式（用户已确认，V2Q-01）

用户希望开发过程中少跑测试、完成后集中测试，由 GPT-6.1 Sol 集中完成实现。方案如下：

| 环节 | 做法 |
|-|-|
| 设计 | 每批开工前由 Opus 细化（V2-x-00）：设计文档、自包含任务卡、测试用例表、必要的回归样本（待修项以 known\_gaps 登记）、SPEC-V2 变更稿。用户确认后 GPT 才开工 |
| 单个任务 | GPT 按任务卡实现，**测试用例照写**（可以多写，不得删改）；**只运行与本任务相关的测试文件**（通常几秒到一分钟），不跑整仓全量；改了脱敏规则的任务另加脱敏回归集与 A-03（约半分钟）；前端任务只跑 `npm run build`，浏览器检查留到批次末。每个任务照常提交 |
| 批次末 | 一个“集中测试”任务（GPT）：整仓全量测试、修复失败、按清单做浏览器检查、运行评测脚本，写批次测试报告 |
| 审核 | Opus 按批次审核一次（不再每个任务停下）：核对测试用例与样本未被删改、文件范围、日志与权限，审实现；问题列给用户或直接修复 |
| 验收 | V2 全部完成后 Opus 做一次总验收：全量回归、浏览器、评测对比、在测试服务器上用 upgrade.sh 升级演练，打标签 `v2.0.0` |

**取舍**：少跑整仓测试会让跨模块的问题晚到批次末才暴露，修起来比当场发现难定位；用“相关测试必跑 + 脱敏回归集必跑 + 批次末全量”把风险压到可接受。脱敏与加密这类安全核心任务仍然测试先行（用例由 Opus 给出），只是审核从“每个任务”改为“每批一次”。R4 是 V1.0 上线前的安全收尾，仍按已确认的“逐个审核”执行，不受本节影响。
