## 一、V311-A-01：助手消息“替换”同步替换文件

### 1.1 根因（已定位）

1. 助手消息在 `assistant.service.send` 中由 `_question` 脱敏，选“替换”的疑似项分配中性代号 `[[ORG_n]]` 等，写进会话对照表（`write_full_map`）。
2. 文件正文里的同一文字没有 RedactionItem，外发文本照常带原文。
3. 网关出口复检取 `engine.load_real_values`：对照表里的真实值出现在外发文本 → MAP 拦截。V31Q-119 的豁免只认追问代号（`chat_number(...) is not None`，即 `[类别_Qn]`），助手的中性代号不在其列，于是此后该会话每条消息都被拦截，无法恢复。
4. 同类情形二：先在消息里替换了“星海公司”，之后才加入含“星海公司”的文件，确认脱敏时复检同样失败（`confirm` 的 precheck → `refresh_if_blocked` 重算不会新增词条 → `OUTBOUND_BLOCKED`）。实施时先写用例确认是否复现。

### 1.2 做法

原则：**助手会话里，对照表中的真实值在会话全部文件中一律替换**。消息里选“替换”即等于为本会话加一个用户词条（与确认页“手动补充”同一机制：`detected_by="user"` 的 RedactionItem，重算时 `_user_terms` 自动带上）。不改 `load_real_values` 的拦截规则——助手的文件不一定外发过，拦截是对的，要做的是让文件跟着替换。

1. **新函数 `engine.cover_session_values(db, task, extra: list[UserTerm] = ()) -> int`**（只用于 kind=assistant，调用方持有任务行锁与对照表锁）：
   * 候选 = `extra` ∪ 对照表中非 `@`、非日期的真实值（类别从中性代号 `[[ORG_n]]`/`[[PERSON_n]]`/… 反查，`[[OUR]]` 视为 ORG；查不出的按 CUSTOM）。
   * 用 `_user_pattern` 在 `task_texts` 中查找；只保留“至少有一处没被现有 RedactionItem 覆盖、且不是用户明确保留（`load_kept_values`）”的候选。
   * 没有候选直接返回 0（只做字符串查找，正常发送不重算）；有则 `_run(db, task, _current_overrides(existing), existing, terms)` 一次重算，返回新增词条数。
   * 助手 `_run` 走 `pin=True`，`NeutralAllocator.seed` 按“类别 + 规范化值”复用已有代号，所以文件里的“星海公司”会拿到消息里已经分配的同一代号。实施时用用例确认这一点，以及重算后旧代号全部仍在对照表（历史消息还原不能断）。
   * 词条若出现在助手固定提示文字中（参照 `_add_term` 的 `TERM_IN_PROMPT` 检查，取助手提示词的固定部分），拒绝 422 `TERM_IN_PROMPT`，前端提示改选“不替换”。
2. **`assistant.service.send`**：锁任务与对照表后、`_question` 之前，把本次 `decisions` 中 `replace` 的文字作为 `extra` 调用 `cover_session_values`，再用重算后的对照表脱敏消息（消息与文件同一代号）。同一函数不带 `extra` 也会补上历史遗留：**已经被拦截的旧会话下一次发送即自愈**，无需迁移。
3. **`assistant.service.confirm`**：precheck 之前调用 `cover_session_values(db, task)`，覆盖“先替换、后加文件”的情形。
4. **预览 `preview`**：每个疑似项增加 `in_files: bool`（该文字在会话文件中出现且未被替换）。只读，不写库。
5. **前端 `components/assistant/Composer.vue` 的“确认发送内容”**：`in_files` 为真且选中“替换”时，在该项下显示一行提示“文件中的同一文字也会替换”。发送成功后若有新增词条，刷新会话详情（文件抽屉的替换计数、“查看外发文本”随之更新）。不加新弹窗、不加开关。
6. **审计**：新增词条时记一条 `assistant_session_terms`，detail 只记条数。
7. 审核追问（chat）不在本项范围，V31Q-119 已处理，不动。

### 1.3 测试（少量，写进 `tests/test_assistant*.py` 现有文件）

1. 已确认文件含“星海公司”，消息“星海公司负责什么？”选替换 → 发送成功；文件外发文本与消息用同一代号；随后一条不含该词的消息也能发送（模拟模型）。
2. 构造旧状态（对照表已有消息代号、文件未替换）→ 下一次发送自愈，不拦截。
3. 先替换后加入含该词的文件 → 确认脱敏通过，文件中该词被替换。
4. 旧代号在重算后仍在对照表，历史回复还原正确。

## 二、V311-B-01：实体识别提速

### 2.1 现状（已读代码）

* `ner.raw_recognize` 把每段按 320 字窗口、288 步长切开，**每个窗口单独一次 `session.run`，batch=1**；`engine.compute` 对每个节点（含每个表格单元格）分别调用 `ner.recognize`。万字文本约 35 个窗口串行。
* `intra_op_num_threads = NER_THREADS`（默认 8），`inter_op=1`；测试机 28 vCPU 空闲时 8 线程 31.9 秒、4 线程 45.0 秒，171 项。
* 已有：被前序规则替换的文字先 `mask` 成空格；纯数字节点跳过；同一次重算内相同残余文本复用；节点级结果缓存（`NerNodeResult`，用于重算）。首次解析无缓存。

### 2.2 硬约束

* 不换模型、不量化、不改窗口大小与步长、不改阈值与 `keep_entity`；**识别结果与改动前一致**：同一输入的实体（起止、类别）完全相同，分数差 ≤ 1e-4。
* 不引入新依赖；onnxruntime、tokenizers 版本不变。
* 内存门槛不变（单进程增加 ≤ 2.5 GB）。

### 2.3 步骤

1. **先剖析，再动手**（结果写进报告，作为后续取舍依据）：用 `tests/ner_benchmark.py` 的万字文本，加一份虚构的表格密集 DOCX/XLSX（几百个短单元格），在开发机 8 线程下分别计：分词、构造张量、`session.run`、解码四段耗时；窗口数、每窗词数与 span 数；节点数与 `session.run` 调用次数。
2. **批量推理**：把多个窗口（同一节点的各窗口，以及多个短节点的窗口）按长度排序后组成一批，用 attention_mask / words_mask / span_mask 补齐，一次 `session.run`。先确认导出的 ONNX 第 0 维是动态的；若不是或补齐后结果超出 2.2 的容差，放弃本项并在报告中说明。批大小按剖析结果选一个固定值（如 4～8），不做自适应。
   * 接口：新增 `ner.recognize_many(texts: list[str]) -> list[list[Entity]]`，`recognize` 改为它的单元素调用；`engine.compute` 把需要识别的节点（缓存未命中、去重后）先收集，一次调用 `recognize_many`，再按原顺序回填。节点之间**不拼接文本**（拼接会改变上下文与结果）。
3. **跳过无名称可能的残余**：mask 后不含任何汉字或字母的残余直接返回空（这些结果本来就会被 `keep_entity` 过滤）；仅此一条，不做别的启发式跳过。
4. **线程**：在开发机测 `NER_THREADS` 8 / 12 / 16 与批量后的组合，只按结果调整默认值（deploy/.env.example、docker-compose 与 models.yaml 一致）；不加并行会话、不加线程池。
5. **一致性对拍**：对 benchmark 文本、golden 全部样本与表格样本，比较改动前后 `raw_recognize`/`recognize_many` 的输出，按 2.2 判定；对拍脚本放 `backend/tests/` 旁的一次性脚本或现有 `ner_benchmark.py` 的扩展，不新增常规测试函数（`test_ner.py` 中补一个“批量与逐条结果相同”的小用例即可）。

### 2.4 目标与验收

* 开发机 8 线程万字纯 NER 耗时 ≤ 改动前的 50%；表格密集样本的 `session.run` 次数显著下降（报告给出前后数字）。
* 识别结果按 2.2 一致；golden、A-03、回程样本、`test_ner.py`、脱敏相关测试通过。
* 测试机口径（SPEC 第 3 节“约 32 秒”）在 V311-Z 由用户决定是否在正式服务器上做一次只读计时；未测前 SPEC 写开发机前后数字。
* 若批量推理达不到目标，报告写明瓶颈所在（例如 span 层计算本身），停下交 Opus，不自行扩大范围（不提量化、换模型）。
