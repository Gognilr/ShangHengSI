# 商衡SI 运维说明

适用：PVE 中的 Ubuntu 26.04 x86_64 虚拟机；基准配置 28 vCPU、38 GiB 内存（balloon 下限见第 13 节）；系统盘约 32 GiB，ext4 数据盘 /data 约 344 GiB。命令在服务器 bash 中执行，除首次解包外默认已进入 `/data/apps/aireview`。示例中的 `<服务器IP>`、`<运维账号>`、`<备份文件>`、`<内网网段>`须由 IT 替换，不直接粘贴尖括号。

正式安装后，停服、清空或替换数据须先得到负责人同意。

## 1. 概览与准备

核心服务为 db（PostgreSQL 16.15）、app（接口与迁移）、worker（解析、审核与备份）、converter（LibreOffice 转换与 ffmpeg 录音解码）和 web（Caddy 与静态前端）。启用 `asr` 时增加 transcriber（录音转写），启用 `mt` 时增加 translator（本地翻译）。converter、transcriber、translator 均断网，只通过 2 GiB 内存盘卷 convert_spool 与 worker 交换文件。

录音解码使用 converter 镜像内的 Debian ffmpeg，版本由 `converter/Dockerfile` 的 `FFMPEG_VERSION` 锁定，当前为 `7:7.1.5-0+deb13u1`。Debian 构建启用 GPL，许可证说明随软件包保留在镜像的 `/usr/share/doc/ffmpeg/copyright`，对应源码可从 [Debian ffmpeg 源码页](https://sources.debian.org/src/ffmpeg/) 获取。发布包按 V31Q-71 在公司内部分发。`MAX_AUDIO_MB` 默认 500，代理对录音加入路径另留 20 MB 表单余量；录音解码成功后删除上传原件，仅加密保留回放副本，按原件保留期清理。

准备离线发布包、模型接口地址及 API 密钥、固定内网 IP、证书方案、密钥保管人，以及独立 Windows 异地备份管理机。发布包已包含运行依赖和模型，服务器通过 docker load 导入。

基础镜像为 `aireview-backend:{版本}`、`aireview-web:{版本}`、`aireview-converter:{版本}`、`aireview-db:{版本}`。启用对应 profile 的发布包另含 `aireview-transcriber:{版本}` 或 `aireview-translator:{版本}`。db 基于 `postgres:16.15` 并安装固定版本的 pgvector。恢复前脚本检查目标镜像是否提供 vector 扩展。

构建发布包统一使用 `--models <目录>`，目录组织与资源设置见第 13 节；模型不进入 Git。

安装目录 `/data/apps/aireview`；备份 `/data/apps/aireview/backup`；Docker `/data/docker`；containerd `/data/containerd`。备份与数据库在同一块盘，必须做异地备份。原件与数据库是 Docker 卷，不能只复制安装目录代替备份。

## 2. 服务器检查

```bash
findmnt /data
df -h / /data
docker version
docker compose version
sudo docker info --format '{{.DockerRootDir}}'
sudo grep -E '^root[[:space:]]*=' /etc/containerd/config.toml
sudo ss -ltnp '( sport = :80 or sport = :443 )'
```

预期 /data 独立挂载；Docker 与 containerd 的 root 都在数据盘；首次安装前 80 / 443 没有监听者。脚本会检查安装目录、备份目录、Docker root、containerd root 不在根分区。/data 未挂载时停止操作，先由 IT 修复挂载；不得让 Docker 写满系统盘。

不得改动 `/etc/docker/daemon.json` 的 data-root、registry-mirrors、日志轮转。当前服务器已完成 containerd 迁移，无须重复操作。新服务器若需迁移，先建 PVE 快照、停业务及 Docker/containerd，在所有数据仍完整保留时由 IT 执行：

```bash
sudo systemctl stop docker.service docker.socket containerd.service
sudo mkdir -p /data/containerd
sudo rsync -aHAX --numeric-ids /var/lib/containerd/ /data/containerd/
sudoedit /etc/containerd/config.toml
# 将顶层 root 设置为 /data/containerd；不是 plugins 段里的 root。
sudo systemctl start containerd.service docker.service
sudo docker images
sudo docker ps -a
```

确认镜像、卷、容器及服务健康后才安排旧目录清理；不自动删除旧存储。新装系统缺少配置文件时应由 IT 生成与已安装 containerd 版本相符的配置后再设顶层 root，不能直接覆盖现有配置。

## 3. 首次部署与首次登录

由 IT 将发布包解压至尚未安装的 `/data/apps/aireview`；包内不是源码仓库，根目录直接有 docker-compose.yml 和 scripts/。解包时去掉包内顶层目录，并让文件属主为 root：

```bash
sudo mkdir -p /data/apps/aireview
sudo tar -xzf aireview-<版本>.tar.gz -C /data/apps/aireview --strip-components=1 --no-same-owner
cd /data/apps/aireview
sha256sum -c SHA256SUMS
sudo ./scripts/install.sh --site <服务器IP> --admin admin
```

脚本校验发布包、数据盘、端口，导入包内镜像，创建 gid 10001 的 aireview 组；生成 .env、主密钥和备份密码，启动服务并创建管理员。已存在 .env 或密钥时拒绝重装，应走升级。备份目录属主 10001:10001、权限 2750；secrets/ 为 700，密钥 600；.env 为 root:600。

同机演练用单独目录、独立 Compose 项目名和空闲端口，例如在该目录执行 `sudo env COMPOSE_PROJECT_NAME=aireview-rehearsal ./scripts/install.sh --site <服务器IP> --http-port 18080 --https-port 18443`。安装后在该目录的 `.env` 中保存同一个 `COMPOSE_PROJECT_NAME`，备份、恢复和升级都会用这个项目。证书下载页走 HTTP 端口，系统入口走 HTTPS 端口。

初始管理员密码仅显示一次，按本单位凭据交接流程交付，不放入工单或共享日志。自动演练可用以下方式只写入 root 可读文件；`--yes` 跳过确认，仅限演练，不表示已创建快照：

```bash
sudo bash -c 'umask 077; ./scripts/install.sh --site <服务器IP> --yes > /root/aireview-install.log 2>&1'
```

浏览器访问 HTTPS，首次登录强制改密。进入设置填写模型，确认备份时间并做一次备份，配置异地拉取。把 secrets/master_key 与 secrets/backup_password 各保留离线副本，交专人保管；屏幕不会显示两份密钥。不得覆盖已有密钥。

## 4. 模型设置推荐值

管理员在设置中填写 API 密钥，不把密钥放在命令行参数或文档。推荐接口 `https://api.deepseek.com`，模型 `deepseek-flash`（全小写，须与厂商控制台的模型名完全一致，否则返回 HTTP 400）；最大输出 32000、超时 600 秒、分段长度 300000、JSON 输出开启、temperature 0.1。附加请求参数不必手写：点输入框下方的“填入推荐值”，即填入：

```json
{"thinking":{"type":"enabled"},"reasoning_effort":"high"}
```

“测试连接”测的是**已保存**的设置：先点页面底部“保存”，再点“测试连接”；有未保存的修改时页面会提示先保存。测试失败时，提示中会附上模型服务返回的原因（如“支持的模型名为……”），按原因修改后保存再测。以上为项目设计推荐值，须通过连接测试与虚构样本核对。思考模式下 temperature 不生效。每月调用上限按单位预算设置正整数；0 表示不限制，不推荐直接沿用到生产。单价须按控制台账单币种填写每百万 token 的输入、输出单价；系统只有两项单价，估算不区分峰谷和缓存折扣。不能将美元数直接填进按人民币管理的预算。

2026-10-24 核对的官方美元峰时未缓存输入 / 输出价为 0.30 / 1.20 美元每百万 token；这仅是核价参考，不是人民币推荐输入值。上线前按实际账单币种与预算确认并填写。来源：[官方调用说明](https://api-docs.deepseek.com/quick_start/first_api_call)、[官方价格表](https://api-docs.deepseek.com/quick_start/pricing/)。价格与模型服务版本可能变更，交付时重新核对；本系统不自动变更厂商参数。

## 5. IP 访问与根证书

服务器必须使用固定 IPv4 私有地址（静态地址或路由器地址保留）。IP 改变会使员工书签失效，须通知员工更新地址。无需公司域名、域或内网 DNS。根证书允许网段默认 `172.16.0.0/12`，可用 `--net` 缩小。根与中间证书采用 ECDSA P-256，有效期 10 年；中间证书只允许服务器 IP，根只允许指定私网段，均不允许真实域名。

**安装前生成**：先校验发布包并导入离线镜像，以下版本替换为包的 VERSION。由密钥保管人在离线 Linux 电脑或指定测试环境执行；不连接正式服务器。若在安装机器生成，保管人须立即取走并删除该机上的 root.key。

```bash
sha256sum -c SHA256SUMS
docker load -i images/aireview-images-<版本>.tar
umask 077
mkdir -p /安全离线目录/商衡SI-ca
docker run --rm --network none --pull never --user 0 \
  -v /安全离线目录/商衡SI-ca:/out aireview-backend:<版本> \
  python -m app.cli gen-ca --ip <服务器IP> --out /out
```

输出 root.crt、root.key、intermediate.crt、intermediate.key、root.sha256，已有任一目标文件即拒绝覆盖。root.sha256 是根证书 DER 的 SHA-256 指纹（大写、冒号分隔），与主密钥一起登记，独立提供给员工。根证书与 root.key 由主密钥同一保管人按同等级别离线保存，至少保留两份受控副本。服务器仅放以下四个文件：

```bash
sudo install -d -m 700 secrets/ca
# 从保管人的受控介质逐个复制，不复制 root.key。
sudo install -m 644 /介质/root.crt /介质/intermediate.crt /介质/root.sha256 secrets/ca/
sudo install -m 600 /介质/intermediate.key secrets/ca/
sudo ./scripts/install.sh --site <服务器IP>
```

install.sh 检查文件齐全且没有 root.key，从 root.sha256 自动生成证书下载页。Caddy 只读挂载 secrets/ca/，加载根公证书、中间证书及私钥，自动签发和续期站点证书；不自动更换外部中间证书，不向容器安装信任。没有 CA 的源码开发环境仍用 `tls internal`，不适用于正式安装。

**员工电脑导入**（用户本人操作）：方法一，打开 `http://<服务器IP>/cert/` 下载根证书，在下载文件夹中打开 PowerShell，按页面命令计算 DER SHA-256，核对与 IT 独立登记的指纹一致；再按页面命令 `Import-Certificate -FilePath .\shangheng-si-root.crt -CertStoreLocation Cert:\CurrentUser\Root` 导入，弹出“安全警告”时点“是”（不点“是”不会导入）。也可双击证书，选择“安装证书”→“当前用户”→“将所有的证书都放入下列存储”→“受信任的根证书颁发机构”，完成向导并在安全警告中点“是”。方法二，由 IT 通过受控介质提供同一 root.crt，按相同步骤核对与导入；也可运行 `certmgr.msc`，在“受信任的根证书颁发机构 / 证书”中右键“所有任务 / 导入”。两种方法均无需管理员权限。关闭并重新打开浏览器访问 `https://<服务器IP>/`，须无警告。不能只信任 HTTP 页显示的指纹，也不能用 SHA-1 指纹代替 SHA-256。

安装后核对：

```bash
docker compose exec -T web sh -c 'CADDY_CA_MODE=custom caddy validate --config /etc/caddy/Caddyfile'
curl --cacert secrets/ca/root.crt https://<服务器IP>/
curl -I http://<服务器IP>/cert/
```

HTTPS 应返回页面，下载页返回 200，其余 HTTP 路径跳转 HTTPS；不得通过任何下载路径获取私钥。`curl -k` 只用于排障，不能代替信任验证。

**换 IP**：在根允许网段内，由保管人在离线环境挂载原根证书与 root.key 到 `/offline:ro`、新空目录到 `/out`，运行同一镜像的 `python -m app.cli gen-ca --reissue-intermediate --ip <新IP> --root-cert /offline/root.crt --root-key /offline/root.key --out /out`。新中间证书期限不超过原根剩余期限。将输出四个文件替换服务器对应文件（先保留旧副本），修改 .env 中 SITE_ADDRESS，在部署目录运行 `sudo bash -c 'ROOT="$PWD"; source scripts/lib.sh; prepare_cert_page "<新IP>"'` 重新生成下载页，再 `docker compose up -d --no-build --force-recreate web`。员工更新书签，无需重新导入根。新 IP 超出根约束时须新建整套 CA 并重新导入。

**到期更换**：登记根与中间证书到期日；10 年到期前在新空目录生成整套 CA，登记新指纹，替换服务器证书、重新生成下载页并重建 web，通知员工导入新根，核对后删除旧根。根私钥丢失时无法沿用原根换 IP 或换发中间证书，须重建整套 CA 并重新导入。

### 5.1 安装到桌面与工作文件夹

前提：员工电脑已按 `http://服务器IP/cert/` 导入根证书，Edge 打开系统时没有证书告警。不使用组策略，各人自行操作：

1. 在 Edge 中打开 `https://服务器IP/`，点右上角“…”→“应用”→“将此站点作为应用安装”，确认名称“商衡SI”后安装；之后可从开始菜单或桌面图标打开，窗口没有地址栏。
2. 不想安装时，可手工建桌面快捷方式，目标写 `"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --app=https://服务器IP/`。
3. 需要开机即开：在 Edge 地址栏输入 `edge://apps`，对“商衡SI”勾选“登录时自动启动”。

系统不使用 Service Worker，不做离线，也不在本机缓存业务数据；安装只是给网页加桌面入口。

**工作文件夹**（Edge / Chrome 在 HTTPS 下可用）。在「智能审核 → 上传与设置」的上传区左上角，点击「选择工作文件夹」。智能助手的加入文件区也有此入口。选定后页面显示文件夹名称，点击旁边的「不使用」即可取消选择。

* 只列出该文件夹第一层、系统支持格式的文件，勾选并点“加入”的文件才会上传；选定、打开文件夹本身不上传任何内容；
* 有工作文件夹且授权有效时，审核报告、批注版、助手导出文件等直接写入该文件夹。同名时自动另存为「名称 (2).docx」。
* 未选工作文件夹或授权失效时，浏览器会在条件允许时弹出系统「另存为」，取消即结束导出。浏览器不支持该功能、点击激活过期或写入失败时，退回普通下载。
* 文件夹路径、名称和文件名不发送到服务器、不进日志，授权只保存在该浏览器里。浏览器提示“允许编辑文件”是授权写入导出文件，可在地址栏的站点权限中随时撤销。

## 6. 网络与防火墙

只有 web 发布 80 / 443。db、app、worker 不发布端口；converter network_mode 为 none。Docker 发布端口可能绕过 UFW 的 INPUT 规则，不能仅凭 UFW 状态断言访问范围。

以下是使用 iptables 后端且已有 DOCKER-USER 链的单网段示例，由 IT 替换网段、确认 SSH 管理路径与规则持久化后执行；Docker 使用其他防火墙后端时由 IT 配置对应规则，不直接套用：

```bash
sudo iptables -nL DOCKER-USER
sudo iptables -I DOCKER-USER 1 -m conntrack --ctstate ESTABLISHED,RELATED -j RETURN
sudo iptables -I DOCKER-USER 2 -p tcp -m multiport --dports 80,443 -s <内网网段> -j RETURN
sudo iptables -I DOCKER-USER 3 -p tcp -m multiport --dports 80,443 -j DROP
sudo iptables -nvL DOCKER-USER
```

分别从允许和不允许的客户端验证 HTTPS；检查命中计数并重启后复核持久化。示例按容器目标端口 80 / 443 过滤，应用在独占该服务的主机上；有其他 Docker 应用时须限定目标，避免误拦其他服务。

出站限制属于可选加固，不由脚本自动修改。域名可能解析到变化的 CDN IP，静态 IP 白名单会失效；IT 应采用支持域名策略的出口设备，保留 DNS 和必要服务。模型外发仍必须经过代码网关、脱敏和出口复检，网络白名单不能替代它们。

## 7. 日常运维

```bash
cd /data/apps/aireview
docker compose ps
docker compose logs --tail 100 app worker web converter
docker compose up -d --no-build --pull never
docker compose stop
docker compose restart web
df -h /data
curl -k -s -o /dev/null -w '%{http_code}\n' https://<服务器IP>/
curl -k -s -o /dev/null -w '%{http_code}\n' https://<服务器IP>/api/v1/auth/me
```

预期五服务运行，db、app、converter 健康；最后两项分别为 200、401。401 是未登录的预期结果。每天检查磁盘、备份成功时间及异地拉取结果；每周核查证书与服务重启策略。各服务 unless-stopped；手工 stop 后不会仅因主机重启而保证恢复，应明确执行 up。

日志标准输出，五服务各 50 MB × 5 轮转。管理员顶部备份失败、备份空间不足和调用上限提醒需处理；只分享脱敏后的诊断信息，不导出业务原文或密钥。不要手工删除 Docker 卷或运行 down -v 做日常停机。

## 8. 本地备份与密钥

`secrets/ca/` 与主密钥一样不进入业务备份；保管人另存 root.crt、root.key、intermediate.crt、intermediate.key、root.sha256，登记指纹与到期日。服务器仅保留四个非 root.key 文件；丢失中间私钥可由离线根重新签发，员工无需重新导入。不得把根私钥放入业务备份、发布包或服务器。

默认每日 Asia/Shanghai 02:00，保留 7 份，可在设置调整。worker 每分钟检查；当天过时才启动会补做一次，可能暂时占用备份任务。

```bash
sudo ./scripts/backup_now.sh --wait
cd /data/apps/aireview/backup
sha256sum -c <备份文件>.sha256
```

备份名形如 aireview_20261024_0200.bak，其校验文件为同名 `.bak.sha256`。只拉取完成的 .bak 及 .bak.sha256，不拉 .tmp、.restore。SHA 校验预期 OK。备份文件 0640，目录 2750；用户加入 aireview 组后重新登录才生效。

CLI `backup-now --wait --timeout 3600` 成功 0、失败 1、已有备份 2、等待超时 3；超时不代表任务已取消。脚本 backup_now.sh 仅接收 --wait。已有任务或同一分钟重名时先查看记录，在下一分钟重试，不循环反复触发。

恢复同时需要原主密钥、原备份密码和备份文件。备份加密不等于密钥已备份；丢失任一密钥无法恢复。轮换仅在新备份成功后清除最旧备份，异地端应设置独立保留策略，避免同步删除导致所有副本同时消失。

## 9. 异地备份（必做）

IT 创建使用密钥登录的专用 SFTP 账号，加入 aireview 组；该账号只需读取加密备份，不应加入 Docker 组或读取 secrets/。例如：`sudo usermod -aG aireview <运维账号>`。连接前独立核对 SSH 主机指纹。

Windows 安装 WinSCP，创建仅该任务账号可读的脚本，替换以下占位参数：

```text
option batch abort
option confirm off
open sftp://<运维账号>@<服务器IP>/ -privatekey="C:\Secure\aireview.ppk" -hostkey="<已核验的SSH主机指纹>"

cd /data/apps/aireview/backup

```

任务计划程序每天 03:00 执行 `WinSCP.com /ini=nul /script=C:\Secure\aireview-pull.txt /log=D:\AireviewBackup\pull.log`。先手工运行，退出码必须 0，日志可见两个类型文件；必要时根据实际备份耗时延后计划。账号私钥、脚本与日志限制 ACL；不在脚本写密码。拉取与备份并发时可能缺一份校验文件，下次补拉后再标为完整，不使用未校验副本恢复。

```powershell

```

逐字与对应 .sha256 第一列比较；不一致重新拉取，仍不一致停止恢复并报警。任务退出 0 只表示传输成功，不能代替 SHA 比对。每日检查计划任务结果与完整备份时间，管理机使用独立磁盘及独立保留策略。

## 10. 恢复与恢复失败怎么办

恢复到新机器时，先由保管人提供 secrets/ca/ 的根公证书、中间证书与中间私钥、指纹文件；没有原中间私钥时按第 5 节重新签发。保留原根，员工无需重新导入；新地址须在根允许网段内。业务备份不含证书，restore.sh 不会恢复或替换证书。先按第 5 节生成下载页并核对 HTTPS，根私钥始终离线。

部署后做一次恢复演练，此后每季度一次；正式数据上先审批并建 PVE 快照。确保对应密钥就位，备份和校验文件位于 .env 的 BACKUP_HOST_DIR，数据库正在运行，空闲空间至少为备份文件的 2.2 倍。

```bash
cd /data/apps/aireview
sudo ./scripts/restore.sh /data/apps/aireview/backup/<备份文件>
```

脚本先校验、解密、检查迁移与主密钥，展示摘要，须输入“确认恢复”。第 1–5 步失败不停止 app / worker；停止服务后不自动回滚。恢复成功所有用户须重新登录；核对原件、任务、报告及追问后完成演练记录。服务器版本须不低于备份版本；没有原件的备份无法通过原件解密验证主密钥，摘要会说明。

失败时保留日志、旧数据库 aireview_pre_restore、.restore-old/ 和备份，禁止重新运行清理命令。最稳妥的是按 IT 流程恢复 PVE 快照。手动回退必须由熟悉 PostgreSQL 的人员按失败阶段处理：

1. 停在数据库恢复之前、原库未被替换：排除原因后 `docker compose start app worker` 可继续使用原数据。
2. 已存在 aireview_pre_restore：停止 app / worker，先查询数据库名并确认无同名冲突。使用 `docker compose exec db psql -U aireview -d postgres` 进入维护库，断开业务连接后依次执行 `ALTER DATABASE aireview RENAME TO aireview_failed_restore;`、`ALTER DATABASE aireview_pre_restore RENAME TO aireview;`。若首次改名已发生但第二次未发生，依据实际库名恢复，不盲目重做。
3. 原件尚未交换时无需改文件；已交换或部分交换时必须同时恢复原件。可用 `docker compose run --rm --no-deps --user 0 worker sh` 进入原件卷，检查 /data/files/.restore-old 与 .restore-new。把当前 32 位 storage_key 文件移动到新建、权限 700 的隔离子目录，再逐个把 .restore-old 中的文件改名回 /data/files；只操作符合 storage_key 命名的普通文件，不覆盖、不删除隔离副本。部分交换时尚未移动的原文件仍在根目录，应逐文件对照旧目录与备份清单，不能把全部根目录内容当作新文件处理。
4. 数据库与原件一致后 `docker compose up -d --no-build app worker`，核对原件数及页面。不能确定部分交换的集合时停止手工回退，恢复 PVE 快照。未核对前不删除 aireview_failed_restore 或隔离文件。

### 10.1 更换主密钥

安排停机并由保管人分别保存新旧主密钥。在受控目录用当前发布版本的后端镜像运行 `python -m app.cli gen-key --out /out/master_key.new`，将该目录挂载为 `/out`。将新密钥文件交给运维人员，确认恰好 32 字节、权限为 600，再从部署目录运行：

```bash
sudo ./scripts/rotate_key.sh --new-key-file /安全目录/master_key.new
```

脚本先等待完整备份，再停止 app、worker，更换并验证加密数据，切换主密钥后重新启动服务。重新登录，测试已保存模型的连接，核对录音回放、译文和批注版导出。旧备份仍需要对应旧主密钥。

若轮换中途失败且脚本提示数据可能已部分轮换，保留 `secrets/master_key.pending`，使用同一新密钥再次运行脚本续做。若提示已切换为新主密钥，按服务启动失败排查。

## 11. 升级

从 3.1 起使用 `upgrade.sh` 升级，已在测试机完成 3.1.0-rc1 → 3.1.0-rc2 演练。本系统没有 2.x 正式安装，2.x → 3.1 未演练。升级须原样保留 secrets/ca/，由保管人与主密钥一起保管。若证书页模板更新，按第 5 节重新生成下载页。

先审批停机并在 PVE 创建快照，记录快照标识。新包解压到数据盘新目录，不能覆盖当前运行目录直接执行升级。

```bash
sudo mkdir -p /data/apps/aireview-upgrade-<版本>
sudo tar -xzf aireview-<版本>.tar.gz -C /data/apps/aireview-upgrade-<版本> --strip-components=1 --no-same-owner
cd /data/apps/aireview-upgrade-<版本>
sha256sum -c SHA256SUMS
sudo ./scripts/upgrade.sh --target /data/apps/aireview
```

输入“已创建快照”。默认先手动备份，失败就不继续；--skip-backup 只用于有充分证据的演练，不推荐生产使用。导入镜像并更新版本后自动迁移，等待 app 健康。Caddyfile 与现有 caddy/ 片段有差异时，脚本保留原文件，另存同名 .new，IT 比较合并后校验并重启 web；旧镜像保留。

升级后核对 HTTPS 200、未登录接口 401、版本、已有用户/任务/原件/报告及一次备份。失败不自动回退，按快照恢复；数据库迁移后不能只换回旧镜像。日志需说明失败阶段，保留升级包和备份用于排障。

## 12. 常见问题与交接

| 现象 | 处理 |
|---|---|
| 管理员忘记密码 | `docker compose exec -T app python -m app.cli create-admin --username recovery_admin` 新建临时管理员，初始密码按凭据流程交付；登录后重置原账号并停用临时账号。账号已存在时换唯一用户名，不改库内密码字段 |
| 备份失败提醒 | 查看设置中的失败原因、worker 日志、磁盘与目录权限，处理后在新分钟做备份并校验；已有备份时先等待 |
| 磁盘不足 | 检查 /data、异地副本及日志，不删除数据库或原件卷，不直接清除所有镜像；经审批清理历史候选包 |
| 浏览器证书告警 | 核查访问地址、证书 SAN、信任链与终端时间，不让员工长期忽略告警 |
| 模型连接失败、超时或额度提醒 | 管理员测试接口、核对模型名/密钥/预算与超时；日志不记录密钥；只用虚构样本重试 |

| 重启后未启动 | 先确认 /data 挂载和 Docker/containerd 正常，再 up -d --no-build --pull never；排查是否曾手工 stop |

交接须提供：版本与发布包 SHA-256、验收报告、快照记录、密钥保管人、管理员交付方式、异地拉取任务及最后一次恢复演练记录。不得将测试安装当作正式交付。


## 13. 本地模型

模型唯一清单为发布包中的 `models.yaml`（采用 YAML 的 JSON 子集），列出用途、固定来源、推理库、许可与冒烟命令。模型已装入镜像，运行时不下载、不在线升级。许可原文在 `licenses/models/<id>/`，随内部发布包保留。更换模型、版本或量化须重新选型并经负责人确认；换向量模型时升级步骤须重算法条、范本、知识库与历史合同的全部向量，不混用旧向量。

构建机需 Git、Docker、bash、tar、sha256sum 与 Python 3.11+（命令 `python3`，只用标准库）。在干净源码副本中执行：

```bash
# 离线目录包含 ner/、embedding/、asr/、mt/，以仓库 MANIFEST 校验。
COMPOSE_PROFILES=asr,mt bash deploy/scripts/build_release.sh 3.1.0 --models /offline/models --out /offline/release
# 硬件较小时只打包主线，生成的 .env.example 同样关闭 asr。
COMPOSE_PROFILES= bash deploy/scripts/build_release.sh 3.1.0 --models /offline/models --out /offline/release-main
```

旧 `--ner-models`、`--embedding-models` 参数已移除。转写五项共用 `asr/` 与一份 MANIFEST，构建时整组校验、复制；缺少启用模型即失败。各模型镜像构建后按清单断网冒烟；包内附清单、许可证、小型校验清单与镜像，均由 SHA256SUMS 覆盖。启用转写时增加第五个镜像 `aireview-transcriber:{版本}`；主线仍用原有四镜像。

以下为配置示例，正式安装前须结合容量验收结果确定。16 GiB 轮次由用户决定跳过，24 GiB 未做本轮整套容量测试，不能据此确定 balloon 下限。

| 来宾配置 | NER_THREADS | EMBED_THREADS | COMPOSE_PROFILES | ASR_CPUS | ASR_THREADS | ASR_MEM |
|-|-|-|-|-|-|-|
| 28 vCPU / 38 GiB | 8 | 8 | asr | 8 | 8 | 4g |
| 16 vCPU / 24 GiB | 8 | 8 | asr | 4 | 4 | 4g |
| 8 vCPU / 16 GiB | 4 | 4 | 留空 | 不启用 | 不启用 | 不启用 |

NER、向量资源为 worker 设置；app 固定 4 线程。转写编码器、标点和说话人使用 ASR_THREADS，转写解码器固定 1 线程。转写速度与内存来自 M-01 开发机参考测量（8 核：3 小时录音约 50 分钟，实时率 0.28；10 分钟录音全流程约 2 GB，3 小时推算 2.6～3.0 GB，4g 限额内完成）；要求是 1 小时会议 1 小时内处理完；24 GiB 档速度为推算。内存按各常驻模型、整组转写 4 GiB（五项共用，不相加五次）、主线高峰再留 4 GiB 预算；balloon 下限应覆盖该预算，不足则调高下限或关闭转写。资源不合适只改 `.env`，然后 `docker compose up -d`，无需改代码或重建镜像。

V31-Z-03 在 38 GiB 配置下同时运行转写、翻译与轻负载。三小时录音实时率 0.7809，未记录 OOM，但万字纯 NER 耗时 128.837 秒，超过 15 秒门槛，500 字追问提交被出口复检拦截。因此该并发组合尚未通过整体验收，正式配置及 balloon 下限交 V31-Z-04 审核。具体口径见演练报告。

安装仍按前文 `docker load` 与安装脚本进行。安装后核对：

```bash
docker compose run --rm worker python -m app.cli model-check
docker compose ps
```

命令可加模型 id（如 `model-check ner`）；返回码 1 表示有启用项不可用。系统状态接口的 `local_models` 同样列出 id、用途、固定来源版本、校验结果与启用状态，界面在 V31-U4 接入。轻量模型核对实际文件哈希（OCR 核对锁定包版本与三个模型），不加载重型模型。转写只读 MANIFEST 与 30 秒内的心跳：`manifest_only` 仅表示清单可读，`container_verified` 表示独立容器校验模型后健康；未启用为 `disabled`，启用但无有效心跳为 `unavailable`。重型组不可用只影响录音，轻量模型校验失败仍阻止 worker 启动。

用虚构合同检查一次脱敏；启用转写后用短虚构录音检查一次。transcriber 无网络、只挂 /spool、不挂主密钥、原件或数据库；模型在容器用时加载、空闲 5 分钟卸载，开始前等内存，解析任务进行时在段落间暂停让路；心跳由不加载模型的独立小进程写入。

转写问题处理：系统状态或 `model-check asr` 显示 `unavailable` 时先看 `docker compose ps transcriber` 与其日志（只有 id、时长、耗时、结果代码）；容器正常而录音仍失败时，让用户在会话中点“重试转写”（从加密回放副本重新解码，不需重新上传）。/spool 内存盘为 2 GiB（只占实际写入的内存），可容纳几个 3 小时录音同时排队，V31Q-80。

### 13.1 本地翻译（V31Q-100）

只启用经确认的 Hy-MT2-7B Q6_K。它生成需要人工核对的离线译稿，万字中译英在约 36 GiB 测试机实测约 65 分钟；名称、金额、币种、付款条件须逐段核对。翻译页可切换“本地 · 不外发 / 云端 · 脱敏后发送”；本地只需解析完成，云端仍须确认脱敏。译文加密保存，不作为之后云端对话的历史发送；译文和双语对照均可导出 Word。

离线模型目录增加 `mt/HY-MT2-7B-Q6_K.gguf` 和 `mt/llama.cpp.tar.gz`。源码归档为 ggml-org/llama.cpp 固定提交 `8642541b255bfb5dc39cd351a178be09013a55d6`（GitHub 该提交 tar.gz，SHA-256 `1688a167a8edd9499cdd0c19b8bd044f0fa184b466981977bbf2222d884953a4`），由构建脚本复制并核对；模型按仓库 MANIFEST 校验。构建时 `COMPOSE_PROFILES=asr,mt` 才增加 translator 镜像；只用翻译时可设为 `mt`。安装后的 `.env` 同样加入 `mt`，再 `docker compose up -d`。

| 来宾配置 | MT_THREADS | MT_CPUS | MT_CPUSET | MT_MEM | 启用建议 |
|-|-|-|-|-|-|
| 28 vCPU / 约 36～38 GiB | 4 | 8 | 8-15 | 12g | 与 asr 同开已实测，NER 和完整追问未通过，正式配置待审核 |
| 16 vCPU / 24 GiB | 4 | 8 | 按实际空闲 CPU 分配 | 12g | 最多选择一个重型组；本轮未验证整套容量，启用前核对主线高峰与剩余内存，不视为已验收配置 |
| 8 vCPU / 16 GiB | — | — | — | — | 只跑主线，不启用 mt |

translator 无网络、只读、只挂内存盘 `/spool`，不挂原件、主密钥和数据库。它一次只处理一个段落，在段落边界等待解析 / 脱敏 / 追问；启动加载前等待可用内存达到 MT_MEM，空闲五分钟卸载。MT_CPUSET 必须属于实际可用 CPU，线程保持选型确认的 4。系统状态查看 mt 行，CLI 用 `python -m app.cli model-check mt`；无有效心跳仅禁用翻译功能，不阻止审核主线。
