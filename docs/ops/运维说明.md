# 商衡SI V1.0 运维说明

适用：PVE 中的 Ubuntu 26.04 x86_64 虚拟机，10 核、15 GiB 内存；系统盘约 32 GiB，ext4 数据盘 /data 约 344 GiB。命令在服务器 bash 中执行，除首次解包外默认已进入 `/data/apps/aireview`。示例中的 `<服务器IP>`、`<运维账号>`、`<备份文件>`、`<内网网段>`须由 IT 替换，不直接粘贴尖括号。

本文交付的是部署候选的操作说明。M8-03 安装升级实跑属于测试；全量验收、恢复演练、真实模型抽查和正式安装由 M8-05 单独完成。正式安装后，停服、清空或替换数据须先得到负责人同意。

## 1. 概览与准备

系统有五个服务：db（PostgreSQL 16.15）、app（接口与迁移）、worker（解析、审核与备份）、converter（断网 LibreOffice 转换）、web（Caddy 与静态前端）。converter 与 worker 只通过 512 MB 内存盘卷 convert_spool 交换旧格式文件；converter 不接网络、不接数据库、不挂载密钥或原件。

准备四镜像离线发布包、模型接口地址及 API 密钥、内网 IP 或域名、证书方案、密钥保管人，以及独立 Windows 异地备份管理机。发布包已包含运行依赖和 OCR 模型；服务器通过 docker load 导入，运行时不拉取镜像或模型。

安装目录 `/data/apps/aireview`；备份 `/data/apps/aireview/backup`；Docker `/data/docker`；containerd `/data/containerd`。备份与数据库在同一块盘，必须做异地备份。原件与数据库是 Docker 卷，不能只复制安装目录代替备份。

## 2. 服务器检查

```bash
findmnt /data
df -h / /data
docker version
docker compose version
sudo docker info --format '{{.DockerRootDir}}'
sudo grep -E '^root[[:space:]]*=' /etc/containerd/config.toml
sudo ss -ltnp '( sport = :80 or sport = :443 )'
```

预期 /data 独立挂载；Docker 与 containerd 的 root 都在数据盘；首次安装前 80 / 443 没有监听者。脚本会检查安装目录、备份目录、Docker root、containerd root 不在根分区。/data 未挂载时停止操作，先由 IT 修复挂载；不得让 Docker 写满系统盘。

不得改动 `/etc/docker/daemon.json` 的 data-root、registry-mirrors、日志轮转。当前服务器已完成 containerd 迁移，无须重复操作。新服务器若需迁移，先建 PVE 快照、停业务及 Docker/containerd，在所有数据仍完整保留时由 IT 执行：

```bash
sudo systemctl stop docker.service docker.socket containerd.service
sudo mkdir -p /data/containerd
sudo rsync -aHAX --numeric-ids /var/lib/containerd/ /data/containerd/
sudoedit /etc/containerd/config.toml
# 将顶层 root 设置为 /data/containerd；不是 plugins 段里的 root。
sudo systemctl start containerd.service docker.service
sudo docker images
sudo docker ps -a
```

确认镜像、卷、容器及服务健康后才安排旧目录清理；不自动删除旧存储。新装系统缺少配置文件时应由 IT 生成与已安装 containerd 版本相符的配置后再设顶层 root，不能直接覆盖现有配置。

## 3. 首次部署与首次登录

由 IT 将发布包解压至尚未安装的 `/data/apps/aireview`；包内不是源码仓库，根目录直接有 docker-compose.yml 和 scripts/。解包时去掉包内顶层目录，并让文件属主为 root：

```bash
sudo mkdir -p /data/apps/aireview
sudo tar -xzf aireview-1.0.0.tar.gz -C /data/apps/aireview --strip-components=1 --no-same-owner
cd /data/apps/aireview
sha256sum -c SHA256SUMS
sudo ./scripts/install.sh --site <服务器IP> --admin admin
```

脚本校验发布包、数据盘、端口，导入四镜像，创建 gid 10001 的 aireview 组；生成 .env、主密钥和备份密码，启动服务并创建管理员。已存在 .env 或密钥时拒绝重装，应走升级。备份目录属主 10001:10001、权限 2750；secrets/ 为 700，密钥 600；.env 为 root:600。

初始管理员密码仅显示一次，按本单位凭据交接流程交付，不放入工单或共享日志。自动演练可用以下方式只写入 root 可读文件；`--yes` 跳过确认，仅限演练，不表示已创建快照：

```bash
sudo bash -c 'umask 077; ./scripts/install.sh --site <服务器IP> --yes > /root/aireview-install.log 2>&1'
```

浏览器访问 HTTPS，首次登录强制改密。进入设置填写模型，确认备份时间并做一次备份，配置异地拉取。把 secrets/master_key 与 secrets/backup_password 各保留离线副本，交专人保管；屏幕不会显示两份密钥。不得覆盖已有密钥。

## 4. 模型设置推荐值

管理员在设置中填写 API 密钥，不把密钥放在命令行参数或文档。推荐接口 `https://api.deepseek.com`，模型 `deepseek-flash`（全小写，须与厂商控制台的模型名完全一致，否则返回 HTTP 400）；最大输出 32000、超时 600 秒、分段长度 300000、JSON 输出开启、temperature 0.1。附加请求参数不必手写：点输入框下方的“填入推荐值”，即填入：

```json
{"thinking":{"type":"enabled"},"reasoning_effort":"high"}
```

“测试连接”测的是**已保存**的设置：先点页面底部“保存”，再点“测试连接”；有未保存的修改时页面会提示先保存。测试失败时，提示中会附上模型服务返回的原因（如“支持的模型名为……”），按原因修改后保存再测。以上为项目设计推荐值，须通过连接测试与虚构样本核对。思考模式下 temperature 不生效。每月调用上限按单位预算设置正整数；0 表示不限制，不推荐直接沿用到生产。单价须按控制台账单币种填写每百万 token 的输入、输出单价；系统只有两项单价，估算不区分峰谷和缓存折扣。不能将美元数直接填进按人民币管理的预算。

2026-10-24 核对的官方美元峰时未缓存输入 / 输出价为 0.30 / 1.20 美元每百万 token；这仅是核价参考，不是人民币推荐输入值。上线前按实际账单币种与预算确认并填写。来源：[官方调用说明](https://api-docs.deepseek.com/quick_start/first_api_call)、[官方价格表](https://api-docs.deepseek.com/quick_start/pricing/)。价格与模型服务版本可能变更，交付时重新核对；本系统不自动变更厂商参数。

## 5. HTTPS 与证书

默认 Caddy 内部 CA，裸 IP 访问由全局 default_sni 指定默认证书。验证：

```bash
docker compose exec -T web caddy validate --config /etc/caddy/Caddyfile
curl -k -s -o /dev/null -w '%{http_code}\n' https://<服务器IP>/
docker compose cp web:/data/caddy/pki/authorities/local/root.crt ./aireview-root.crt
```

预期配置有效、HTTP 200。由 IT 验证根证书后通过组策略导入员工电脑“受信任的根证书颁发机构”。curl 的 -k 仅用于排障，不能代替浏览器的证书信任部署。不要分发 CA 私钥。

改域名时先配置内网 DNS，再改 .env 的 SITE_ADDRESS，重建 web：`docker compose up -d --no-build web`。公司证书放 certs/server.crt 与 certs/server.key，在 Caddyfile 将 `tls internal` 换为 `tls /etc/caddy/certs/server.crt /etc/caddy/certs/server.key`，校验后 `docker compose restart web`。certs 以只读方式挂载；私钥权限由 IT 限制，Caddy 运行用户必须可读。80 自动跳转 HTTPS。

## 6. 网络与防火墙

只有 web 发布 80 / 443。db、app、worker 不发布端口；converter network_mode 为 none。Docker 发布端口可能绕过 UFW 的 INPUT 规则，不能仅凭 UFW 状态断言访问范围。

以下是使用 iptables 后端且已有 DOCKER-USER 链的单网段示例，由 IT 替换网段、确认 SSH 管理路径与规则持久化后执行；Docker 使用其他防火墙后端时由 IT 配置对应规则，不直接套用：

```bash
sudo iptables -nL DOCKER-USER
sudo iptables -I DOCKER-USER 1 -m conntrack --ctstate ESTABLISHED,RELATED -j RETURN
sudo iptables -I DOCKER-USER 2 -p tcp -m multiport --dports 80,443 -s <内网网段> -j RETURN
sudo iptables -I DOCKER-USER 3 -p tcp -m multiport --dports 80,443 -j DROP
sudo iptables -nvL DOCKER-USER
```

分别从允许和不允许的客户端验证 HTTPS；检查命中计数并重启后复核持久化。示例按容器目标端口 80 / 443 过滤，应用在独占该服务的主机上；有其他 Docker 应用时须限定目标，避免误拦其他服务。

出站限制属于可选加固，不由脚本自动修改。域名可能解析到变化的 CDN IP，静态 IP 白名单会失效；IT 应采用支持域名策略的出口设备，保留 DNS 和必要服务。模型外发仍必须经过代码网关、脱敏和出口复检，网络白名单不能替代它们。

## 7. 日常运维

```bash
cd /data/apps/aireview
docker compose ps
docker compose logs --tail 100 app worker web converter
docker compose up -d --no-build --pull never
docker compose stop
docker compose restart web
df -h /data
curl -k -s -o /dev/null -w '%{http_code}\n' https://<服务器IP>/
curl -k -s -o /dev/null -w '%{http_code}\n' https://<服务器IP>/api/v1/auth/me
```

预期五服务运行，db、app、converter 健康；最后两项分别为 200、401。401 是未登录的预期结果。每天检查磁盘、备份成功时间及异地拉取结果；每周核查证书与服务重启策略。各服务 unless-stopped；手工 stop 后不会仅因主机重启而保证恢复，应明确执行 up。

日志标准输出，五服务各 50 MB × 5 轮转。管理员顶部备份失败、备份空间不足和调用上限提醒需处理；只分享脱敏后的诊断信息，不导出业务原文或密钥。不要手工删除 Docker 卷或运行 down -v 做日常停机。

## 8. 本地备份与密钥

默认每日 Asia/Shanghai 02:00，保留 7 份，可在设置调整。worker 每分钟检查；当天过时才启动会补做一次，可能暂时占用备份任务。

```bash
sudo ./scripts/backup_now.sh --wait
cd /data/apps/aireview/backup
sha256sum -c <备份文件>.sha256
```

备份名形如 aireview_20261024_0200.bak，其校验文件为同名 `.bak.sha256`。只拉取完成的 .bak 及 .bak.sha256，不拉 .tmp、.restore。SHA 校验预期 OK。备份文件 0640，目录 2750；用户加入 aireview 组后重新登录才生效。

CLI `backup-now --wait --timeout 3600` 成功 0、失败 1、已有备份 2、等待超时 3；超时不代表任务已取消。脚本 backup_now.sh 仅接收 --wait。已有任务或同一分钟重名时先查看记录，在下一分钟重试，不循环反复触发。

恢复同时需要原主密钥、原备份密码和备份文件。备份加密不等于密钥已备份；丢失任一密钥无法恢复。轮换仅在新备份成功后清除最旧备份，异地端应设置独立保留策略，避免同步删除导致所有副本同时消失。

## 9. 异地备份（必做）

IT 创建使用密钥登录的专用 SFTP 账号，加入 aireview 组；该账号只需读取加密备份，不应加入 Docker 组或读取 secrets/。例如：`sudo usermod -aG aireview <运维账号>`。连接前独立核对 SSH 主机指纹。

Windows 安装 WinSCP，创建仅该任务账号可读的脚本，替换以下占位参数：

```text
option batch abort
option confirm off
open sftp://<运维账号>@<服务器IP>/ -privatekey="C:\Secure\aireview.ppk" -hostkey="<已核验的SSH主机指纹>"
lcd D:\AireviewBackup
cd /data/apps/aireview/backup
get -neweronly *.bak
get -neweronly *.bak.sha256
exit
```

任务计划程序每天 03:00 执行 `WinSCP.com /ini=nul /script=C:\Secure\aireview-pull.txt /log=D:\AireviewBackup\pull.log`。先手工运行，退出码必须 0，日志可见两个类型文件；必要时根据实际备份耗时延后计划。账号私钥、脚本与日志限制 ACL；不在脚本写密码。拉取与备份并发时可能缺一份校验文件，下次补拉后再标为完整，不使用未校验副本恢复。

```powershell
certutil -hashfile D:\AireviewBackup\<备份文件> SHA256
```

逐字与对应 .sha256 第一列比较；不一致重新拉取，仍不一致停止恢复并报警。任务退出 0 只表示传输成功，不能代替 SHA 比对。每日检查计划任务结果与完整备份时间，管理机使用独立磁盘及独立保留策略。

## 10. 恢复与恢复失败怎么办

部署后做一次恢复演练，此后每季度一次；正式数据上先审批并建 PVE 快照。确保对应密钥就位，备份和校验文件位于 .env 的 BACKUP_HOST_DIR，数据库正在运行，空闲空间至少为备份文件的 2.2 倍。

```bash
cd /data/apps/aireview
sudo ./scripts/restore.sh /data/apps/aireview/backup/<备份文件>
```

脚本先校验、解密、检查迁移与主密钥，展示摘要，须输入“确认恢复”。第 1–5 步失败不停止 app / worker；停止服务后不自动回滚。恢复成功所有用户须重新登录；核对原件、任务、报告及追问后完成演练记录。服务器版本须不低于备份版本；没有原件的备份无法通过原件解密验证主密钥，摘要会说明。

失败时保留日志、旧数据库 aireview_pre_restore、.restore-old/ 和备份，禁止重新运行清理命令。最稳妥的是按 IT 流程恢复 PVE 快照。手动回退必须由熟悉 PostgreSQL 的人员按失败阶段处理：

1. 停在数据库恢复之前、原库未被替换：排除原因后 `docker compose start app worker` 可继续使用原数据。
2. 已存在 aireview_pre_restore：停止 app / worker，先查询数据库名并确认无同名冲突。使用 `docker compose exec db psql -U aireview -d postgres` 进入维护库，断开业务连接后依次执行 `ALTER DATABASE aireview RENAME TO aireview_failed_restore;`、`ALTER DATABASE aireview_pre_restore RENAME TO aireview;`。若首次改名已发生但第二次未发生，依据实际库名恢复，不盲目重做。
3. 原件尚未交换时无需改文件；已交换或部分交换时必须同时恢复原件。可用 `docker compose run --rm --no-deps --user 0 worker sh` 进入原件卷，检查 /data/files/.restore-old 与 .restore-new。把当前 32 位 storage_key 文件移动到新建、权限 700 的隔离子目录，再逐个把 .restore-old 中的文件改名回 /data/files；只操作符合 storage_key 命名的普通文件，不覆盖、不删除隔离副本。部分交换时尚未移动的原文件仍在根目录，应逐文件对照旧目录与备份清单，不能把全部根目录内容当作新文件处理。
4. 数据库与原件一致后 `docker compose up -d --no-build app worker`，核对原件数及页面。不能确定部分交换的集合时停止手工回退，恢复 PVE 快照。未核对前不删除 aireview_failed_restore 或隔离文件。

## 11. 升级

先审批停机并在 PVE 创建快照，记录快照标识。新包解压到数据盘新目录，不能覆盖当前运行目录直接执行升级。

```bash
sudo mkdir -p /data/apps/aireview-upgrade-1.0.1
sudo tar -xzf aireview-1.0.1.tar.gz -C /data/apps/aireview-upgrade-1.0.1 --strip-components=1 --no-same-owner
cd /data/apps/aireview-upgrade-1.0.1
sha256sum -c SHA256SUMS
sudo ./scripts/upgrade.sh --target /data/apps/aireview
```

输入“已创建快照”。默认先手动备份，失败就不继续；--skip-backup 只用于有充分证据的演练，不推荐生产使用。导入镜像并更新版本后自动迁移，等待 app 健康。Caddyfile 不同时保留原文件，将新内容放 Caddyfile.new，IT 比较合并后校验并重启 web；旧镜像保留。

升级后核对 HTTPS 200、未登录接口 401、版本、已有用户/任务/原件/报告及一次备份。失败不自动回退，按快照恢复；数据库迁移后不能只换回旧镜像。日志需说明失败阶段，保留升级包和备份用于排障。

## 12. 常见问题与交接

| 现象 | 处理 |
|---|---|
| 管理员忘记密码 | `docker compose exec -T app python -m app.cli create-admin --username recovery_admin` 新建临时管理员，初始密码按凭据流程交付；登录后重置原账号并停用临时账号。账号已存在时换唯一用户名，不改库内密码字段 |
| 备份失败提醒 | 查看设置中的失败原因、worker 日志、磁盘与目录权限，处理后在新分钟做备份并校验；已有备份时先等待 |
| 磁盘不足 | 检查 /data、异地副本及日志，不删除数据库或原件卷，不直接清除所有镜像；经审批清理历史候选包 |
| 浏览器证书告警 | 核查访问地址、证书 SAN、信任链与终端时间，不让员工长期忽略告警 |
| 模型连接失败、超时或额度提醒 | 管理员测试接口、核对模型名/密钥/预算与超时；日志不记录密钥；只用虚构样本重试 |
| converter 不健康 | 查 converter 日志和内存，确认 spool tmpfs 与权限；旧格式失败可另存 DOCX/XLSX，不给 converter 加网络 |
| 重启后未启动 | 先确认 /data 挂载和 Docker/containerd 正常，再 up -d --no-build --pull never；排查是否曾手工 stop |
| /data 未挂载 | 停止业务写入，由 IT 修复挂载；禁止改路径到系统盘绕过脚本检查 |

交接须提供：版本与发布包 SHA-256、验收报告、快照记录、密钥保管人、管理员交付方式、异地拉取任务及最后一次恢复演练记录。不得将测试安装当作正式交付。M8-05 应独立审核 M8-02～M8-04 提交，执行全部验收和正式安装后再宣布交付。
